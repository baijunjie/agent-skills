# 全局规则

与项目自己的指令文件冲突时，以项目的为准。

## 注释规范

注释的唯一读者是不了解此处上下文的未来维护者，判断标准是「读代码本身得不到、但维护时必须知道」。

**应该写：**

- 设计意图与取舍理由：为什么这样实现、为什么没采用更直观的写法。
- 代码读不出的隐含前提与约束：外部接口的古怪行为、并发与性能考虑、边界条件、单位 / 时区等易错约定。
- 复杂算法、正则、位运算的整体思路，让人不必逐行反推。
- `TODO`：临时代码、部分实现、等待外部依赖完善的内容必须标注。
- 改代码时同步改它的注释——过期的注释比没有注释更有害。

**不应该写：**

- 复述代码字面含义的冗余注释（显而易见的赋值、getter/setter 等）。
- 变更历史：删掉了什么、原来是什么、「新增」「修改」标记——这些交给 git。
- 被注释掉的代码，直接删除。
- 与其它实现的对比或交叉引用、对项目文档的引用——被引用方一改动就失真。
- 过程性信息：引发本次改动的问题 / Bug 编号 / 需求讨论 / 评审反馈。
- 说给本次改动评审者听的话（「这里改用了缓存」）——注释属于代码，不属于这次 diff。

## Git 提交信息

- 不要在 commit 消息或 PR 描述里留下任何 AI 痕迹：不写 `Co-Authored-By`、不写
  「Generated with …」、不提 AI 协助。
- 以人类开发者的身份撰写——第一人称、自然语气，不作任何关于自己是 AI 的声明。
- 遵循 Conventional Commits（`feat:` / `fix:` / `refactor:` / `docs:` / `chore:` 等前缀）。
- 提交信息的语言跟随仓库历史。

## 分派子任务

- 一次只交代一件事，说清完成判据；让它报结论，不要它复述过程。
- **按任务难度选执行者，不要一律用最强的**：批量搜索、代码定位这类机械活给最便宜的档，
  架构设计与技术选型才给最强的。

## 编码结束自检

完成开发后，无论改动大小，都按以下顺序逐项自检：

1. **代码自审** —— 通读本次修改涉及的每个文件全文（而非仅看 diff），确认：改动后是否存在可进一步
   优化的实现（重复逻辑、命名、结构、可读性、异常处理等）；是否遗留了因本次改动而产生的死代码
   （未使用的变量/函数/导入/类型/分支，被替换后残留的旧实现等），如有则一并清理。
2. **文档更新** —— 本次改动要更新任何给后来者看的文档时，**派子代理去写，不要自己接着写**：
   你手上的上下文最容易把别处写过的东西再写一遍。没有子代理机制就自己写，
   但落笔前必须先完整读一遍要改的那几份。
3. **代码质量检查** —— 执行项目约定的质量检查命令（格式化、类型检查、Lint 等），确认无报错。

## 仅适用于 Claude Code：子代理档位

- 派子代理时不要沿用主会话的档位：主会话的 effort **会被子代理继承**，而 effort 只能钉在
  agent 定义里，所以按难度从下表选一个，而不是临时传 `model`。

  | agent | 档位 | 用途 |
  |---|---|---|
  | `mechanical` | haiku | 批量搜索、代码定位、批量替换、格式化、简单文本处理。**haiku 不支持 effort，不要给它写** |
  | `implement` | sonnet / medium | 编写具体逻辑代码、实现已定方案、目标明确的重构与修 Bug。默认的性价比选择 |
  | `investigate` | opus / high | 跨模块疑难排查、根因定位、大范围重构 |
  | `architect` | fable / xhigh | 架构设计、跨模块改造方案、技术选型。只在确实需要最强推理能力时用 |
- 用内置 agent（`general-purpose` / `Explore` / `Plan`）时仍要显式传 `model`，但它们的 effort
  一定跟着主会话，所以别拿它们跑廉价的批量任务。
- 新增或修改 agent 定义时只写档位名
  （模型 `fable` / `opus` / `sonnet` / `haiku`，effort `low` / `medium` / `high` / `xhigh` / `max`），
  不要写具体模型版本号，避免模型换代后规则失效。
