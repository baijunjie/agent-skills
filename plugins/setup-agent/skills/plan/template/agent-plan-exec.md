# 按开发计划文档执行开发

「汇报」指停下，写清要定的事（有哪些选项）、缺的信息或需要用户协助完成的事，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。「通知」指做完后告诉用户一声，不等答复。

**一次会话默认只处理一个里程碑**：做完并收尾就结束，不接着做下一个；用户明确要求连做多个时按用户的指示，前一个收尾完才开始下一个。用词：

- **开工**：里程碑里已有 checkbox 被勾过，或带「中途交接」节；没有就是「未开工」
- **收尾**：下面「里程碑收尾」的三步（清账、固化、删除）都做完；「最终确认里程碑」指专门汇总需要用户确认的事项的那一份（见「调整里程碑」）
- **「目标 / 完成判据」块**：里程碑文档开头点明目标与完成判据的那段引用文字
- **移交**：把做不了的事写进别处，由别处接手

## 选定里程碑

先看项目有没有自己的文档规范（见「如何了解项目上下文」），有就先读，其中关于计划目录的约定以它为准。

开发计划文档目录默认 `docs/plans/`，项目已有自己的约定时按项目的。

用户指明了做哪份就做哪份，只指明主题时取该主题里第一个还没收尾的；没指明时，自己到开发计划文档目录里挑一个当前最适合开工的里程碑。目录不存在或是空的，直接说没有可做的开发计划。

挑选判据：

- 优先接着已开工的主题往下做——有里程碑已勾了一部分（含带「中途交接」节的），或前序里程碑已收尾的主题
- 同一主题内按编号顺序（`02` < `02a` < `03`）取第一个还没收尾的里程碑；前序里程碑还没收尾的不能跳过去做后面的
- 多个主题都可开工时，取依赖最少的；主题之间的依赖看各主题 `README.md` 总览里的写明，没写明、候选之间取舍不清（优先级相当、互相有依赖）时，汇报，列出候选让用户拍板，不要自己硬挑

选定后先说明做的是哪个里程碑，再按下面检查，通过了才开工。不论是自己挑的还是用户指明的，遇到下列情形都不开工：

- 前序里程碑还没收尾（用户指明了靠后的一份时）
- 是最终确认里程碑（`NN-最终确认.md`）而用户不在场
- 「交接」节里有标「需用户协助，未完成前不得开工」的事而用户还没协助完成
- 带「中途交接」节，且上次卡住的条件还没解除

用户在场与否、协助是否完成、条件是否解除，都要问用户或自己核实；核实不了就按不在场、未完成、未解除处理。
自己挑的先换别的主题，都没有再汇报；用户指明的直接汇报。「需用户协助」标注已经满足的，删掉标注再开工，该事项本身仍是本里程碑的任务，照常了结。

## 如何读开发计划文档

- **主题目录**：开发计划文档目录下的 `YYYYMMDD-{开发简述}/`，一个开发主题一个目录
- **总览文档**：主题目录下的 `README.md`——问题描述、方案概述、关键设计决策；
  拆成多个里程碑时这里还有里程碑清单。清单每项一行：未收尾的写 `NN 开发简述`，收尾后改成 `NN 已收尾`，对应文档已删掉
- **里程碑文档**：按编号顺序排列的文件（`02a` 排在 `02` 之后、`03` 之前），一份对应一个能独立测试、能独立合并的里程碑，
  开头有「目标 / 完成判据」块。编号即依赖顺序，按顺序做
- **只有 `README.md` 的目录**：说明这个主题只有一个里程碑，总览与里程碑内容都在这一份里，
  按它开发即可，不要另建编号文档
- **「交接」节**：位于「目标 / 完成判据」之后，是前面做完的工作移交给本里程碑的账——过渡层（代码里有对应 `TODO`）、
  要接的接口、待统一的约定、需要用户协助才能继续的事（标「需用户协助，未完成前不得开工」）。
  这些都是本里程碑的任务，**开工前先读，做完要逐条了结，了结不了的重新走清账分流**；
  过渡层都标了 `TODO`，不要当成遗漏顺手删掉，各自写明了由哪个里程碑删
- **「中途交接」节**：位置同上，与「交接」节并存时排在它前面（只有 `README.md` 的主题写在里程碑部分的「目标 / 完成判据」之后），是上次无法继续时留下的上下文（见下面「无法继续时的中途交接」）。接手先读；恢复开发后，仍有用的上下文并入正文（设计取舍写进对应设计段，没做的写成 checkbox），其余删掉
- **checkbox 条目**：勾上表示已实现且已验证；完成一个就立即勾上，严禁攒到最后批量勾

## 如何了解项目上下文

- 项目有自己的文档规范就先读它（选定里程碑之前），文档目录与本项目额外的规则以它为准
- 否则（选定里程碑之后、动手之前）从总索引（默认 `docs/README.md`）入手，按其中的项目地图定位要动的模块，
  再读对应的产品文档确认现有行为

## 计划与实际不符、做不下去时

- 补漏掉的条目、修正与代码不符的设计，直接改计划文档；改「完成判据」、改关键设计决策、缩减范围，先汇报，得到决定再改
- 里程碑里某一项被阻断（缺外部条件、要用户协助）时，不依赖它的其它项照常做；整个里程碑都做不下去才停下：若本次会话要结束或代码要合并，先按「无法继续时的中途交接」写好，再汇报

## 调整里程碑

计划执行中新建、插入里程碑，以及整理编号，都在这里定。编号即开发顺序，不填补缺口，已有文档不改号（下面「插到最前」除外）。

- **新建的里程碑**：格式同其它里程碑文档——开头点明目标与完成判据，内容项写成 checkbox，命名 `[编号]-[开发简述].md`；
  只写要做的事与移交内容，不添加没有依据的设计，也不写实现代码与代码落点；同步 `README.md` 里程碑清单（单份转多份时清单新建，写入 `01` 与新里程碑）
- **位置**：必须排在它依赖的里程碑之后；被后面某个里程碑依赖的，插到最早的依赖者之前；两头都没有约束的，排到后面，但一律在最终确认里程碑之前。
  最早的依赖者已开工时，插到它之前会改动已开工里程碑的前提，排到它之后又会让依赖倒挂，汇报，由用户决定；前后约束互相夹不出位置时同样汇报
- **编号**：排到最后且没有最终确认里程碑时，接在清单与目录里出现过的最大整数编号之后；
  其余情况（插到中间，或已有最终确认里程碑）取插入点前一份编号的整数部分，加一个排序落在前后两份之间的字母后缀（`02` 与 `03` 之间插入得 `02a`，已有 `02a` 时再插到它后面得 `02b`，顺序为 `02` < `02a` < `02b` < `03`）；放不下时汇报
- **插到最前**：只有所有里程碑都没开工（没有已收尾的，没有已勾选或带中途交接的，代码里也没有指向编号的 `TODO`）时才会出现，
  相当于开工前改计划，重新为计划内所有里程碑编号并同步 `README.md` 清单；已有开工的，新里程碑一律排在它们之后用后缀，与它们的依赖关系写进新里程碑文档
- **只有 `README.md` 的主题要加里程碑**：把里程碑内容（「目标 / 完成判据」块、技术设计、实现方案、checkbox、交接、开发者提示）移进 `01-…` 编号文档，
  新里程碑从 02 起编，`README.md` 只留问题描述、方案概述、关键设计决策与里程碑清单
- **最终确认里程碑**：只在出现无法现在做或确认、又不阻断后续开发的事项时才建，命名 `NN-最终确认.md`，排在整个主题的最后，已有就追加条目；
  每条写明怎么确认、期望结果。它是终点，后面没有可交的地方：确认项必须用户在场确认完才算做完，不得再往后留；
  确认出缺陷就在本里程碑内修复并重新确认，不新建里程碑

## 里程碑收尾

**一个里程碑要真正做完才收尾，不留尾巴**：所有未了结的事都要移交到后面未开发的里程碑文档里，或由用户处理掉。

### 1. 清账

收尾前先按「目标 / 完成判据」块里的完成判据逐条验证，再对所有未勾条目、未验证项、刻意留下的过渡层逐条分流。**能做的就做**：
现在能实现、能验证、又不越出本里程碑范围的，必须现在做完，「以后再说」不是去向。现在确实做不了的，去向只有下面几种。
还没实现的项做不了，里程碑就不能收尾，走「无法继续时的中途交接」；只有验证、确认类的项可以按下表移交后收尾：


| 情形 | 怎么办 |
|---|---|
| 确属后面某个未开发里程碑的范围（现在做会越出本里程碑），且不需要用户协助或外部条件 | 写进该里程碑文档的「交接」节 |
| 没有合适的里程碑接，且不需要用户协助或外部条件 | 按「调整里程碑」新建或插入里程碑，再写进它的「交接」节 |
| 需要用户协助或外部条件才能做或验证，且**阻断后续开发**（后面的里程碑依赖它的结果） | 写进第一个依赖它的里程碑的「交接」节，标「需用户协助，未完成前不得开工」；先写好，再收尾本里程碑，最后通知用户，本次会话到此为止（用户明确要求连做时，也先停在这里等用户协助） |
| 需要用户协助或外部条件才能做或验证，但**不阻断后续开发** | 汇入「最终确认里程碑」（见「调整里程碑」） |
| 要放弃、不做 | 属于范围变更，汇报由用户决定，不自行放弃；用户同意后删掉相应条目并同步 `README.md` 的范围描述 |

- 是否阻断由你先判断，拿不准就汇报
- 最终确认里程碑本身要结束时后面没有可移交的地方，上表前四种去向都不适用：只有做完、范围变更（汇报）、或走中途交接
- 「交接」节只写接手要知道的上下文：是什么（过渡层 / 接口 / 约定 / 阻断项）、要做什么，不写出处；
  过渡层在代码里保留 `TODO` 并写明由哪个后续里程碑删，接收方的「交接」节有对应条目；过渡层若在产品文档里写了过渡态说明，条目里一并写明，删过渡层时同步改
- 移交出去的就写在接收方，本里程碑文档不留去向记录；已收尾的里程碑只在 `README.md` 清单里留一行，其它任何地方（交接节、产品文档、代码注释）都不提它

### 2. 固化

清账全部完成后，把本里程碑做完的东西里有长期价值的部分整理进产品文档与项目地图。

- 判据是**读代码本身得不到、但接手时必须知道**；纯内部实现细节、换实现而外部行为不变的改动不写
- 项目有自己的文档规范的按它的规定做
- 没有的自己整理，落笔前必须先完整读一遍要改的那几份文档；项目里没有可以落笔的产品文档与项目地图时，汇报，由用户定落点
- 主题里最后一份里程碑（有最终确认里程碑时指它；清账后若还有别的里程碑，就不是最后一份）收尾时，`README.md` 总览里有长期价值的内容（问题描述、方案概述、关键设计决策）一并按此判据整理，因为总览随后也要删掉
- **刻意留下的过渡层不进产品文档**，除非它造成了用户看得见的行为差异——那就如实写现状并标明是过渡态，
  但不写计划、不带里程碑编号

### 3. 删除

删除放在完成判据中现在能验证的都已验过、验不了的已按清账分流、固化已完成、且项目要求的审查（若有，由项目的文档规范规定）也通过之后；审查没过就改完再回到清账重新核对。

删掉本里程碑文档，`README.md` 总览里程碑清单里对应的条目改成一行 `NN 已收尾`（`NN` 为它的编号；若它是主题里最后一份，直接按下面处理，不必改清单）。
留着这一行，是为了让后来追加的里程碑不复用这个编号。
主题目录里的里程碑文档全部删掉后，`README.md` 总览随之删掉，再删主题目录；整个主题删完后，计划目录里不留任何记录。

只有 `README.md` 的主题：没有要移交出去的事时固化后直接删掉 `README.md` 和主题目录；清账后有要移交出去的事时先按「调整里程碑」转成多份，再按上面收尾 `01`。

开发计划文档目录因此空了的一并删掉。

### 无法继续时的中途交接

**唯一例外**：本里程碑还没做完，并且当前确实无法继续开发（例如缺外部条件、需要用户长期不在场的决定），
又必须结束任务、合并代码时，才可以不收尾（汇报之后会话要结束或代码要合并，就属于这种情况）。此时不删文档，在「目标 / 完成判据」之后加「中途交接」节，
让后来接手的人读到就能继续：

- 做到哪里了、哪些已勾、哪些没做
- 卡在哪里、要什么条件才能继续
- 已查明的情况与做过的设计取舍
- 没验证的部分
- 接手需要的其它上下文

已完成并随代码合入的部分，外部可见的行为仍按「固化」的判据整理进产品文档；已合入的过渡层仍标 `TODO`，并写进中途交接。
能继续做就不得以中途交接代替收尾。
