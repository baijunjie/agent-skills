# 编写开发计划文档

「汇报」指停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

下面只定原则和不能越过的边界，其余细节自行判断；**拿不准就汇报**。

## 范围

- 输入只限三类：本次讨论确定的方案、用户给出的完整需求描述、开发中发现并已向用户说明的追加功能（没说明过的先汇报，不写）。追加功能指当前任务中发现、可独立开发、不属于本次任务的功能。
- **简洁整理**输入，不添加输入以外的信息与推测的方案（开发者提示除外）；输入再长也不丢设计决策与理由，只删叙述。
- 输入里没定下来的设计点不补：不影响里程碑拆分与完成判据的，写进 `README.md` 总览末尾的「待定」一节；会让某个里程碑说不清目标或完成判据的，汇报，能确定的部分先写，受影响的里程碑先不写。
- 只写新主题，不往已有主题追加或调整里程碑。
- 只写计划，不实现：写完不动手，追加功能不进入本次改动；只落盘、不提交，告知用户写在哪个目录。

## 目录与拆分

开发计划文档目录默认 `docs/plans/`，项目已有自己的约定时按项目的。目录里只放尚未做完的内容。

- 一个主题一个目录 `YYYYMMDD-{开发简述}/`，简述用仓库既有文档的语言，日期是目录的创建日期。
- 一个里程碑必须能独立测试、独立合并：做完就能自行验证并合入，不等后续里程碑。验证不限于业务行为，迁移能执行、类型检查或单元测试通过都算。
- 粒度自行裁量，不为凑数硬拆，也不把彼此独立的两块塞进一份；按依赖排序，被依赖的在前。
- 只有一个里程碑时目录下只放 `README.md`，先写总览，再接里程碑内容。两个及以上时 `README.md` 只写总览，里程碑各写一份 `[编号]-[开发简述].md`（如 `01-订单状态存储与迁移.md`，开发简述的语言同目录名），编号即开发顺序。

## 写什么

**`README.md` 总览**：问题描述、方案概述、关键设计决策及其理由；拆成多个里程碑时加里程碑清单，每行一个里程碑（编号、开发简述），链到对应文档。

**里程碑**（只有一个时写在 `README.md` 总览之后）：

- 开头是目标与完成判据块：

  ```
  > 目标: <这一份要做成什么样>
  > 完成判据: <怎么算做完、怎么验证>
  ```

- **技术设计**：接口签名、数据结构、核心方法定义；**实现方案**：重构策略、方法分解、调用流程框架。都以输入为限，输入里没有的节省略。
- 技术设计与实现方案的每一项写成 `- [ ]` checkbox，粒度取可独立验证的最小一项；目标与完成判据块、开发者提示不写成 checkbox。勾选与文档清理不归本 skill。
- 末尾写**开发者提示**，这是唯一要查项目现状的部分，只到「项目里已有什么、该复用哪块」的粒度，无内容的项省略：
  - **可复用能力**：应直接复用的已有机制或模块（鉴权、缓存、错误处理、公共组件、工具函数等），写到能力与模块名，不写文件路径；不确定项目里有没有就不写
  - **开发要点**：要遵守的开发规范、与现有系统的集成方式、已有的全局功能（防止重复实现）
  - **参考文档**：相关技术文档、规范文档的路径

## 不写什么

- **实现代码**：不写函数体内部逻辑。示例只到方法间调用关系与执行流程（「校验通过后调用 A，再调用 B」），不写实现分支、算法与第三方库调用。输入里的业务规则与约束（如「已支付的订单不可取消」）是设计决策，用自然语言照写。
- **代码落点与编码步骤**：不列要改的文件、不指定代码路径、不写编码步骤，留给实现时调查。
- **重复**：文档之间不重复，依赖前面的就简洁引用。

## 与别处的关系

开发计划文档是临时文档：

- 不进项目文档的总索引，增删主题目录都不改总索引。
- 引用是单向的：主题目录之外任何地方（含代码注释、提交说明、PR 描述）都不引用它，同一主题目录内互相引用不限；别处需要其中的内容就直接写进去。
