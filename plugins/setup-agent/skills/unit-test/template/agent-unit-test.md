# 单元测试

## 本项目约定

本节由安装器按项目现状填写，重装时按项目现状重新核对，确定不了的沿用；monorepo 每个包在表里各填一行，表下两项各包不同时分别写明。

| 范围 | 框架 | 测试根目录 | 路径映射 | 共享辅助代码 | 运行全部 | 运行指定文件 | 按改动选测试 |
|---|---|---|---|---|---|---|---|
| <包的路径；不是 monorepo 写「整个项目」> | <框架名（项目现状；没有时由用户选定）> | <测试根目录（项目现状 → 语言或构建工具约定 → 默认 tests/unit/）；表下选 ③ 的写「无」> | <源路径模式> → <测试路径模式（项目已有测试的镜像方式 → 默认按相对项目（包）根的完整路径镜像，只有单一源码根时省掉这一级；表下选 ③ 的写与源文件同目录的模式）> | <共享辅助代码的位置（项目现状 → 默认测试根目录下的 helpers/；表下选 ③ 的默认源码根下的 test-helpers/）> | <运行全部测试的命令> | <运行指定测试文件的命令> | <框架自带的按改动选测试的命令；框架没有这种能力写「无」> |

- 已有与源码同目录的测试（按语言惯例放的除外）怎么处理：<安装时询问用户，三选一：① 旧测试留在原处，新测试进测试根目录（默认）② 旧测试随源文件被改逐个迁移到测试根目录 ③ 新旧测试都放源码同目录；项目里没有这类旧测试写「无」>
- 按语言惯例放测试的语言：<项目里按语言惯例放测试、不套测试根目录与镜像规则的语言及其惯例，如 Go（同目录 `_test.go`）、Rust（源文件内的 `#[cfg(test)]` 模块）；没有写「无」>

## 放在哪

- 测试一律写进测试根目录，镜像源码目录结构；**不要写进源码目录**，「本项目约定」另有规定的除外。
- 「本项目约定」里列为按语言惯例放测试的语言，照语言惯例放，本节其余规则不适用。
- 文件名与源文件同名，只加识别测试所需的标记（`.test`、`.spec`、`test_` 前缀、`Test` 后缀等）。
  框架能配成不加标记也不要去掉：同名同扩展名的两份文件会在模块解析、导入路径与编辑器里互相遮蔽。
- 一份源文件对应一份测试文件。源文件移动、改名、删除时，对应测试文件跟着移动、改名、删除。
- 多份测试共用的辅助代码与 fixture 放「本项目约定」里共享辅助代码的位置，不占镜像路径——否则会被当成某个源文件的测试。
- 与源码同目录的旧测试按「本项目约定」里选定的处理方式处理，选定方式之外不要顺手搬，要整批搬交给用户定：
  - ①：旧测试留在原处，对应源文件被改时就地更新，不在映射路径另建一份；新测试进测试根目录。
  - ②：改到哪个源文件，就把它的旧测试移进映射路径再更新；没改到的不动。
  - ③：新旧测试都放源码同目录，按「路径映射」列的同目录模式放；本节测试根目录与镜像的规则不适用。

## 找不到框架时

- 「本项目约定」的表还没填（只剩 `<…>`）：**停下来**，请用户运行 `setup-agent:unit-test` 安装器。
- 填的框架已不在项目依赖里：**停下来问用户**。给出与技术栈匹配的主流框架作为推荐并说明理由，
  用户同意后装成开发依赖，按「框架配置要求」配置，再更新「本项目约定」表里的「框架」和三个命令列，其余不动。

## 框架配置要求

框架是新装的还是项目已有的，配置都要满足：

- 收集「本项目约定」规定的测试位置；选 ①、② 时，留在源码同目录的旧测试照样收集，其它位置不收集。
  允许不同目录下出现同名测试文件——镜像结构必然会有。
- 测试文件纳入类型检查与 Lint，排除在构建产物与发布包之外。

## 收尾：补测试

1. 列出本次改动的源文件，含新增、改名、删除。
2. **派 `test-writer` 子代理补测试，不要自己写**：写代码的人按自己的实现写断言，测试只会给实现盖章。
   可测判据与写法都在它自己的定义里，你只交代改动清单、每处改动**应有的行为**，以及用户定下的取舍——
   它看不见你们的对话，预期没交代，它只能照实现反推。
   没有要补的测试时（只改了不可测的文件），不必派它，自己按运行范围跑。
3. 逐条处理它的报告：
   - 失败用例指向本次改动的缺陷 → 你改源码，不要让它改断言迁就实现。
   - 失败用例指向本次范围以外的既有缺陷 → 交给用户定：本次修，还是标成已知失败并注明原因。
   - 它认为测试本身写错 → 它改。
   - 预期说不清、它列为待定的 → 你按需求定；需求也定不了就交给用户定。
   - 报为「难测、需改源码结构」的 → 由你判断改不改，改动大就交给用户定。
4. 之后源码又改了（审查意见、修缺陷）就重跑受影响的测试；改出了新行为就再派它补。

没有子代理机制的工具：自己写，但先按需求写下每个用例的预期，再去读实现。

## 运行范围

默认只跑**受影响的测试**：本次新增或修改的测试文件，以及导入链（直接或间接）包含改动源文件的测试文件。

框架自带按改动或依赖选测试的能力时优先用它，但确认它选出的范围覆盖上面这些。

下列情况改跑**全量**：

- 改了测试配置、全局 setup、共享辅助代码
- 改了依赖版本、构建 / 编译配置、环境变量约定
- 改的文件被大范围依赖（公共工具、全局类型），依赖面数不清
- 依赖关系静态查不出：动态导入、按字符串注册、反射、依赖注入容器——查不出就等于没选
- 删除或改名了被别处引用的文件

拿不准就跑全量。在最终回复里写清跑了哪个范围、为什么。
