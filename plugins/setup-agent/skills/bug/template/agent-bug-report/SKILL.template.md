# 创建 bug 工单

「汇报」指停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

把本次描述的缺陷整理成一份工单，交接给修复者：说清哪里不对、怎么复现、怎么算修好。拿不准就汇报。

- **只写事实**：事实小节只写用户说的与你查证到的，推断只进「线索」并标明；缺的信息汇报。
- **建完单就结束，不修**；开发中途建单的，建完回到当前任务。
- 工单是一次性文档，**修完就删**：任何地方都不许引用它，也不进项目文档的总索引，建单、删单都不改它。

## 目录与命名

工单目录默认 `docs/bugs/`，项目已有自己的约定时按项目的。

- 一个 bug 一份 `YYYYMMDD-{简述}.md`，日期是工单创建日期，简述用仓库既有文档的语言。
- 按缺陷分单：同一缺陷的新表现追加进已有工单，表象相似而根因不同的分开建。

## 工单格式

开头一行标注严重程度：

```
> 严重程度: <致命 / 严重 / 一般 / 轻微 之一>
```

致命＝数据损坏或核心流程不可用；严重＝主要功能失效且无法绕过；一般＝功能受损但有绕法；轻微＝体验或文案问题。严重程度拿不准时直接取高的一档，不为此汇报。

正文按下列小节写，**不省略小节，也不用猜测填**，查不到的写「未知」。复现步骤、「预期与实际」里的预期、验收判据不许写「未知」：缺信息又补不到就不建单，汇报还缺什么。

- **现象**：出了什么错，一句话
- **复现步骤**：编号步骤，写到照着能复现的粒度；偶发的写明触发条件与出现概率。代码里已有被挂起的复现用例（注释掉、标成已知失败、靠垫片绕过等）时，写它的文件路径、用例名与恢复动作，不另写手工复现路径
- **预期与实际**：各一行；预期写明依据——产品文档里的哪一条，或用户当场确认的口径
- **环境**：版本、平台、配置、数据前提等影响复现的条件
- **影响范围**：谁受影响、有没有绕法
- **线索**：报错、日志、可疑位置，**每条标明是查证的还是推断的**
- **验收判据**：怎么算修好，写成能逐条验证的条件

## 不写什么

- 修复方案与实现代码：工单只界定问题
- 待办、进度、状态流转、修复过程：修复者不回来更新它
- 复述代码；过程与归属（谁报的、谁写的代码）
