# 修复 bug

「汇报」指停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

**bug 的定义是代码行为与产品文档（或用户确认的口径）不符。** 所以修复只改代码，
**不改产品文档**——文档是判定谁对谁错的基准，改了基准就等于把 bug 认定成了正确行为。

## 选定要修的 bug

**一次只处理一个工单**。只处理工单目录下已有的工单；用户直接描述、没有工单的缺陷不走这个 skill。

工单是目录下的单份文件 `YYYYMMDD-{简述}.md`，开头一行 `> 严重程度: <致命 / 严重 / 一般 / 轻微 之一>`，
正文有现象、复现步骤、预期与实际、环境、影响范围、线索、验收判据各节。下文依赖这些约定：
复现步骤用来复现，预期与实际里写明的依据用来确认预期行为，验收判据用来验证修复；线索是推断还是查证的，各条自带标注。

工单目录默认 `docs/bugs/`，项目已有自己的约定时按项目的。

用户指名了哪个工单就只处理哪个。没指名时，自己到工单目录里挑一个。

挑选判据：

- 严重程度高的优先
- 同级别里取复现步骤清楚、影响范围明确的

选定与挑不出时：

- 选定后先说明修的是哪个再开工
- 目录不存在或是空的：直接说没有待修的工单
- 候选之间取舍不清（严重程度相当、互相牵连）：汇报，列出候选让用户拍板，不要自己硬挑

## 动手之前

- 项目有自己的文档规范就先读它，文档目录与本项目额外的规则以它为准
- 否则从总索引（默认 `docs/README.md`）入手，按项目地图定位要动的模块，
  再读对应的产品文档确认现有行为
- **必须先复现**。复现不了就汇报——写明试了什么、缺什么条件，不许凭工单描述猜着改
- 复现后定位根因，**根因没定位到不许改代码**；查不出来就汇报卡在哪，不要试探性地改着看
- 对照产品文档、或工单里写明的依据确认预期行为。**两者都没有，或文档写的就是当前这个行为**，
  说明这不是实现偏差——汇报，问清要的是哪种行为，定下来之前不要改

## 产品设计要改时

根因出在产品设计本身、只改代码修不掉的，**汇报**：说明现状、为什么按现在的设计修不掉、
有哪些改法。**决定要改设计之后**，才动产品文档与对应的代码；决定不改设计就按文档的口径修代码。

- 改产品文档时，项目有自己的文档规范的按它的规定做；没有的落笔前必须先完整读一遍要改的那几份
- 设计变更超出本 bug 的范围时，那是需求变更，按项目的需求讨论与开发流程另行排期，
  本次只修与 bug 直接相关的部分

## 怎么修

- 改在根因上，不在表象上堵。确实只能临时绕过时，代码里标 `TODO` 写明绕过了什么、什么条件下能真正修掉
- 只改与本 bug 相关的部分；顺带发现的其它问题记下来，在最终回复里写清，不要顺手改
- 能加回归测试的加一条，覆盖这次的复现路径
- **不要回头改工单**：不勾进度、不写修复记录、不改状态。工单只负责把问题交接过来

## 验证与收尾

1. **验证**：按工单的验收判据逐条验；判据不足以逐条验证时，退回按复现步骤确认现象消失。
   **验证不过不算修完**，验不了的部分如实说明是哪部分、为什么
2. **删工单**：验证通过就把工单删掉，删空的目录一并删掉（含工单目录）。
   收尾的删除放在本次改动的验证与审查都通过之后；验证没通过、或修复没做完的不许删
