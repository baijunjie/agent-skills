# 修复 bug

「汇报」指停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

下面只定原则和不能越过的边界，其余细节自行判断；**拿不准就汇报**。

**bug 是代码行为与产品文档（或用户确认的口径）不符**，所以只改代码，**未经决定不改产品文档**：文档是判定对错的基准，改了它等于把 bug 认定成正确行为。

## 选定工单

工单目录默认 `docs/bugs/`，项目已有自己的约定时按项目的。

工单是目录下的单份文件 `YYYYMMDD-{简述}.md`，开头一行 `> 严重程度: <致命 / 严重 / 一般 / 轻微 之一>`，正文有现象、复现步骤、预期与实际、环境、影响范围、线索、验收判据各节：复现步骤用来复现，预期与实际里写明的依据用来确认预期行为，验收判据用来验证修复，线索各条自带查证 / 推断的标注。

- **一次只处理一个工单**，只处理目录下已有的；用户直接描述、没有工单的缺陷不走这个 skill，直接告知用户。
- 用户指名就只处理那个；没指名时自己挑：严重程度高的优先，已有未合入修复（如开着的 PR 里已删了它）的不挑；取舍不清就汇报并列出候选，不硬挑。
- 选定后先说明修的是哪个再开工。

## 动手之前

- 项目有自己的文档规范就先读，文档目录与额外规则以它为准；再读要动的模块对应的产品文档，确认现有行为。
- **必须先复现**，复现不了就汇报试了什么、缺什么条件，不凭工单描述猜着改。工单指到被挂起的复现用例（注释掉、标成已知失败、靠垫片绕过等）时，按工单写的恢复动作恢复它来复现，不另写：它断言的是期望行为，恢复后没有失败、或恢复不了，都汇报。
- **根因没定位到不许改产品代码**（恢复复现用例除外）；查不出就汇报卡在哪，不试探性地改着看。
- 对照产品文档或工单写明的依据确认预期行为；两者都没有、或文档写的就是当前行为，说明不是实现偏差，汇报问清要哪种行为，定下来前不改。

## 产品设计要改时

根因在产品设计本身、只改代码修不掉的，汇报：现状、为什么按现在的设计修不掉、有哪些改法。决定改设计后才动产品文档与对应代码；决定不改就按文档的口径修代码。

- 改产品文档按项目的文档规范。
- 设计变更超出本 bug 范围的是需求变更，按项目的需求流程另行排期，本次只修与 bug 直接相关的部分。

## 怎么修

- 改在根因上，不在表象上堵；只能临时绕过时，代码里标 `TODO` 写明绕过了什么、什么条件下能真正修掉。
- 只改与本 bug 相关的部分；顺带发现的问题在最终回复里写清，不顺手改。
- 这次的复现路径要有回归测试覆盖，测试怎么写、由谁写按项目的规定；交给别人写时把复现路径与验收判据作为预期交代清楚。用挂起用例复现的，恢复后的它就是回归测试。
- **不回头改工单**：不勾进度、不写修复记录、不改状态。
- 代码注释、提交说明、PR 描述都不引用工单文件：工单删后引用就失效，需要的信息直接写进去。

## 验证与收尾

1. **验证**：按工单的验收判据逐条验；有判据验不了的，至少按复现步骤确认现象消失，并如实说明是哪条、为什么验不了。**验证不过不算修完**。
2. **删工单**：只有全部验收判据逐条验证通过、且改在了根因上，才删工单；删单与修复放在同一份改动里提交、一起送审。有判据验不了、只做了临时绕过、验证没通过的都不删，汇报，由用户决定。
