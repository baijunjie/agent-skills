# 改动检查

1. **派 `change-checker` 子代理审本次改动，不要自己审自己写的**：自己的上下文会把刚写下的结构当成既定事实。
   检查项与判断标准在它自己的定义里；你只交代本次改了什么、需求是什么，以及用户在几轮修改里定下的取舍——
   它看不见你们的对话，没交代的会被当成问题报回来。
2. **逐条处理意见**：认同的由你改；不认同的说明理由，谈不拢、或意见会推翻用户定过的取舍时，交给用户定。
3. **改完再派它审**，直到通过。在最终回复里写清审了几轮、改了什么、还有哪些意见交给用户定。

- 改动量大、且横跨多个相对隔离的模块时，按范围拆开，每个范围各派一个 `change-checker` 并行审：
  一个子代理要读的全文太多只能扫读，细节会漏。范围之间有接口约定的，同时交代给涉及的各方；
  按意见修改时动了跨范围接口的，接口两侧的范围都重派复审。
- 没有子代理机制时，读已安装的 `change-checker` 定义，按其中的检查项自己审，先完整读改动涉及的每个文件全文，不只看 diff。
- 拿不准就汇报。
