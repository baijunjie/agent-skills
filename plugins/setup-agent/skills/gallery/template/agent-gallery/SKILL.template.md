# UI 状态 gallery

下面只定原则和不能越过的边界，其余细节自行判断。
拿不准就汇报：停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

gallery 是只在开发时用的场景集合：每个场景用 mock 数据摆出一个 UI 状态，不依赖真实后端，供人确认、供快速检查逐个遍历。

## 本项目约定

「本项目约定」只由安装器填写，运行时不改：要用到的项还是 `<…>`、填的命令或路径本身已失效（与本次改动无关；缺数据库、网络等环境条件的照常汇报，不算），或要跟着项目改的，停下，请用户重新运行装出本 skill 的安装器，并说明哪项要改、为什么。

本次改动弄得跑不起来的，按快速检查失败处理。有多个 UI 包时表里各填一行，表下各项各包不同时分别写明。

| 范围 | gallery 方案 | 场景放在哪 | 打开 gallery | 场景直达入口 | 快速检查（全量） | 快速检查（指定场景） |
|---|---|---|---|---|---|---|
| <UI 包的路径；只有一个写「整个项目」> | <方案名（项目已有 → 用户选定）；自建的写「自建」与入口文件> | <`gallery-writer` 维护的场景的位置与命名；已有场景另有用途、不归它增删的，写明哪些不归它管> | <启动命令，以及怎么避开别的工作副本、启动后从哪读出实际地址> | <打开一个场景的方式（URL、deep link、启动参数等），含主题、语言、尺寸等查看条件的写法> | <检查全部场景的命令> | <只检查指定场景的命令，用于只跑写进 gallery 或要预览的场景、修场景时反复验证；方案不支持写「无」> |

- UI 检查项：<快速检查对每个场景查什么，每项注明工具（第三方的名字或「自建」），如「渲染冒烟（就绪、无失败信号、无未捕获错误）：Playwright」；查看条件：源语言（写明是哪种）、默认主题；不进快速检查的检查连同命令列出，没有写「无」；安装时用户同意记明的缺项也写在这里>
- 多个场景共用的：<gallery 一侧改了会波及多个场景的目录与文件：多个场景共用的 mock、mock 层、gallery 机制（页面、检查脚本）各在哪>
- 应用预览：<从当前工作副本启动应用本身的命令、怎么避开别的工作副本、访问时需要的登录或配置；应用离不开真实后端、只能看 gallery 的写「只用 gallery」>
- 预览临时位置：<被版本库忽略、按工作副本隔离的目录：只为预览加的临时场景放在哪（gallery 要能加载它）、本次预览启动的服务与装上的构建记在哪>

## 改 gallery

- 正式场景、mock 与 gallery 机制的写入都派 `gallery-writer` 子代理，有子代理机制时你不写（没有的见本节末条）：新增或改变了 UI 状态、或改了 mock 依赖的接口契约与类型（UI 没变也算）都派它，场景怎么摆、扩哪个删哪个由它判断。
- 同一时刻只派一个，免得各加各的；它看不见你们的对话，每次交代全部待摆的 UI 状态、每个状态给人确认的是什么、契约改了什么、本次改动涉及的文件、用户定下的取舍，本工作副本在跑预览的连同地址。
- 它报上来的摆不出来、要改应用代码、定不了的取舍，影响小的你定，其余交给用户；约定要跟着改的按「本项目约定」处理。
- 本 skill 要派的子代理是和它一起装出的：有子代理机制却找不到所派子代理的定义，是安装不完整：停下，请用户重新运行装出本 skill 的安装器。没有子代理机制时，读装出的定义，照其中的规则自己做。

## 快速检查

- 快速检查守 gallery 不守应用（应用对错归类型检查与测试）：只在下面两处与用户要求时跑：
  - `gallery-writer` 写进 gallery 的，由它在报告前自己跑，范围见下一条；
  - 要给用户预览的场景，给入口前按 id 跑一遍（「快速检查（指定场景）」）；自 `gallery-writer` 跑过并通过后本次改动没再变的不重跑。
- 写进 gallery 的，快速检查只跑新增或改动的场景；改了被多个场景用到的东西时跑全量，波及哪些场景从改动的场景看不出来（约定的「多个场景共用的」只列已知部分，不以它为限）。
- 快速检查只在源语言（界面文案原本写成的语言）、默认主题下跑，场景里写死了语言或主题的按它自己的条件跑；语言相关的对错（译文齐全、格式正确、场景步骤在其它语言下找得到控件）归类型检查与测试，能写成脚本检查的不靠多渲染几种语言。其它语言、主题的遍历只在用户要求时跑，子代理以派它的人转达的为准。
- 跑到的场景都要通过。
- 只靠改对来通过：不为让检查通过而删场景，不跳过、不放宽检查，不改场景或 mock 去迁就应用的错误；场景有意改变后更新截图基线不算放宽。

- 失败按原因处理：

  | 失败原因 | 处理 |
  |---|---|
  | 本次改动弄坏了应用 | 改应用代码 |
  | 场景、mock 或 gallery 机制坏了或跟不上 | 派 `gallery-writer` 修或删 |
  | 命令跑得起来，个别场景在改动前的基线（如要合回的分支）上同样失败 | 不修、不挡交付，在最终回复里写明是改动前就有的失败、不算通过 |

  验证基线另起副本，按约定隔离、用完即清，不动本工作副本。改完的由改的一方按 id 重跑失败过的场景，直到通过。

- 检查通过只说明场景跑得起来，不说明它摆的是最新的 UI：外观与交互要确认的，实际打开看。
- 在最终回复里写清跑了全量、只跑了哪些场景，还是没跑，以及结果。

## 预览给用户确认

- 本次改动涉及 UI 时给用户预览：改得对不对要靠人眼判断的，等用户确认再交付；用户已给定结果、无需判断的（如调换顺序、改一处文案），只给入口不等。
- 从本次任务的分支或工作副本启动 gallery，需要时连同应用预览，按约定避开别的工作副本；不借用别处在跑的服务，那里看不到本分支的改动。
- 给每个要确认的界面一个直达入口：按约定的「场景直达入口」写、带上查看条件、用启动后的实际地址；给之前先自己打开，确认显示的是本分支的改动，自己打不开的（如装在真机上）照给，写明未能自行确认。
- 给不出可用的预览就明说卡在哪，不把 UI 改动当作可以确认的交出去。
- 等确认期间保持预览运行；按修改意见改完后刷新，入口变了重新给。
- 只为预览临时加的场景与 mock 放进「预览临时位置」，不混进正式场景；请用户确认时顺带问要不要留下，不等确认的也等这一问的回答；要留的当即交给 `gallery-writer` 摆成正式场景，由它自己检查。
- 你启动的服务与装上的构建记进「预览临时位置」，记下的要足以在收尾时认出是这一份。
- 不覆盖、不停、不卸不是本工作副本启动或装上的服务与构建，认不准就当不是、汇报：覆盖或卸载同一应用标识的构建会连同它的数据一起删掉。

## 收尾清理

- 分支交出去（合并、推送提 PR 等）、用户放弃这次改动、或工作副本要被删掉之前清理。
- 停掉、卸掉「预览临时位置」记着的服务与构建，删掉那里的临时场景、mock 与记录；那里之外的不碰。
- 核对不了的（如设备连不上）不动它，汇报留在哪、怎么认出；告知用户清掉了什么。
- 交付时预览还没清理的，在最终回复里列出还在跑的服务与留着的构建、怎么认出、怎么清，免得工作副本被直接删掉后再也认不出。
