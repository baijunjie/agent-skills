# 安装 UI 状态 gallery

装两样东西：`agent-gallery` skill（改 gallery 怎么派、快速检查、交付时的预览与收尾清理）与维护 gallery 的 `gallery-writer` 子代理；
并按项目的技术栈选定、搭起 gallery 机制本身与它的快速检查：项目已有就沿用，没有就推荐方案、由用户选定。
装出的 skill 靠 description 自动触发，本安装器不往指令文件写任何内容。

## 跨宿主约定

只执行当前宿主对应的分支。

模板资源先用 `$PLUGIN_ROOT`，为空再用 `$CLAUDE_PLUGIN_ROOT`；两者都为空时，先把 `SKILL_DIR`
设为**当前已加载的这个 `SKILL.md` 的绝对父目录**（不是项目工作目录），再按相对路径定位。
下面的变量定义要和后续命令放在同一次 shell 调用里，分开执行就每次重新定义：

```bash
if [ -n "${PLUGIN_ROOT:-}" ]; then
  SETUP_ROOT="$PLUGIN_ROOT"
elif [ -n "${CLAUDE_PLUGIN_ROOT:-}" ]; then
  SETUP_ROOT="$CLAUDE_PLUGIN_ROOT"
else
  SETUP_ROOT="${SKILL_DIR:?先将 SKILL_DIR 设为当前 SKILL.md 的绝对父目录}/../.."
fi
TEMPLATE_DIR="$SETUP_ROOT/skills/gallery/template"
RENDER_AGENT="$SETUP_ROOT/scripts/render-codex-agent.py"
```

Claude Code 中同名 skill 是**用户级优先于项目级**：写入前发现 Claude Code 用户级配置目录里也有本安装器要装的同名 skill 时，告知用户项目级这份在 Claude Code 中不会生效。
Claude Code 中同名子代理是**项目级 `.claude/agents/` 优先于用户级**；写入前发现另一层也有同名子代理时，告知用户两份都在、实际生效的是项目级那份。

## 写入前检查

首次安装与重装都要做；重装时先按「重装」比对，无变更就不做这一节。这一节做完之前只读取，不写入、不删除任何文件。

- **查软链**：将要写入、整份替换或删除的路径本身——包括本安装器独占的目录（如装出的 skill 目录）——都不能是软链（`[ -L <路径> ]`，路径末尾不带 `/`）。
  配置目录（`.claude/`、`.agents/`、`.codex/`、用户级配置目录）、其下多个安装器共用的 `skills/`、`agents/` 等目录，以及它们的上层目录是软链属正常布局，不查。
  要查的路径是软链，按「现状与预期不符时」处理。
- **查冲突**：本安装器装出的（安装步骤约定路径上做同一件事的 skill、子代理、脚本等，内容与模板差多少都算；装出的文件没有标记，约定路径上已有的同名文件一律按「装过」处理、不判断用途是否相同，这次即重装）不算冲突，其中的手改见「查手改」；其它安装器装出的各管各的，也不算。
  除此之外，要写入的位置已有与要写入内容重叠或冲突的东西就是冲突：已有管同一件事的规则或流程；已有的同一配置项取值与要写入的不同（定制值除外）。
  这几项各安装器都要查，本安装器另外要查的写在本节末尾。
- **查手改**：目标里已有本安装器装过的内容（这次是重装）时，按「重装」的「重装后留下什么」找出这次会被覆盖的手改，与模板比对；没有版本记录，分不清是旧版模板的差异还是手改，所以有差异的一律列出。
  安装步骤要删除的文件或目录里，凡不是这次模板原样装出的内容（用户自建的文件、改过的旧版文件）也一并列出。
  列出了的，写入任何文件之前就**停下来问用户**是否照常重装（软链、冲突要问的，与这一问合成一次问）。
  用户不照常重装的，不写入任何文件，结束并汇报；用户想留住手改的，本安装器的定制值不是「无」时，把它当冲突按下面的「融入」处理；是「无」时手改留不到下次重装，只能二选一：不重装，或覆盖后把手改另存成别的名字自行保留。
- **有冲突时**：**停下来问用户**是「完全覆盖」还是「融入现有内容」，用户选定前不写入任何文件；安装步骤里说的「已有的直接 / 整份覆盖」只指本安装器装出的，冲突的那部分照用户的选择处理。
  - 问时写清冲突的是哪个文件、哪一段，两个选项各会改成什么样：完全覆盖是去掉现有的那部分、装本安装器的；融入是按用户的指示把要装的内容并进现有内容。具体改法先说给用户，不擅自定。
  - 融入的结果优先落进由用户填写的定制值位置，其次是本安装器装出的其它内容，以后重装才界定得出。询问时按「重装」的「重装后留下什么」说明融入的内容以后重装会不会留下；留不下的直说融入只对这一次有效（下次重装会再问，而原有的冲突内容这次就已去掉），并建议选完全覆盖。

本安装器另外要查的冲突：第 8 步要补的依赖、配置项、运行入口（`package.json` scripts、Makefile target 等）与忽略规则，
项目里已有同名而取值或命令不同的。这一项连同第 8 步要写的文件的查软链、查冲突，在第 8 步写入前做，有问题照「写入前检查」处理。

## gallery 必须具备的

不论选哪种方案、第三方还是自建，搭成后都要具备下面几项。补缺项的办法与方案、检查工具一样，都优先成熟的第三方，满足不了才自建。
前两项是快速检查的前提，补不上就停止安装；其余几项对该平台确实不适用、补不上或用户不接受补法的，由用户定停止安装还是记明缺项后继续：

| 能力 | 用来做什么 |
|---|---|
| 能程序化列出全部场景 | 快速检查逐个遍历，核对覆盖 |
| 场景渲染就绪、失败（mock 答不上、渲染异常、未捕获错误）能被程序读出 | 快速检查据此判通过与否 |
| 每个场景有稳定的直达入口（URL、deep link、启动参数等），主题、语言、尺寸等查看条件能写进入口 | 预览时给用户直达入口，同一个入口复现同一个界面 |
| 不依赖真实后端；mock 与真实接口共用一份类型或契约 | 摆出真实环境难以到达的状态；契约变了 mock 报错 |
| 不进生产构建产物 | 不把 mock 与调试页面发布出去 |
| 能从任一工作副本单独启动，多个工作副本同时启动互不干扰 | 在开发分支上起预览，不影响别处在跑的服务 |

## 通用步骤

项目没有 UI、用户不建 gallery、用户连渲染冒烟也不要、或「gallery 必须具备的」前两项补不上时，停止安装，告知用户没装成，不写任何文件。
安装中为验证而启动的服务，验证完就停掉；会用真实账号或写真实数据的，先问用户。

1. **读旧约定**：已装过的（所在宿主安装节里 skill 的安装位置已有 `SKILL.md`；没有时看另一宿主的安装位置），先读出旧 skill 的「本项目约定」一节，
   作为后续各步的依据（见「重装」）；都没装过就跳过。
2. **确认项目有 UI**：找界面代码（Web 前端、移动端、桌面端界面）。monorepo 列出有 UI 的包，请用户确认这次装哪些，后面各步逐包处理。
3. **定 gallery 方案**：
   - 该包已有 gallery（第三方的组件工作台，或自建的场景页面）就沿用，同一个包里多套并存时问用户。
     已有场景另有用途（组件文档、设计评审、视觉回归基线等）的，问用户 `gallery-writer` 管哪部分，不归它管的写进约定。
   - 没有就推荐一个并说明理由，问用户：优先项目技术栈的主流方案，能直接渲染项目的真实组件、维护活跃。
   - 对照「gallery 必须具备的」逐项核对所选方案（含沿用的），缺项的补法列给用户确认。
   用户选定后只记下，搭建在第 8 步。
4. **定 UI 检查项**：渲染冒烟必有（每个场景就绪、没有失败信号、没有未捕获错误）。其余按项目实际有的查看条件（语言含从右到左、主题、宽度等）
   与质量要求（无障碍、外观稳定等）推荐，列给用户选。快速检查要能在每次交付时跑全量：会明显拖慢全量的检查（如截图比对）另设命令，不进快速检查。
5. **定预览方式**：应用本身能不能从当前工作副本单独启动、怎么避开别的工作副本、访问时要不要登录或配置；应用离不开真实后端、或拿不到预览所需条件（如登录凭据）的，只用 gallery 预览。
   再定预览临时位置：被版本库忽略、按工作副本隔离，只为预览加的临时场景放在 gallery 能加载到的地方，预览启动的服务与装上的构建记在那里；平台上两条做不到同时满足的，问用户。
6. **写入 skill**：执行所在宿主安装节里写入 skill 的命令，已有的整份覆盖。
7. **装子代理**：执行所在宿主安装节里装子代理的命令，已有的整份覆盖。
8. **搭建 gallery**：
   - 按第 3–5 步定下的装依赖、写配置，补齐缺项，搭好第 4 步的检查，补上打开 gallery、快速检查全量与指定场景的运行入口与临时位置的忽略规则；
     已有的 gallery 不重建，已有的场景不搬。本步写出的依赖、配置、运行入口与 gallery 机制装好后归项目所有：重装时只核对「gallery 必须具备的」与检查项是否仍满足，缺了才补，不按「查手改」列出、也不覆盖。
   - `gallery-writer` 管的场景一个都还没有的，派刚装好的 `gallery-writer` 为一个代表性界面写第一个场景：交代第 3–5 步定下的方案、检查项与本步补上的命令，
     并说明 skill 的「本项目约定」尚未填写、以这次交代的为准。当前会话还调不到新装的 `gallery-writer` 时，派一个通用子代理，
     把 `gallery-writer` 定义的正文连同交代一起给它；没有子代理机制就按该定义自己写。
   - 跑通全量快速检查，并从当前工作副本启动一次 gallery、打开一个场景的直达入口确认看得到。
     已有场景跑不过的，列出清单，由用户定留作遗留失败照样装完（记进约定的「UI 检查项」），还是停止安装；不改应用代码，也不放宽检查。
   - 为既有界面补齐场景不在安装里做：列出项目里还没有场景的主要界面，留到第 10 步告知用户，可作为单独任务派 `gallery-writer` 补。
   - 第 6 步之后中断安装的：重装先把第 1 步读到的旧约定原样填回；首次安装问用户是否删掉第 6、7 步装出的 skill 与子代理（推荐删，留着的空约定会在每次改 UI 时拦下来）。两种都逐项列出本步已写的改动，由用户定留不留。
9. **填本项目约定**：把装好的 skill「本项目约定」一节里每个 `<…>` 连同尖括号换成实际值，尖括号里的说明不保留；
   路径与命令写成代码体，「无」不用代码体。表里每个 UI 包一行，表下各项各包不同时分别写明；表下各项写第 4、5 步定下的结果。表里与表下的每条命令都要实际跑过。
10. **告知用户**：依赖清单、配置、运行入口与忽略规则的改动要连同装出的文件一起提交进版本库；第 8 步写了场景的，说明写的是哪个、快速检查是否通过，它也要提交；
    列出还没有场景的主要界面与记下的遗留失败。项目已装 `setup-agent:workflow` 的，重装它才会把 gallery 与 UI 预览写进交付前的步骤。其余见所在宿主安装节。

## 重装

不判断版本，只比内容。目标里已有本安装器装过的内容（这次是重装）时，先**只读地比对**：按安装步骤推出这次会写出的内容，与现状比——
本安装器独占的文件整份比，写进共享文件的（指令文件、`.gitignore`、`package.json` / `Makefile` 等本来就有、本安装器只占其中一部分的文件）
只比它写的那一段、那一行、那几个键，不比整份；定制值所列位置的差异不算，缺文件、缺那一段算有差异。
只有全部一致才算无变更，汇报「无需更新」后结束，不做「写入前检查」、不写任何文件；有差异、判不了、拿不准一律算有变更，不再判断、无条件重装：依次做下面四件事（有变更的重装仍要先过「写入前检查」，其中的软链、冲突、手改要问用户的照问）：

无变更早退只对「只来更新安装」的调用成立：用户这次还要改定制值里的内容，照安装步骤填写那些位置，不走早退——
那些位置的差异不参与比对，早退会把用户的诉求一起吞掉。比对只看装出的内容，机器上的状态不在其中：
产物要用户另外执行命令才在机器上生效的，早退时把那一步一并**告知用户**。

- **读定制值**：从旧文件里读出本安装器的定制值，作为这次填写这些位置的依据。定制值只限安装过程本来就要填写的位置，
  逐项写在本节末尾，写「无」的不读。各项这次沿用旧值还是按现状重定，见下面「重装后留下什么」。
- **清理**：只清理这一次要写的位置：整份替换的文件由安装步骤的写入命令直接覆盖，指令文件只替换本安装器的标记范围，模板里没有的文件与同一目录里的其它内容不碰；
  安装步骤另有清理约定、或用户对冲突做了选择的，照它处理。
- **装新的**：按安装步骤写入。
- **填回**：把读出的定制值填回新文件的对应位置。用户在「写入前检查」选了融入的，融入在填回、按现状重定之后做，结果以融入后的为准。

**重装后留下什么**：只有由用户填写的定制值原样保留；由现状推导的定制值（含手改过的）按这次的现状重写，现状确定不了才沿用旧值。
一旦写进产物就必须保持稳定的值（换了它会在机器、远端留下无人认领的残留）按由用户填写处理：产物里已经是字面值的原样保留，不按现状重算。本安装器装出的其余内容都按模板覆盖；安装步骤约定删除的文件或目录，连同其中的内容（包括用户自建的文件）一并删掉。
这一次选了融入的以融入结果为准，不改变以后重装的去留。这是重装去留的唯一定义，别处说保留、覆盖都以此为准。

**告知用户**时按「重装后留下什么」说明以后重装保留什么、覆盖什么；定制值为「无」的，说这个安装器没有可定制的位置。
不要修改已安装 plugin 内的模板。

本安装器的定制值：「本项目约定」一节整节，第 1 步读出，第 9 步填回。约定的表还只剩 `<…>`、或其中的命令跑不起来时，不算无变更，照常重装并重新确定这些位置。

- 表：按第 2、3、8 步从项目现状重新确定，确定不了的才沿用旧表；第 3 步用户定的方案与 `gallery-writer` 管的范围，方案还在用就沿用、不再问。
- 表下「UI 检查项」：用户选定的与记下的遗留失败原样沿用，不再问；工具已不在项目里的重新问。
- 表下「应用预览」「预览临时位置」：按第 5 步从项目现状重新确定，确定不了的沿用。

## 现状与预期不符时

下列情况，以及各节指明要按本节处理的情形，**停下来问用户**，不要照写、照删，也不要自行修复：

- 要写入、替换或删除的路径不是普通文件 / 目录（「写入前检查」里说明不查的配置目录等除外），最常见的是软链：写入会写穿到它指向的那份，删除或整份替换会让那份从此脱钩，都不报错。
  用户同意写进软链指向的那份时，只原地修改它，不先删后建，也不整份替换链接本身。
- 安装步骤里的命令报错退出、拒绝写入。
- 按安装步骤与项目现状确定不了要写什么、写到哪。
