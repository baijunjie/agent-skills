# 全局规则

与项目自己的指令文件冲突时，以项目的为准。

## 分派子代理

**判据：默认自己做。只有长任务（执行开发计划、跨多个模块的大批量改动或排查）才把其中要吃掉大量上下文的整块工作派给子代理，自己只收结论：小任务交代给子代理的成本比自己做完还高。** 交付前的自检（补测试、改动检查、文档更新等）及其整改按工作流、对应的 skill 与下面的规则派，不受这条限制。

- 你是子代理时，只做派给你的任务，亲自做完交回：不再派子代理，不推送、不合并、不发 PR，也不走指令文件工作流里交付前的自检；确认改动可用只跑直接覆盖你这次改动的测试，不跑整套测试、Lint、类型检查与构建。派给你的任务本身是自检中的一项（如补测试、审查）的，按派发时的交代与你自己的定义做。开工前只读项目上下文，不 fetch、不对齐分支。自检由派你来的一方在全部任务交回后统一做。子代理各自再派、各自自检时彼此没有协调，会同时跑满本机资源。
  子代理指被另一个代理派来做具体任务、做完向它交回的代理，不论用什么方式派出（子代理机制、另开的会话等）、是否在自己的分支或工作副本上做：任务说明、你的定义或系统提示写明你向另一个代理交回的，你就是子代理；交付只由直接向用户负责的代理做；用户直接要子代理推送、合并或发 PR 的，它就转为交付方，先按工作流自检再交付。派子代理时在任务说明里写明「你是子代理，做完交回」：有的子代理只能从这里认出身份。
- 一次只交代一件事，说清完成判据，背景给全（没写进去的前提它一概不知道），让它只报结论、不复述过程。
- 不要让多个子代理同时改同一处，也不要并发派几个做同一件事：前者互相覆盖，后者互相抢资源、谁也不收敛。
- 要它的结果才能往下走的，派发时显式要求阻塞等它，不要假定派出去就会等，也不要自己定时等或反复查状态：后台派出的子任务，报告回不到你手上，而你的回合一停就交回了。
- 手上没有结果就不交回：报告里用「已派出，在等它」代替结论的，算没做完。
- 自检意见、检查失败要改的代码是子代理写的，交回它去改：能续接原来那个就续接，不能就新派一个，附上意见与当初的任务说明；这种情况下，自检 skill 里写的「你改」「你改源码」指由你安排改。你只判断每条改不改（不认同的说明理由）、哪些交给用户定；判断时需要看代码就只看相关几处，不要自己动手改：写代码的上下文会回到你身上，派子代理就白派了。
- 有专职子代理负责的交给它；没有的按任务难度从下表选，不要一律用最强的。

| agent | 用途 |
|---|---|
| `mechanical` | 长任务里的批量搜索、批量替换、格式化、简单文本与数据处理 |
| `implement` | 编写具体逻辑代码、实现已定方案、目标明确的重构与修 Bug。默认的性价比选择 |
| `investigate` | 跨模块疑难排查、根因定位、大范围重构 |
| `architect` | 架构设计、跨模块改造方案、技术选型。只在确实需要最强推理能力时用 |
