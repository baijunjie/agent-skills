# 改动检查

你是子代理时不走本 skill：做完交回，由派你来的一方安排。
子代理指被派来做一件事、把结论或改动交回派发者、由派发者负责并进分支的代理；交付物是一个分支的（不论最后由谁推送或合并）不算子代理。

## 本项目约定

「本项目约定」只由安装器填写，运行时不改：要用到的项还是 `<…>`、填的命令或路径本身已失效（与本次改动无关；缺数据库、网络等环境条件的照常汇报，不算），或要跟着项目改的，停下，请用户重新运行装出本 skill 的安装器，并说明哪项要改、为什么。

- 编码规范：<项目编码规范文档的路径，多份逐行列出，并注明界面规范在哪份文档的哪一节（分散在各节的写明分散）；项目没有规范文档的写「无」；用户级安装写「未指定」>
- 界面代码：<界面代码（Web 前端、移动端、桌面端界面）所在的路径，monorepo 逐包列出；项目没有界面的写「无」；用户级安装写「未指定」>

「界面代码」写「未指定」时，由你按本次改动的内容判断。本次改动新增了不在所列路径里的界面代码时不中断审查：照常派，没装 `ui-checker` 的不派它、由 `change-checker` 兼审界面，汇报时请用户重新运行装出本 skill 的安装器。「界面代码」为「无」时没有 `ui-checker` 是预期的，不算安装不完整。

## 审查

1. **派审查子代理审本次改动，不要自己审自己写的**：自己的上下文会把刚写下的结构当成既定事实。
   `change-checker` 审全部代码，每轮都派；本次改动碰到界面代码（含样式文件与文案资源）时同时并行派 `ui-checker` 另审界面层面。
   交代本次改了什么（拆范围时是该范围的）、需求是什么、这次有没有同时派 `ui-checker`，以及用户在几轮修改里定下的取舍——
   它们看不见你们的对话，没交代的会被当成问题报回来。
2. **逐条处理意见**：认同的由你改；认为该改的是规范而不是代码的，连同规范建议交给用户定，定下前这条意见不算通过，用户不同意改规范的按原意见改代码；不认同的说明理由，谈不拢、或意见会推翻用户定过的取舍时，交给用户定，其余意见照常整改，不等它。
3. **改完再审**，直到通过：整改动过的范围按第 1 步重派（拆范围时只派整改碰到的范围）；复审时交代上一轮各条意见与规范建议怎么处理的（改了哪些、哪些不改及理由、哪些交给了用户或已由用户定下），免得同一条被再报回来。
   其余都通过后还有交给用户定的意见，就汇报；按用户的决定改完后同样复审，通过才算通过。在最终回复里写清审了几轮、改了什么、用户定了什么。

- 改动量大、且横跨多个相对隔离的模块时，按范围拆开，每个范围按上面的规则派所需的子代理，并行审：
  一个子代理要读的全文太多只能扫读，细节会漏。范围之间有接口约定的，同时交代给涉及的各方，接口两侧都算负责它的范围。
- 本 skill 要派的子代理是和它一起装出的：有子代理机制却找不到所派子代理的定义，是安装不完整：停下，请用户重新运行装出本 skill 的安装器。没有子代理机制时，读装出的定义，照其中的规则自己做。

## 规范建议

子代理报告里另列的「规范建议」（规范缺了、过时了、与用户定下的取舍冲突）不算审查未通过，也不阻塞本次交付；规范是整个项目的长期约定，只按用户的决定改。

- 合并各子代理、各轮的建议并去掉重复，汇报时逐条写清改规范的哪一处、改成什么、依据是什么，交给用户定。
- 用户同意的，改建议所指的规范文档：只改同意的那几条，与已有条目矛盾的一并理顺，不顺手改别的；改出来的同样算本次改动，按「审查」复审。
- 建议所指的是安装器装出的内容（装出的 skill、子代理，指令文件里安装器写入的段落）的，不改，把要改的内容列给用户：重装会把它覆盖回去。
- 「编码规范」写「无」或「未指定」的，照样把建议交给用户，并告知用户：要把规范固定下来，在项目里以项目级运行装出本 skill 的安装器建立或登记规范文档。

拿不准就汇报：停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。
