# 安装项目级回退闸门

装两样东西，都只装进当前项目：随仓库提交的闸门脚本与常驻守护分支列表（`.githooks/` 下），以及各 clone 自己的 hook 入口。
受守护的分支（常驻守护分支，加上各分支 `branch.<分支>.targetBranch` 记下的目标分支）移动时，本地 merge / commit / reset
与 push 都会被检查，拒绝改写已发布的历史、以及撤销该分支已有改动的更新；记了 `targetBranch` 的分支自己被推送时，
按内容核对它相对目标分支远端尖端有没有撤销已有改动。

目标分支与切出点（`branch.<分支>.forkPoint`）由 `bjj-setup-git:pr`、`bjj-setup-git:worktree` 装出的流程脚本记录，本安装器只读不写；
没装那两个的仓库只守常驻守护分支，靠切出点的那条判据（撤销纯新增的提交、删掉只追加过的文件）不生效。
本安装器不写指令文件、不装 skill：被拦下时怎么复原、怎么处理写在闸门的拒绝信息里。当前目录不是 git 仓库时汇报并停下。

## 跨宿主约定

两个宿主装出的内容相同，下面的命令与宿主无关。

模板资源先用 `$PLUGIN_ROOT`，为空再用 `$CLAUDE_PLUGIN_ROOT`；两者都为空时，先把 `SKILL_DIR`
设为**当前已加载的这个 `SKILL.md` 的绝对父目录**（不是项目工作目录），再按相对路径定位。
下面的变量定义要和后续命令放在同一次 shell 调用里，分开执行就每次重新定义：

```bash
if [ -n "${PLUGIN_ROOT:-}" ]; then
  SETUP_ROOT="$PLUGIN_ROOT"
elif [ -n "${CLAUDE_PLUGIN_ROOT:-}" ]; then
  SETUP_ROOT="$CLAUDE_PLUGIN_ROOT"
else
  SETUP_ROOT="${SKILL_DIR:?先将 SKILL_DIR 设为当前 SKILL.md 的绝对父目录}/../.."
fi
TEMPLATE_DIR="$SETUP_ROOT/skills/revert-gate/template/githooks"
```

## 写入前检查

首次安装与重装都要做；重装时先按「重装」比对，无变更就不做这一节。这一节做完之前只读取，不写入、不删除任何文件。

- **查软链**：将要写入、整份替换或删除的路径本身——包括本安装器独占的目录（如装出的 skill 目录）——都不能是软链（`[ -L <路径> ]`，路径末尾不带 `/`）。
  配置目录（`.claude/`、`.agents/`、`.codex/`、用户级配置目录）、其下多个安装器共用的 `skills/`、`agents/` 等目录，以及它们的上层目录是软链属正常布局，不查。
  要查的路径是软链，按「现状与预期不符时」处理。
- **查冲突**：本安装器装出的（安装步骤约定路径上做同一件事的 skill、子代理、脚本等，内容与模板差多少都算；装出的文件没有标记，约定路径上已有的同名文件一律按「装过」处理、不判断用途是否相同，这次即重装）不算冲突，其中的手改见「查手改」；其它安装器装出的各管各的，也不算。
  除此之外，要写入的位置已有与要写入内容重叠或冲突的东西就是冲突：已有管同一件事的规则或流程；已有的同一配置项取值与要写入的不同（定制值除外）。
  这几项各安装器都要查，本安装器另外要查的写在本节末尾。
- **查手改**：目标里已有本安装器装过的内容（这次是重装）时，按「重装」的「重装后留下什么」找出这次会被覆盖的手改，与按安装步骤推出、已填回定制值的内容比对；没有版本记录，分不清是旧版模板的差异还是手改，所以有差异的一律列出。
  安装步骤要删除的文件或目录里，凡不是这次模板原样装出的内容（用户自建的文件、改过的旧版文件）也一并列出；由现状推导的定制值，这次推导出的与旧值不同的也一并列出，逐项问沿用旧值还是用新值。
  列出了的，写入任何文件之前就**停下来问用户**是否照常重装（软链、冲突要问的，与这一问合成一次问）。
  用户不照常重装的，不写入任何文件，结束并汇报；用户想留住手改的，有含义相符的定制值位置可落时，把它当冲突按下面的「融入」处理；没有（含定制值为「无」）时手改留不到下次重装，只能二选一：不重装，或覆盖后把手改另存成别的名字自行保留。
- **有冲突时**：**停下来问用户**是「完全覆盖」还是「融入现有内容」，用户选定前不写入任何文件；安装步骤里说的「已有的直接 / 整份覆盖」只指本安装器装出的，冲突的那部分照用户的选择处理。
  - 问时写清冲突的是哪个文件、哪一段，两个选项各会改成什么样：完全覆盖是去掉现有的那部分、装本安装器的；融入是按用户的指示把要装的内容并进现有内容。具体改法先说给用户，不擅自定。
  - 融入的结果优先落进含义相符的定制值位置，其次是本安装器装出的其它内容，以后重装才界定得出。询问时按「重装」的「重装后留下什么」说明融入的内容以后重装会不会留下；留不下的直说融入只对这一次有效（下次重装会再问，而原有的冲突内容这次就已去掉），并建议选完全覆盖。

本安装器另外要查的冲突：

- hook 入口：配置文件里设了 `core.hooksPath`（以 `env -u GIT_CONFIG_COUNT -u GIT_CONFIG_PARAMETERS git config core.hooksPath`
  有输出为准；`-c` 或环境变量 `GIT_CONFIG_COUNT` 临时给的不算），或 `$(git rev-parse --git-common-dir)/hooks/` 下已有不含
  `# revert-gate hook entry` 一行的 `reference-transaction` / `pre-push`。两个 hook 逐个判定。完全覆盖会让原来那套 hook 失效，询问时说明；
  `core.hooksPath` 不在本仓库自己的配置里（`git config --show-scope core.hooksPath` 不是 `local`）的，不提供完全覆盖，只能融入：
  改全局或系统配置会影响本机所有仓库；询问时说明融入的调用会写进本机所有仓库共用的 hook 文件。入口里已调用 `.githooks/hook.sh` 的，按第 5 步「融入」那一行处理，不算冲突；
  融入写在对方体系自己的文件里，本安装器重装时不碰，以后一直保留，不适用「写入前检查」里「融入只对这一次有效」的说法。
- `.githooks/` 下的 `revert-gate.py`、`hook.sh`、`install.sh`、`branches` 是本安装器装出的，已有的按装过处理；
  `.githooks/` 里别的文件（如 `bjj-setup-git:pr`、`bjj-setup-git:worktree` 装的 `flow-*.sh`）不碰。

## 项目级安装

1. **确认环境**：闸门脚本要 `python3`，本地 merge / commit / reset 那一层（reference-transaction）另要 git 2.28+。
   没有 `python3` 的，问用户是装 Python 还是不装闸门：不装闸门的不写任何文件，结束；装好 Python 的继续。
   git 低于 2.28 的照装，只有 push 那一层生效，告知用户。
2. **确认主分支名**：主分支取远端的默认分支（`git symbolic-ref --short refs/remotes/origin/HEAD` 去掉远端前缀，或远端仓库设置里的默认分支），
   定不下来的：已装过的沿用旧文件第一行，不问；首次安装问用户；不按当前检出的分支推断。第 4 步把它写成常驻守护分支。已装过的，从 `.githooks/branches`
   读出上次的常驻守护分支（忽略空行与 `#` 开头的行）：旧文件第一行就是上次的主分支，与这次定出的不一致时，
   按「重装」里由现状推导的定制值处理；其余行是用户加的，第 4 步一并写回。
3. **复制闸门脚本**：模板里只有 `revert-gate.py`、`hook.sh`、`install.sh` 三个文件，不含 `branches`。保留可执行位，已有的同名文件直接覆盖，`.githooks/` 里别的文件不动：

   ```bash
   top=$(git rev-parse --show-toplevel) && cd "$top" || exit 1
   : "${TEMPLATE_DIR:?}"
   mkdir -p .githooks && cp -p "$TEMPLATE_DIR/"* .githooks/
   ```
4. **写常驻守护分支列表**：整个重写随仓库提交的 `.githooks/branches`，每行一个分支，主分支放第一行，
   其后是第 2 步沿用的其它分支。文件开头写一行 `#` 注释，说明这是回退闸门的常驻守护分支、主分支在第一行，
   `sh .githooks/install.sh` 不带参数时从这里读。各分支记录的目标分支另外自动受守护，不写进来。
5. **接 hook 入口**：按「写入前检查」里 hook 入口的冲突结果，三种接法选一：

   | 情况 | 做法 |
   |---|---|
   | 没有冲突 | 直接装：执行下面的命令（可重复执行），它按 `.githooks/branches` 写好本 clone 的常驻守护分支配置 |
   | 用户选完全覆盖 | 按询问时说给用户的改法撤掉原来那套入口（如 `git config --unset core.hooksPath`、移走原 hook 文件），再按直接装执行 |
   | 用户选融入，或入口里已调用 `.githooks/hook.sh` | 在那套体系（如 husky）的 `reference-transaction` 与 `pre-push` 里各调用一次 `[ ! -f .githooks/hook.sh ] || sh .githooks/hook.sh <所在 hook 的名字> "$@"`（原样转发 stdin；还没有 `.githooks/` 的分支或 worktree 里跳过，不然 reference-transaction 失败会让所有 ref 更新失败，代价是在那些地方两层检查都不生效，询问时说明），怎么接由用户定；已调用的不重复接。然后执行 `sh .githooks/install.sh --branches-only`：只按 `.githooks/branches` 写本 clone 的常驻守护分支配置，不装 hook（不带这个参数会因同一原因报错退出） |

   直接装的命令：

   ```bash
   top=$(git rev-parse --show-toplevel) && cd "$top" || exit 1
   sh .githooks/install.sh
   ```

   有些体系（如 husky v9）不生成 `reference-transaction`，接不上时只剩 pre-push 一层，要告知用户。
   不带参数的 `install.sh` 报 `core.hooksPath` 已设置或同名 hook 已存在，是事先漏查了这项冲突，先按「写入前检查」问用户。
6. **告知用户**：
   - `.githooks/`（含 `branches`）要提交进版本库才随仓库生效；闸门读的是受守护分支上已提交的那份脚本
     （常驻守护分支优先），提交并合进主分支之后才开始检查。
   - hook 与常驻守护分支配置在各 clone 的 `.git/` 里，不随仓库生效：其它 clone 各自执行一次 `sh .githooks/install.sh`
     （hook 由 husky 等体系接管的改为按第 5 步接进那套体系，再执行 `sh .githooks/install.sh --branches-only`），
     同一 clone 的所有 worktree 共用；`bjj-setup-git:pr`、`bjj-setup-git:worktree` 的流程脚本记录目标分支时，发现本 clone 没装会提示。
     改常驻守护分支时改 `.githooks/branches` 并提交，各 clone 重新执行一次同样的命令才生效。
   - 被拦下时的复原与处理写在拒绝信息里；确属有意撤销的，用 `git revert`，或在撤销它的提交信息里为每个被撤销的提交加一行 `Reverts: <sha>`。
     `git push --no-verify` 跳过 pre-push 一层，`REVERT_GATE_SKIP=1` 整体跳过，只供人确认过的场合使用。
   - git 每次 ref 更新的每个阶段都会启动一次 hook：rebase 一长串提交会慢上几秒，一次 fetch 几千个新 tag 或分支可能多出一分钟以上。

## 重装

不判断版本，只比内容。目标里已有本安装器装过的内容（这次是重装）时，先**只读地比对**：按安装步骤推出这次会写出的内容，与现状比——
本安装器独占的文件整份比，写进共享文件的（指令文件、`.gitignore`、`package.json` / `Makefile` 等本来就有、本安装器只占其中一部分的文件）
只比它写的那一段、那一行、那几个键，不比整份；定制值所列位置的差异不算，缺文件、缺那一段算有差异。
只有全部一致才算无变更，汇报「无需更新」后结束，不做「写入前检查」、不写任何文件；有差异、判不了、拿不准一律算有变更，不再判断、无条件重装：依次做下面四件事（有变更的重装仍要先过「写入前检查」，其中的软链、冲突、手改要问用户的照问）：

无变更早退只对「只来更新安装」的调用成立：用户这次还要改定制值里的内容，照安装步骤填写那些位置，不走早退——
那些位置的差异不参与比对，早退会把用户的诉求一起吞掉。比对只看装出的内容，机器上的状态不在其中：
产物要用户另外执行命令才在机器上生效的，早退时把那一步一并**告知用户**。

- **读定制值**：从旧文件里读出本安装器的定制值，作为这次填写这些位置的依据。定制值只限安装过程本来就要填写的位置，
  逐项写在本节末尾，写「无」的不读。各项这次沿用旧值还是按现状重定，见下面「重装后留下什么」。
- **清理**：只清理这一次要写的位置：整份替换的文件由安装步骤的写入命令直接覆盖，指令文件只替换本安装器的标记范围，模板里没有的文件与同一目录里的其它内容不碰；
  安装步骤另有清理约定、或用户对冲突做了选择的，照它处理。
- **装新的**：按安装步骤写入。
- **填回**：把读出的定制值填回新文件的对应位置。用户在「写入前检查」选了融入的，融入在填回、按现状重定之后做，结果以融入后的为准。

**重装后留下什么**：定制值以外的都与模板一致；定制值保留旧值，其中由现状推导的按这次的现状重新推导，与旧值不同的算冲突，按「写入前检查」的「查手改」问用户沿用旧值还是用新值，现状确定不了的沿用旧值。
一旦写进产物就必须保持稳定的值（换了它会在机器、远端留下无人认领的残留）按由用户填写处理：产物里已经是字面值的原样保留，不按现状重算。本安装器装出的其余内容都按模板覆盖；安装步骤约定删除的文件或目录，连同其中的内容（包括用户自建的文件）一并删掉。
这一次选了融入的以融入结果为准，不改变以后重装的去留。这是重装去留的唯一定义，别处说保留、覆盖都以此为准。

**告知用户**时按「重装后留下什么」说明以后重装保留什么、覆盖什么；定制值为「无」的，说这个安装器没有可定制的位置。
不要修改已安装 plugin 内的模板。

本安装器的定制值：

- 常驻守护分支（`.githooks/branches`）：第一行的主分支由项目现状推导，比对时与第 2 步这次定出的不一致算有变更；
  其余行是用户加的，比对时不算。第 2 步读出，主分支重新确认，其余沿用旧值，第 4、5 步写回。

## 现状与预期不符时

下列情况，以及各节指明要按本节处理的情形，**停下来问用户**，不要照写、照删，也不要自行修复：

- 要写入、替换或删除的路径不是普通文件 / 目录（「写入前检查」里说明不查的配置目录等除外），最常见的是软链：写入会写穿到它指向的那份，删除或整份替换会让那份从此脱钩，都不报错。
  用户同意写进软链指向的那份时，只原地修改它，不先删后建，也不整份替换链接本身。
- 安装步骤里的命令报错退出、拒绝写入。
- 按安装步骤与项目现状确定不了要写什么、写到哪。
