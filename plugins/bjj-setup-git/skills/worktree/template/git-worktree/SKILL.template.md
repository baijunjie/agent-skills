# worktree 分支的操作

下文单说「分支」时指本次在 worktree 里开发的分支，「目标分支」指它合回去的分支。
拿不准就汇报：停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

分支合并回哪、从哪切出，从它自己的 git config 读（怎么记见「## 创建」）：目标分支（`targetBranch`）读不出来、切出点（`forkPoint`，分支最初从目标分支切出的位置）缺失，
或指定的 worktree 没有分支（临时的 `--detach` worktree），都汇报，不要按分支名猜或自己补。
对齐远程（含其中的 rebase 与验证）、合并、reset 与推送目标分支在仓库原目录（下称主工作副本，`git worktree list` 的第一项）里做：做之前它要检出目标分支（不在就切回），有未提交的改动或切不回去就汇报。压平、分支的 rebase 与合并前的验证在分支自己的 worktree 里做。
没指定是哪个分支时，取当前 worktree 的分支；在主工作副本里调用的，只有一个 worktree 分支（记着 `targetBranch` 的分支）就是它，否则问用户。

## 流程脚本

机械操作由仓库 `.githooks/` 下的 `flow-*.sh` 完成。一律执行主工作副本里的那份，从目标分支新切出的 worktree 里可能还没有这些文件；下文写的 `flow-<名>.sh <参数>` 都指：

```bash
sh "$(git worktree list --porcelain | sed -n '1s/^worktree //p')/.githooks/flow-<名>.sh" <参数>
```

- 退出码 0：做完了。输出里以「注意：」起头的提示告知用户。
- 退出码 1：脚本停下了。下文点名了的原因按下文处理，其余汇报。
- 退出码 2，或脚本不存在：汇报。

下文为某种原因写明了做法的按下文做；其余提示只转述给用户，不自行照做。不要绕过脚本手工完成它停下的操作。

## 创建

- 目标分支是创建 worktree 时主工作副本检出的分支，不一定是主分支。主工作副本是 detached HEAD、没有检出分支时汇报。
- 分支名按变更类型取 `feat/`、`fix/`、`refactor/`、`docs/` 前缀；worktree 放在仓库内的 `.worktrees/<分支名去掉前缀>/`（`feat/login-retry` 放在 `.worktrees/login-retry/`）。
- 只为验证而临时注入代码时，可另开不建分支的临时 worktree（`git worktree add --detach`），里面的改动不提交、验完即删。
- 按下面的顺序创建：
  1. 按「## 对齐远程的目标分支」把目标分支对齐，对齐不了就汇报，不要在没对齐的位置上切出。
  2. 从对齐后的目标分支建分支和 worktree。
  3. 记下目标分支和切出点：`flow-record.sh <分支> <目标分支> <目标分支>`（第三个参数是切出点，刚建好时就是目标分支）。

## 对齐远程的目标分支

- 先定上游：目标分支设了上游就用 `<目标分支>@{u}`；没设的，只有一个远端有同名分支就用 `<远端>/<目标分支>` 代替（不用设上游），多个远端都有时问用户用哪个，再 `git branch -u <远端>/<目标分支>` 设好；都没有就不用对齐。没设上游时，下文的 `<目标分支>@{u}` 换成 `<远端>/<目标分支>`。
- 在主工作副本里只 fetch 这一个上游分支（`git fetch <远端> <上游分支名>`），再按目标分支与它的关系处理：
  - 一致，或只领先（只有未推送的提交）：不用处理。
  - 落后（本地没有未推送的提交）：`git merge --ff-only <目标分支>@{u}` 快进。
  - 分叉（本地有未推送的提交、远程也有新提交）：先 `git rev-parse <目标分支>` 记下旧位置，再 `git rebase <目标分支>@{u}`，解冲突同「## 压平与 rebase」。
    - rebase 后按「## 合并」的范围验证本地那些未推送的提交（改动按它们相对 `<目标分支>@{u}` 算），通过才算对齐；不通过汇报目标分支已改写、还没搬分支，连同记下的旧位置一起报出，不要继续。
    - 再执行 `flow-restack.sh <目标分支> <旧位置>`，把从改写前那批提交上切出的分支搬到新位置。它搬的可能是别的任务的分支：搬完告知用户搬了哪些。
      报冲突的，冲突在本次要处理的分支以外的先问用户；要解的到它说的 worktree 里解（解法同「## 压平与 rebase」），`git rebase --continue` 后重跑；报分支已推送过的，逐个问用户它是不是独用，是的加 `--allow-pushed <分支>` 重跑，否则汇报。
- 项目走 PR 合并的，对齐后目标分支仍领先远端（有未推送的提交）时先汇报：之后从它切出、或 rebase 到它上面的分支会把这些提交带进 PR。

## 压平与 rebase

- 合并前压平：目标分支上的每个提交都要能独立说明、独立回滚，之后的补改（rebase 后、验证不通过后）都并入所属的提交。分支只做了一件事就压成一个提交；确实包含多个互不依赖的变更才保留多个，要把同一个文件的改动拆进不同提交的，不拆。提交信息描述最终状态，不复述过程（不写「修复上一个提交」「按反馈调整」），语言跟随仓库历史；原提交里的撤销声明（`Reverts:` 行，或 `git revert` 生成的 `This reverts commit <sha>`）必须带进压出来的提交。
- 压平与 rebase 前，分支的 worktree 必须干净（以 `git status --porcelain` 为空为准，含未跟踪文件），不干净就汇报，不要替用户提交、stash 或丢弃。
- 动手前先记下 `git rev-parse HEAD`（下称记下的提交），要退回压平前时用它。
- 压成一个：提交信息写进 worktree 之外的临时文件，执行 `flow-squash.sh <目标分支> <文件>`；它报新提交信息缺了原提交里的撤销声明的，补上后重跑。
- 保留多个：在分叉点（现算的 `git merge-base HEAD <目标分支>`，不是记着的切出点）上自己拆；拆完执行 `flow-squash.sh --check <目标分支> <记下的提交>`，不通过就按它给的命令退回重做。
- 压平后再 `git rebase <目标分支>`，这样冲突只用解一次。解冲突要把双方的改动合起来，不要一律取自己这一侧；拿不准怎么合就问用户。
- 已推送过的分支：自己独用的（远端上没有别人的提交；拿不准就问用户），压平、rebase 后用 `flow-push.sh <分支上游所在的远端> <分支> <上游分支名>` 推送（读不出上游就问用户推往哪），报要改写已推送的历史的，向用户确认后加 `--force` 重跑；不是独用的，不压平、不 rebase、不强推，汇报。

## 被拦下与撤销

- 直接执行的 git 命令（合并、rebase、reset、推送等）被仓库的 git hook 拦下时，照输出里的提示复原现场、处理，不要绕过（经流程脚本执行时被拦下的，按「## 流程脚本」处理）；提示里要 reset、强推或改写已有提交的，先问用户，并仍受下一条、「## 压平与 rebase」与「## 推送」的限制。
- 确要撤销某个提交，先问用户。它和它之后的提交都还没推送、都要丢掉、没有别的分支包含它们（`git branch --contains <sha>` 只列出目标分支）时，可以在主工作副本里 reset 掉。其余情形不要在目标分支上用 reset、amend 去掉提交：在主工作副本里用 `git revert`，或者在做撤销的那个提交的信息里加一行 `Reverts: <sha>`，都在历史里留下有意撤销的记录。

## 合并

- 顺序：对齐远程 → 压平 → rebase →（需要时）验证 → 向用户确认 → `merge --ff-only` → 清理。验证按改动范围跑检查；不通过的，是本次改动引起的就改好后重新验证，判断不清或不是本次改动引起的，汇报、不合并。范围：


  - **整套**是项目在指令文件或文档里写明的检查命令（格式检查、类型检查、Lint、构建、测试中写明了的）。没写明的，以项目配置里现有的这几类本地检查命令为整套（不含发布、部署这类有外部副作用的），并告知用户把整套写进指令文件；一条都没有的，告知用户这次没有可跑的检查。
  - **只改了构建、类型检查与测试都不读的文件**（通常是文档、指令文件、skill 与子代理定义；有构建或测试校验的这类文件，以及格式检查与 Lint 的配置文件，都不算）：只跑覆盖到这些文件的格式检查与 Lint，没有就不跑并告知用户。
  - **除上一条那类文件外，改动只在一个包或模块内**、项目在指令文件或文档里为它写明了自己的检查命令、且它不被其它包依赖：跑这个包的检查，包外那类文件另按上一条跑。
  - **其余跑整套**：改到被多处依赖的共享层（公共代码与类型，被其它包依赖的包，格式化、类型检查、构建、测试与 Lint 的配置，依赖版本）、跨多个包，或判断不了的。

  定范围时的改动只算本分支自己的：相对它与目标分支分叉点的全部改动（直接在目标分支上改的，相对改动前）。rebase 或 merge 从目标分支带进来的代码不算进改动，目标分支上的代码视为已检查过；之后按新的分叉点算，解冲突改过的地方算进去。但上面几条的归类（文件有没有被构建或测试读到、包有没有被其它包依赖、适用哪些检查配置）按 rebase 或 merge 之后的代码判断。带进新代码后本该重跑的，同时满足下面三条时不必重跑，检查结果不会变：本分支的改动全是「只改了构建、类型检查与测试都不读的文件」那类；这些文件与本次会话里覆盖它们的格式检查与 Lint 通过时内容相同；此后带进来的代码没动这些格式检查与 Lint 的配置、写明的命令或工具版本。

  已经确定后面还要跑一次检查、那次会在含有这次改动的代码上跑（由你在本次任务里接着跑），且这次的改动在那次通过前能只留在本地（不推送、不发 PR；合并流程会立即推送或在远端合并的不算），这次不跑，由那次的结果代替：如几个分支依次在本地合并进同一个目标分支，后面的分支对齐到已含前面改动的目标分支后才检查，只在最后的合并结果上跑一次。为判断能否改写某个分支而跑的检查（如对齐时 rebase 目标分支前，验证它上面未推送的提交）当场跑，不由后面代替。向用户确认合并或报检查结果时，写明这次还没检查、由哪次代替。那次定范围时，被代替的改动算进改动，不因已带进目标分支就视为检查过；那次失败的，按失败的那部分追查是哪份改动引起的，属于被代替的改动的单独修，不混进别的分支的提交；那次没跑成的，在当前代码上按被代替的改动定范围补跑。拿不准那次一定会跑、或会不会含这次的改动，照常跑。

- 同一份内容只验证一次：本次会话里覆盖上面算出范围的检查通过时，所检查内容的文件树与当前 `git rev-parse HEAD^{tree}` 相同的，不再验证；拿不准就验证。
- 项目走 PR 合并的（用户说明，或仓库文档约定）：对齐、压平、rebase、需要时的验证、向用户确认照做，到此为止；不在本流程里提 PR，也不在本地 merge，提 PR 与之后的清理按项目的 PR 流程做，没有约定的按用户指示。
- 本地合并前逐项核对：分支的 `HEAD` 仍是验证、征得用户同意时的那个提交（变了就按「分支在验证、确认之后又变了」那条走）；已征得用户同意（给用户看最终的提交列表与验证结果，沿用之前验证的写明沿用）。
- 本地合并在主工作副本里用 `git merge --ff-only <分支>`。失败时先看输出：被仓库的 git hook 拦下的，按「## 被拦下与撤销」第一条处理，改了分支内容的按下一条走；确实不能快进（目标分支又前进了）的，先按「## 对齐远程的目标分支」对齐，再回分支重新 rebase，按下一条走。
- 分支在验证、确认之后又变了（重新 rebase 带进了新代码、对齐远程时被搬过、按 hook 的提示改过）：
  - 先按上面的范围（含其中带进新代码后不必重跑的条件）与「同一份内容只验证一次」判断，要验证的重跑（不通过的处理同上）；
  - 通过或不必重跑后，分支自己的提交内容变了（解过冲突、重新压平、补改）或此前没征得同意的，向用户确认，没变的沿用原确认；
  - 再合并。
- 合并后立即在主工作副本里执行 `flow-cleanup.sh <分支> --merged-into <目标分支>`（不动远端分支），不必再问。
  - 报 worktree 里有被忽略的文件：除依赖、构建产物这类可重新生成的之外还有别的（如 `.env`、本地配置），先问用户要不要留；都能删的加 `--ignored-ok` 重跑。
- 不自动推送目标分支，用户要推再推。

## 推送

- 推送目标分支被拒（远端报非快进，或仓库的 git hook 报远程有本地没有的提交）时不要强推，按「## 对齐远程的目标分支」对齐后再重新推送。
