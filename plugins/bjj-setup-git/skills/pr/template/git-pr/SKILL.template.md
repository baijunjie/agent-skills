# 提交 PR

`<分支>` 指承载本次 PR 的分支：第 1 步另建了分支的是新分支，否则是当前分支。
`<推送目标>` 指 `<分支>` 在 `<推送远端>`（见「目标分支」）上对应的分支名：已有开放 PR 的取它的 head 分支，否则同 `<分支>`。
拿不准就汇报：停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

## 流程脚本

机械操作由仓库 `.githooks/` 下的 `flow-*.sh` 完成。一律执行主工作副本（仓库原目录，`git worktree list` 的第一项）里的那份，从目标分支新切出的 worktree 里可能还没有这些文件；下文写的 `flow-<名>.sh <参数>` 都指：

```bash
sh "$(git worktree list --porcelain | sed -n '1s/^worktree //p')/.githooks/flow-<名>.sh" <参数>
```

- 退出码 0：做完了。输出里以「注意：」起头的提示告知用户。
- 退出码 1：脚本停下了。下文点名了的原因按下文处理，其余汇报。
- 退出码 2，或脚本不存在：汇报。

下文为某种原因写明了做法的按下文做；其余提示只转述给用户，不自行照做。

## 目标分支

- 调用时指定了分支就提到那个分支，不改项目默认值，也不改别的分支的记录。
- 没指定、而当前分支记录了 `git config branch.<当前分支>.targetBranch` 时，提到它记录的分支。
- 没指定、也没有这条记录时，提到 `{{PR_BASE}}`（本项目默认的 PR 目标分支）。
- 当前分支已有开放的 PR、它的 base 与上面定出的目标分支不一致时，先问用户提到哪个，问完再做第 1 步：第 2 步起的改写与推送会直接更新这个 PR。
- 动手前先定两个远端：`<远端>` 是目标分支所在的远端，取基准、做比较、建 PR 都用它；`<推送远端>` 是 `<分支>` 推往、PR head 所在的远端，fork 工作流里两者不同。
  - 当前分支已有开放 PR 的（head 的仓库与分支都要对上，不只看分支名）以它为准：`<远端>` 取 base 仓库对应的远端，`<推送远端>` 取 head 仓库对应的远端。
  - 没有 PR 的按 git 配置推断：`<远端>` 看目标分支的上游，`<推送远端>` 看 `branch.<分支>.pushRemote`、`remote.pushDefault`，再看分支自己的上游（指向目标分支的不算），都没有就取 `<远端>`。
  - 推断不出或有歧义（对应的远端不存在、唯一的远端是 fork、目标分支没有上游而不止一个远端有它等）就问用户，一次问清两个。
- 定好远端后只 fetch 本次要用的两个分支：第 1 步前 `git fetch <远端> <目标分支>`；第 1 步定下 `<分支>` 后、第 2 步判断是否推过前 `git fetch <推送远端> <推送目标>`，它报远端没有这个分支就是还没推过。
- 压平、rebase 与比较的基准一律取 `<远端>/<目标分支>`，不取本地目标分支：它可能领先远端，会把没推送的本地提交垫进 PR。

## 步骤

git 命令被仓库的 git hook 拦下时（直接执行的，以及第 4 步的推送被拒），照提示处理，不要绕过，改了分支内容的按第 3 步验证后再继续：
- 提示里给的跳过办法（`--no-verify`、跳过用的环境变量、改 hook 配置）不采用，非跳过不可的汇报；
- 提示里给的声明有意撤销的办法（`git revert`、`Reverts:` 行），先问用户是否确属有意撤销，不自行声明。

1. **准备分支**：有未提交的改动时先问用户是否纳入本次 PR：纳入的先提交；不纳入的等用户自行提交或 stash 后再继续。
   没有领先 `<远端>/<目标分支>` 的提交就告知用户没东西可提，结束。
   `git log <远端>/<目标分支>..HEAD` 里混有不属于本次 PR 的提交，先问用户怎么处理，不自行丢弃。
   当前检出的就是目标分支（提交直接做在本地目标分支上）时：用户要把其中一部分留在目标分支上的，汇报；否则先 `git switch -c` 另建新分支承载这些提交（按变更类型取 `feat/`、`fix/` 等前缀），再用 `git branch -f` 把本地目标分支退回远端位置。
2. **压平**：
   - 先执行 `flow-record.sh <分支> <目标分支> $(git merge-base HEAD <远端>/<目标分支>)`，记下目标分支与切出点（分支最初从目标分支切出的位置，已记过的不改写；`<目标分支>` 写分支名，不带远端前缀）。
   - 分支已推送过的（`<推送远端>` 上已有 `<推送目标>`），压平或第 3 步的 rebase 真要改动提交时会改写已推送的历史：远端那个分支有本地没有的提交（如在网页上采纳的建议、维护者推的修复）时汇报，不要覆盖；否则要分支是自己独用的（远端上没有别人的提交）、且用户同意强推，才动手改写。
   - 多个提交默认压成一个：提交信息写进工作树之外的临时文件，执行 `flow-squash.sh <远端>/<目标分支> <文件>`；它报新提交信息缺了原提交里的撤销声明的，补上后重跑。
   - 确实包含多个互不依赖的变更时才保留多个：先记下 `git rev-parse HEAD`（下称 `<压前提交>`），在分叉点（现算的 `git merge-base HEAD <远端>/<目标分支>`，不是记着的切出点）上自己拆；
     拆完执行 `flow-squash.sh --check <远端>/<目标分支> <压前提交>`，不通过就按它给的命令退回重做。
3. **rebase 到最新的目标分支**：`git rebase <远端>/<目标分支>`。解冲突要把双方的改动合起来，不要一律取自己这一侧。
   rebase 后、第 4 步前**验证**：按改动范围跑检查。范围：


   - **整套**是项目在指令文件或文档里写明的检查命令（格式检查、类型检查、Lint、构建、测试中写明了的）。没写明的，以项目配置里现有的这几类本地检查命令为整套（不含发布、部署这类有外部副作用的），并告知用户把整套写进指令文件；一条都没有的，告知用户这次没有可跑的检查。
   - **只改了构建、类型检查与测试都不读的文件**（通常是文档、指令文件、skill 与子代理定义；有构建或测试校验的这类文件，以及格式检查与 Lint 的配置文件，都不算）：只跑覆盖到这些文件的格式检查与 Lint，没有就不跑并告知用户。
   - **除上一条那类文件外，改动只在一个包或模块内**、项目在指令文件或文档里为它写明了自己的检查命令、且它不被其它包依赖：跑这个包的检查，包外那类文件另按上一条跑。
   - **其余跑整套**：改到被多处依赖的共享层（公共代码与类型，被其它包依赖的包，格式化、类型检查、构建、测试与 Lint 的配置，依赖版本）、跨多个包，或判断不了的。

   定范围时的改动只算本分支自己的：相对它与目标分支分叉点的全部改动（直接在目标分支上改的，相对改动前）。rebase 或 merge 从目标分支带进来的代码不算进改动，目标分支上的代码视为已检查过；之后按新的分叉点算，解冲突改过的地方算进去。但上面几条的归类（文件有没有被构建或测试读到、包有没有被其它包依赖、适用哪些检查配置）按 rebase 或 merge 之后的代码判断。带进新代码后本该重跑的，同时满足下面三条时不必重跑，检查结果不会变：本分支的改动全是「只改了构建、类型检查与测试都不读的文件」那类；这些文件与本次会话里覆盖它们的格式检查与 Lint 通过时内容相同；此后带进来的代码没动这些格式检查与 Lint 的配置、写明的命令或工具版本。

   已经确定后面还要跑一次检查、那次会在含有这次改动的代码上跑（由你在本次任务里接着跑），且这次的改动在那次通过前能只留在本地（不推送、不发 PR；合并流程会立即推送或在远端合并的不算），这次不跑，由那次的结果代替：如几个分支依次在本地合并进同一个目标分支，后面的分支对齐到已含前面改动的目标分支后才检查，只在最后的合并结果上跑一次。为判断能否改写某个分支而跑的检查（如对齐时 rebase 目标分支前，验证它上面未推送的提交）当场跑，不由后面代替。向用户确认合并或报检查结果时，写明这次还没检查、由哪次代替。那次定范围时，被代替的改动算进改动，不因已带进目标分支就视为检查过；那次失败的，按失败的那部分追查是哪份改动引起的，属于被代替的改动的单独修，不混进别的分支的提交；那次没跑成的，在当前代码上按被代替的改动定范围补跑。拿不准那次一定会跑、或会不会含这次的改动，照常跑。

   同一份内容只验证一次：本次会话里覆盖上面算出范围的检查通过时，所检查内容的文件树与当前 `git rev-parse HEAD^{tree}` 相同的，不再验证；拿不准就验证。
   验证失败是本次改动引起的，改好并入所属的提交后重新验证；判断不清或不是本次改动引起的，汇报、不推送。
4. **推送**：执行 `flow-push.sh <推送远端> <分支> <推送目标>`；报要改写已推送的历史的，第 2 步已确认能强推的加 `--force` 重跑，否则停下问用户。
5. **提交 PR**：建在 `<远端>` 对应的仓库，base 取 `<目标分支>`，head 取 `<推送远端>` 上的 `<推送目标>`（写明它所属的账号或仓库）。该分支已有开放的 PR 就不重建，推送已更新它；它的 base 与 `<目标分支>` 不一致的，改成 `<目标分支>`。
6. **清理本地**：PR 已存在（新建或已有）就立即清理，不必再问。先回到主工作副本（分支自己的 worktree 会被删掉），执行 `flow-cleanup.sh <分支> --pushed-to <推送远端>/<推送目标>`。
   - 报 worktree 里有被忽略的文件：除依赖、构建产物这类可重新生成的之外还有别的（如 `.env`、本地配置），先问用户要不要留；都能删的加 `--ignored-ok` 重跑。
   - 其它原因的，不要绕过脚本手工删。

## PR 建好之后又冲突

本次调用结束后目标分支又前进、PR 报冲突，用户再来处理时：

- 分支与 PR 由用户指定，没指定就问；本节的目标分支、两个远端与 `<推送目标>` 都以这个 PR 的 base 与 head 为准，定好后按「目标分支」一节 fetch 本次要用的两个分支，未提交的改动按第 1 步处理。本地分支已在第 6 步删掉的，`git switch -c <分支> <推送远端>/<推送目标>` 从远端重建，目标分支与切出点按第 2 步重新记。
- 问用户用 merge 还是 rebase 解，两种推送后都按第 6 步清理本地：
  - merge：本地分支先要包含 `<推送远端>/<推送目标>`（落后就快进，分叉就汇报），再把 `<远端>/<目标分支>` 合进来，解冲突同第 3 步，按第 3 步验证、第 4 步推送。这条路不改写已推送的历史：验证或推送出了问题（含推送被仓库的 git hook 拦下）一律汇报。
  - rebase：按第 2–4 步走；选了就是同意强推，独用与否仍按第 2 步核对。

## 撰写身份

适用于所有提交信息（含 amend 的）、PR 标题与描述，语言跟随仓库历史：

- 不留任何 AI 痕迹：不写 `Co-Authored-By`、不写「Generated with …」、不提 AI 协助。
