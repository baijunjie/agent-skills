## 注释规范

注释的唯一读者是不了解此处上下文的未来维护者，判断标准是「读代码本身得不到、但维护时必须知道」。

**应该写：**

- 设计意图与取舍理由：为什么这样实现、为什么没采用更直观的写法。
- 代码读不出的隐含前提与约束：外部接口的古怪行为、并发与性能考虑、边界条件、单位 / 时区等易错约定。
- 复杂算法、正则、位运算的整体思路，让人不必逐行反推。
- `TODO`：临时代码、部分实现、等待外部依赖完善的内容必须标注。
- 改代码时同步改它的注释——过期的注释比没有注释更有害。

**不应该写：**

- 复述代码字面含义的冗余注释（显而易见的赋值、getter/setter 等）。
- 变更历史：删掉了什么、原来是什么、「新增」「修改」标记——这些交给 git。
- 被注释掉的代码，直接删除。
- 与其它实现的对比、指向别处代码的交叉引用——被引用方一改动就失真。
- 过程性信息：引发本次改动的问题 / Bug 编号 / 需求讨论 / 评审反馈。
- 说给本次改动评审者听的话（「这里改用了缓存」）——注释属于代码，不属于这次 diff。

### 解释范畴

注释只解释它所在的那一层：函数注释解释这个函数，文件顶部注释解释这个文件。

- 跨文件的系统性说明不写进注释：模块之间如何协作、整体调用链、架构分层、跨模块的数据流与状态机。它们是文档的职责。
- 本函数 / 本文件确实要提到外面的东西时，只写与它直接相关的那一句，其余引用文档，不在注释里展开。
- 不替别的文件写说明：调用方该怎么用、下游怎么处理，归它们自己那边。

### 引用文档

- 只引长期维护、随代码库提交、位置稳定的正式文档，以及外部标准与第三方官方文档。
- 不引开发计划、方案讨论、任务、Issue、聊天记录等临时文档。
- 引用只指路，不复述被引文档内容。
- 仓库内文档写完整相对路径和章节标题；不用行号或锚点。
- 外部文档写名称、版本或编号和章节；URL 可选。
- 引用不替代注释本身：这里为什么这样写仍要在注释里说明。

## Git 提交信息

- 不要在 commit 消息或 PR 描述里留下 AI 痕迹，例如 `Co-Authored-By` 或「Generated with …」。
- 以人类开发者的身份自然撰写，不作关于 AI 协助的声明。
- 遵循 Conventional Commits（`feat:` / `fix:` / `refactor:` / `docs:` / `chore:` 等前缀）。
- 提交信息语言跟随仓库历史。

## 分派子代理

子代理用于获得独立审视，或分担目标明确的机械工作。一次只交代一件事，给足背景、明确完成判据，并让它只报告结论。

- `mechanical`：批量搜索、定位、替换、格式化和简单文本处理。
- `implement`：已定方案的具体实现、明确重构和修复。
- `code-reviewer`：编码结束后的独立质量检查；只检查，不改代码。
- `investigate`：跨模块疑难排查、根因定位和大范围改造。
- `architect`：模块边界、跨模块方案和技术选型；只在确实需要深入设计时用。

代理 TOML 不指定模型；由当前 Codex 环境按可用配置选择。不要为机械任务临时升级模型，也不要把同一任务拆给多个代理造成冲突。

## 编码结束自检

完成开发后，无论改动大小，都按以下顺序逐项自检：

1. **代码质量检查**：派独立的 `code-reviewer` 审本次改动，不让编码者自己审。没有子代理机制时，先完整读一遍改动涉及的每个文件全文再自查；有意见就修，修完后再审直到通过。
2. **文档更新**：需要更新给后来者看的文档时，派独立的文档子代理；没有子代理机制时，落笔前完整读一遍要改的文档。文档改动现存章节后，处理代码注释的引用点，并确认代码实现与文档一致。
3. **静态检查**：运行项目约定的格式化、类型检查、Lint 等质量检查命令，确认无报错。
