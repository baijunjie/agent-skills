# 开发流程：Git Worktree

- 产生代码变更的任务，一律在独立的 git worktree + 独立分支上完成，编辑、构建、测试、质量检查都在里面进行；主工作副本保持干净，便于随时对照目标分支。只读排查、答疑这类不产生改动的操作除外。
- 目标分支是创建 worktree 时主工作副本所在的分支，不一定是主分支；开发分支从它的最新提交拉出，最终也合并回它。创建时必须记下来：`git config branch.<分支>.worktreeTarget <目标分支>`——换了会话也查得到该合并回哪，回退闸门也靠这条记录才会守护目标分支。
- worktree 放在仓库内的 `.worktrees/<分支短名>/`；分支名按变更类型取 `feat/`、`fix/`、`refactor/`、`docs/` 前缀。
- 开发期间的提交不必讲究，合并前压平：目标分支上的每个提交都要能独立说明、独立回滚。分支只做了一件事就压成一个提交；确实包含多个互不依赖的变更才保留多个，但拆分点落在同一个文件内部时不要硬拆。提交信息描述最终状态，不复述过程（不写「修复上一个提交」「按反馈调整」），格式与语言跟随仓库历史。
- 压平一律在原基点上做：`git reset --soft $(git merge-base HEAD <目标分支>)` 后重新提交。不要 reset 到 `<目标分支>` 等更新的提交，也不要另开分支再把文件拷过去——基点换了而内容没合，旧代码就会被当成新改动，悄悄撤销基点之后目标分支上的改动。压完核对第一个提交的父提交仍是原基点、工作树与压平前完全一致，任何一条不满足就退回重做。
- 压平后再 `git rebase <目标分支>`，一个提交只解一次冲突。解冲突要把双方的改动合起来，一律取自己这一侧等于撤销目标分支上的对应改动。rebase 后还要改的，并回原提交，不要再堆新提交。
- 自己独用的分支压平后需要强制推送，推之前先向用户确认。
- 仓库装有回退闸门（`.githooks/revert-gate.py`）：受守护的分支（上面记录的目标分支，以及闸门常驻守护的分支，通常是主分支）移动时，本地 merge / commit / reset 与 push 都会被自动检查，拒绝改写已发布的历史、以及撤销该分支已有改动的更新。被拦说明压平或解冲突出了错，照提示回分支重做，不要设 `REVERT_GATE_SKIP=1` 绕过。确要撤销某个提交，先问用户，同意后用 `git revert` 或在提交信息里加一行 `Reverts: <sha>`，不要在目标分支上用 reset、amend 去掉提交。
- 合并前必须：功能已验证；收尾自检（代码质量检查、文档同步、静态检查）已完成；历史已压平并 rebase 到最新的目标分支；闸门预检 `s=$(git show "$(git config --get revert-gate.branch)":.githooks/revert-gate.py) && python3 -I -c "$s" check <目标分支> <分支>` 退出码为 0（merge 被闸门拦下时主工作副本已被写成分支内容，要 `git reset --merge` 复原，所以先预检）；主工作副本仍在目标分支上；已向用户确认。
- 在主工作副本里用 `git merge --ff-only <分支>` 合并，快进失败说明 rebase 没做干净，不要退回裸 merge。rebase 带进来的新代码没参与过之前的验证，合并后要在目标分支上重跑构建、测试、格式检查。合并完成后立即 `git worktree remove` 掉该 worktree 并删除分支——这是合并动作的一部分，不必再问。
