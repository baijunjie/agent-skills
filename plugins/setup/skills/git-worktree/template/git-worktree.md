# 开发流程：Git Worktree

- 产生代码变更的任务，一律在独立的 git worktree + 独立分支上完成，编辑、构建、测试、质量检查都在里面进行，不要直接改主工作副本的主分支；主工作副本保持干净，便于随时对照主分支。只读排查、答疑这类不产生改动的操作除外。
- 开工前从最新的主分支创建 worktree，放在仓库内的 `.worktrees/<分支短名>/`；分支名按变更类型取 `feat/`、`fix/`、`refactor/`、`docs/` 前缀。
- 开发期间的提交不必讲究，粒度和措辞都不用纠结——合并前会把它们压平。
- 合并前把分支历史压平：主分支上的每个提交都要能独立说明、独立回滚，开发期的 fix / typo 不该留在主分支。分支只做了一件事就压成一个提交；确实包含多个互不依赖的变更才保留多个，但拆分点落在同一个文件内部时不要硬拆。
- 压平只改历史、不改内容：压平前后的工作树必须完全一致，出现任何差异都说明压错了，退回压平前重做。
- 压平后的提交信息描述最终状态，不复述过程（不写「修复上一个提交」「按反馈调整」），格式与语言跟随仓库历史。
- 先压平、再 `git rebase <主分支>`，这样一个提交只需解一次冲突。rebase 后重跑验证时若还要改，把改动并回原提交，不要再堆新提交。
- 改写历史可能悄悄撤销主分支上的改动，所以合并前要逐个核对基点之后主分支上的每个提交 `C`：待合并分支里某个文件的内容等于 `C^` 里的版本、而不等于 `C` 里的版本，就说明 `C` 对这个文件的改动丢了（该文件在 `C` 之后又被别的提交改过时这样比不出来，改比对 `C` 的增删行集合还在不在）。成因是 `git reset --soft <新基点>` 这类做法只换基点、不动工作树，分支若没真正 rebase 过，压出来的差额里就带着「撤销基点之后主分支上的全部改动」；rebase 时把冲突一律解到自己这一侧，结果相同。整个过程没有任何信号——`git merge --ff-only` 只校验祖先关系、不看内容，照样快进成功，被撤销的那些提交在 `git log` 里也还在。
- 自己独用的分支压平后需要强制推送，推之前先向用户确认。
- 合并前必须确认这几件都做完了：功能已验证通过、收尾自检（代码质量检查、文档同步、静态检查）已完成、历史已压平、已 rebase 到最新主分支。rebase 带进来的新代码没参与过之前的验证，构建、测试、格式检查要在合并后的主分支上重跑一遍才算数。
- 合并回主工作副本用 `git merge --ff-only <分支>`：快进失败说明 rebase 没做干净，不要退回裸 merge 生成 merge commit。
- 合并回主分支前必须先向用户确认。合并完成后立即 `git worktree remove` 掉该 worktree 并删除分支——这是合并动作的一部分，不必再问，也不要留到下次。
