# 文档输出

补充说明（可选）：

<notes>
$ARGUMENTS
</notes>

很好，将本次讨论的最终方案**简洁整理**并输出成开发文档。

## 文档内容要求

**重要**：文档应该是**简洁的设计方案文档**，仅整理我们讨论过的内容，不添加额外信息。

### 必须包含的内容
- **问题描述** - 从讨论中提取的具体问题和现象描述
- **解决方案概述** - 讨论确定的核心解决思路和关键设计决策理由
- **技术设计** - 讨论中确定的接口签名、数据结构、核心方法定义（仅接口，无实现）
- **实现方案** - 讨论中涉及的重构策略、方法分解、调用流程框架

### 严格禁止包含的内容
- **完整实现代码** - 绝对不写函数体内部实现逻辑
- **编码实施指导** - 不写具体的编码步骤和实现指导
- **讨论之外的内容** - 严格限制在讨论范围内，不添加任何推测或扩展
- **代码落点** - 不列要改哪些文件、不指定代码放进哪个路径，那是实现阶段由开发者调查确定的

### 代码示例边界说明
- **允许的示例**：展示讨论中定义的方法间调用关系和执行流程，所有调用的方法都是本次讨论确定的
- **禁止的示例**：包含具体业务逻辑、算法实现、第三方库调用等实际执行代码

## 文档输出要求

### 目录结构要求
- 在项目的开发文档目录（默认 `docs/development/`，项目已有自己的约定时按项目的）下建一个开发主题目录，格式 `YYYYMMDD-{中文开发简述}`；日期是目录的创建日期，不代表开发周期。不要把文档直接放在开发文档目录根下
- 本次讨论属于某个已有主题时，进那个目录追加或更新文档，不另建目录
- 开发任务文档按功能阶段划分，一份对应一个**能独立测试、能独立合并**的里程碑：这一份做完，代码应当可以自行验证并合入，不必等后续文档一起才跑得通
- 拆多细由你裁量：一个里程碑可以横跨数据、逻辑、接口、界面多个层次，也可以只动一个文件。不要为凑数硬拆，也不要把彼此独立的两块塞进一份
- 按依赖方向排序，被依赖的里程碑排在前面（通常是数据结构 → 核心逻辑 → 对外接口 → 调用方）
- **只有一个里程碑时，目录下就只放 `README.md`**，总览与该里程碑的内容合在这一份里写：一份文档不需要索引，也没有顺序可编号。此时不要另建编号文档
- 拆成两份及以上时，`README.md` 只作总览——问题描述、解决方案概述、关键设计决策——里程碑内容放进各自的编号文档
- 目录下已有 `README.md` 的不重复创建，只更新内容；原先单份的主题这次要加里程碑时，把 `README.md` 里的里程碑内容移进编号文档，README 退回纯总览

### 文档命名和排序
本节只适用于拆成两份及以上的情形；单个里程碑的主题只有 `README.md`，不编号。

- 将文档按照合理的开发顺序进行排序，并在文件名中编号
- 文档命名格式：`[编号]-[开发简述].md`
  - 开发简述应使用中文简洁描述该文档的主要开发内容
  - 例如：`01-订单状态存储与迁移.md`、`02-状态流转接口与校验.md`

### 文档内容组织
- 各个文档中不应该出现重复的内容描述
- 如果排在后面的文档依赖前面文档的内容，可以简洁引用前面的文档
- 每个文档只聚焦自己那个里程碑，范围之外的设计不掺进来
- 每个里程碑文档（单份时即 `README.md`）开头点明本里程碑的目标与完成判据，格式为：

  ```
  > 目标: <这一份要做成什么样>
  > 完成判据: <怎么算做完、怎么验证>
  ```

### 开发者提示信息
在每个里程碑文档（单份时即 `README.md`）的末尾，根据当前开发功能添加针对开发者的提示。提示只到「项目里已经有什么、该复用哪一块」的粒度，具体在哪个文件、怎么调用留给开发者自行调查：

- **可复用能力**：项目里已有、本里程碑应当直接复用的机制或模块（鉴权、缓存、错误处理、公共组件、工具函数等），指到能力与所属模块即可，不必给文件路径；不确定项目里有没有就不写，别猜（无可复用内容时省略）
- **开发要点**：需要遵守的开发规范、注意事项、与现有系统的集成方式，强调已实现的全局功能，防止开发者重复实现
- **参考文档**：相关的技术文档、规范文档路径（避免重复描述已有内容）
