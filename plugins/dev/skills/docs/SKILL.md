# 文档输出

补充说明（可选）：

<notes>
$ARGUMENTS
</notes>

很好，将本次讨论的最终方案**简洁整理**并输出成开发文档。

## 文档内容要求

**重要**：文档应该是**简洁的设计方案文档**，仅整理我们讨论过的内容，不添加额外信息。

### 必须包含的内容
- **问题描述** - 从讨论中提取的具体问题和现象描述
- **解决方案概述** - 讨论确定的核心解决思路和关键设计决策理由
- **技术设计** - 讨论中确定的接口签名、数据结构、核心方法定义（仅接口，无实现）
- **实现方案** - 讨论中涉及的重构策略、方法分解、调用流程框架

### 严格禁止包含的内容
- **完整实现代码** - 绝对不写函数体内部实现逻辑
- **编码实施指导** - 不写具体的编码步骤和实现指导
- **讨论之外的内容** - 严格限制在讨论范围内，不添加任何推测或扩展

### 代码示例边界说明
- **允许的示例**：展示讨论中定义的方法间调用关系和执行流程，所有调用的方法都是本次讨论确定的
- **禁止的示例**：包含具体业务逻辑、算法实现、第三方库调用等实际执行代码

## 文档输出要求

### 目录结构要求
- 在 `@docs/development` 下创建文档目录（格式：`YYYYMMDD-{中文开发简述}`）
- 如果文档目录已存在，则在现有目录下添加新文档
- 目录下必须包含 `README.md` 作为总览文档，包含问题描述、解决方案概述、关键设计决策
- 如果目录下已有 `README.md`，则不重复创建，只需更新内容
- 开发任务文档必须按文件划分，每个需要修改的文件都要输出一个对应的文档
- 按照以下顺序来安排任务，确保依赖关系合理：
  1. **数据层**：数据库定义修改（如需要）
  2. **服务层**：后端 API 接口与业务逻辑
  3. **数据交互层**：前端 API 封装与状态管理
  4. **展示层**：前端 UI 组件与用户交互

### 文档命名和排序
- 将文档按照合理的开发顺序进行排序，并在文件名中编号
- 文档命名格式：`[编号]-[开发简述].md`
  - 开发简述应使用中文简洁描述该文档的主要开发内容
  - 例如：`01-文档服务Git集成.md`、`02-乐观更新核心Hook.md`

### 文档内容组织
- 各个文档中不应该出现重复的内容描述
- 如果排在后面的文档依赖前面文档的内容，可以简洁引用前面的文档
- 每个文档都应该专注于单一文件的设计变更，保持内容聚焦
- 每个开发文档开头必须注明文件的实际路径，格式为：`> 文件路径: src/actual/file/path.ts`

### 开发者提示信息
在每个具体文档的末尾，根据当前开发功能添加针对开发者的提示：

- **可复用资源**：项目中可直接使用的组件、hooks、工具函数等路径（无可复用内容时省略）
- **开发要点**：需要遵守的开发规范、注意事项、与现有系统的集成方式，强调已实现的全局功能，防止开发者重复实现
- **参考文档**：相关的技术文档、规范文档路径（避免重复描述已有内容）
