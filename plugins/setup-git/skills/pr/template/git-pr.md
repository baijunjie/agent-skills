# 提交 PR

## 目标分支

- 调用时指定了分支就提到那个分支，只对本次生效。
- 没指定、而当前分支记录了 `git config branch.<分支>.worktreeTarget` 时，提到它记录的分支。
- 没有这条记录时，没指定就提到 `{{PR_BASE}}`（本项目默认的 PR 目标分支，安装时确定）。
- 动手前先 `git fetch` 目标分支，后面的比较与压平都以远端的最新状态为准。远端以目标分支的上游为准
  （`git config branch.<目标分支>.remote`）；本地没有这个分支或它没设上游时，用有同名分支的那个远端，
  不止一个就问用户。下文的 `<远端>` 指它。

## 步骤

1. **准备分支**：有未提交的改动时先问用户是否纳入本次 PR。当前就在目标分支上时：
   - 先 `git switch -c` 另建新分支承载本地提交（按变更类型取 `feat/`、`fix/` 等前缀）；
   - 再用 `git branch -f` 把本地目标分支退回远端位置，否则这些提交会残留在上面。
     只有它比远端多出的提交全属于本次 PR 时才退回，混有别的提交就先问用户。
2. **压平**：多个提交默认压成一个，确实包含多个互不依赖的变更时才保留多个。压平在原基点上做：
   `git reset --soft $(git merge-base HEAD <远端>/<目标分支>)` 后重新提交。
   不要 reset 到目标分支的最新提交——基点换了而内容没合，会悄悄撤销目标分支上的改动。
   提交信息格式与语言跟随仓库历史。
3. **推送**：压平改写了已推送的历史时，只有自己独用的分支才能用 `--force-with-lease` 强推，且推之前先问用户。
4. **提交 PR**：标题与描述的语言跟随仓库历史。建好后不主动 rebase。PR 与目标分支冲突时告诉用户，需要解冲突时先问用户用 merge 还是 rebase；
   解冲突要把双方的改动合起来，不要一律取自己这一侧——那等于撤销目标分支上的对应改动。
5. **清理本地**：确认 PR 已创建、分支已推到远端后立即清理，这是提交 PR 的一部分，不必再问——
   - 分支在某个 worktree 里：先离开该 worktree 目录，再 `git worktree remove`；
   - 主工作副本停在该分支上：切回目标分支（本地没有就从远端建跟踪分支）；
   - 最后 `git branch -D` 删除本地分支。

   worktree 里有未提交或未跟踪的文件、目标分支被别的 worktree 占用而切不回去时，停下来问用户，不要加 `--force`。

操作被仓库的 git hook 拦下时照提示处理，不要绕过。

## 撰写身份

适用于压平后的提交信息、PR 标题与描述：

- 不留任何 AI 痕迹：不写 `Co-Authored-By`、不写「Generated with …」、不提 AI 协助。
- 以人类开发者的口吻撰写，不作关于自己是 AI 的声明。
