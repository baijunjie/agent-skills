# 提交 PR

`<分支>` 指承载本次 PR 的分支：第 1 步另建了分支的是新分支，否则是当前分支。

## 目标分支

- 调用时指定了分支就提到那个分支，不改项目默认值，也不改别的分支的记录。
- 没指定、而当前分支记录了 `git config branch.<当前分支>.targetBranch` 时，提到它记录的分支（当前就在目标分支上时视为没有记录）。
- 没有这条记录时，没指定就提到 `{{PR_BASE}}`（本项目默认的 PR 目标分支，安装时确定）。
- 动手前先 `git fetch --all`。接着定下 `<远端>`：以目标分支的上游为准（`git config branch.<目标分支>.remote`）；本地没有这个分支
  或它没设上游时，用有同名分支的那个远端，不止一个就问用户，一个都没有就停下问用户；上游指向的远端不存在的，按本地没有处理。下文的 `<远端>` 都指它。
- 压平、rebase 与比较的基准一律取 `<远端>/<目标分支>`，不取本地目标分支：合并发生在远端。
- 第 1 步之后，把本次定下的目标分支记进 `<分支>`：
  `git config branch.<分支>.targetBranch <目标分支>`。没有记录就写；已有记录且与本次不同时先问用户，
  同意了再改。值写分支名、不带远端前缀（`main`，不是 `origin/main`）。

## 步骤

操作被仓库的 git hook 拦下时照提示处理，不要绕过。提交信息、PR 标题与描述按文末「撰写身份」写。

1. **准备分支**：有未提交的改动时先问用户是否纳入本次 PR：纳入的先提交；不纳入的请用户自行提交或 stash，等他处理完再继续，不要替他处理。没有领先 `<远端>/<目标分支>` 的提交（只落后也算没有）就没东西可提，告知用户并结束。否则看当前在哪：
   - **在目标分支上**：先核对本地领先的提交是否全属于本次 PR，混有别的先问用户，由用户决定去向、不替他丢弃；
     再 `git switch -c` 另建新分支承载它们（按变更类型取 `feat/`、`fix/` 等前缀）；
     最后用 `git branch -f` 把本地目标分支退回远端位置，否则这些提交会残留在上面。
   - **不在目标分支上**：`git log <远端>/<目标分支>..HEAD` 里混有不属于本次 PR 的提交，先问用户，由用户决定去向。
2. **压平**：
   - 先记下切出点 `git config branch.<分支>.forkPoint $(git merge-base HEAD <远端>/<目标分支>)`——
     rebase 之后就再也算不出来；已经记着切出点的不要改写它。
   - 分支已推送过的（远端已有同名分支），压平和第 3 步的 rebase 都会改写已推送的历史：动手前先按第 5 步确认能强推，不行就停下，不要先改写。
   - 只有一个提交的不用压平，也不用做下面的核对。多个提交默认压成一个，确实包含多个互不依赖的变更时才保留多个。
   - 压平在原基点上做：先记下 `git rev-parse HEAD`（下称 `<压前提交>`），再 `git reset --soft $(git merge-base HEAD <远端>/<目标分支>)` 后重新提交；
     这个 merge-base 就是原基点，不是记着的切出点。
     不要 reset 到目标分支的最新提交，也不要另开分支再把文件拷过去——基点换了而内容没合，会悄悄撤销目标分支上的改动。
   - 压完核对压出来的那个提交的父提交仍是原基点、`git diff <压前提交> HEAD` 为空，
     任何一条不满足就 `git reset --hard <压前提交>` 退回重做。
3. **rebase 到最新的目标分支**：`git rebase <远端>/<目标分支>`。
   解冲突要把双方的改动合起来，不要一律取自己这一侧。
   rebase 后重跑构建、测试、格式检查，失败且判断不清是否本次改动引起的，停下问用户、不推送；还要改的并回原提交，不要再堆新提交。
4. **推送前预检**：工作树里没有 `.githooks/revert-gate.py`（仓库没有回退闸门）的，直接做下面的「人工核对」；有的，先确认 hook 入口、再跑预检。

   **hook 入口**：确认本 clone 装了 hook 入口。它管第 5 步推送时的自动检查，缺了不影响预检：设了 `core.hooksPath` 的只汇报，没设的补装并告知用户。
   - 设了 `core.hooksPath` 的仓库，看它指向的 `pre-push` 里有没有调用 `.githooks/hook.sh`：有就是已经接好，没有就汇报。
     这种仓库不要执行 `install.sh`，它会直接报错退出。
   - 没设 `core.hooksPath`、而 `$(git rev-parse --git-common-dir)/hooks/pre-push` 里没有
     `# revert-gate hook entry` 一行的，在仓库（或当前 worktree）根目录执行 `sh .githooks/install.sh` 补装
     并告知用户。仓库里没有 `.githooks/branches` 就加 `--pr-only`，有就不加。

   **预检**：执行下面的命令，它读的是 `<远端>/<目标分支>` 上的脚本，整条命令的退出码就是预检的退出码：

   ```bash
   s=$(git show "<远端>/<目标分支>:.githooks/revert-gate.py" 2>/dev/null) || { echo "闸门未就绪" >&2; (exit 3); } && python3 -I -c "$s" check-pr <远端>/<目标分支> <分支>
   ```

   | 退出码 | 含义 | 做什么 |
   |---|---|---|
   | 0 | 通过 | 往下做第 5 步 |
   | 1 | 查出了问题 | 按预检输出的原因：还没 rebase 的回第 3 步；撤销了已有改动的按「撤销了已有改动」处理；其它原因停下问用户 |
   | 2 | 闸门自身出错 | 汇报，再做人工核对，不当作通过 |
   | 3 或其它 | 预检跑不起来（闸门还没合进目标分支、没有 `python3` 等） | 做人工核对，不当作通过 |

   **人工核对**：逐个检查 `git log <分支记的切出点 branch.<分支>.forkPoint>..<远端>/<目标分支>` 里的提交，
   确认它们的改动在当前分支里都还在；有改动不见了，按「撤销了已有改动」处理；核对过了告知用户这次没用上闸门。

   **撤销了已有改动**（预检报的，或人工核对发现改动不见了）：先判断是不是有意删除，判断不了就问用户。
   - 出了错的（压平或解冲突丢了改动）：回到第 2 步压平前记下的提交（没压平过的，用 `git reflog` 找），重新压平并 rebase。
   - 确实要删掉切出点之后目标分支上新增内容的：先问用户，同意后用 amend 在做了这个删除的那个提交的信息里，
     为每个被撤销的提交加一行 `Reverts: <sha>`（分支已推送过的按第 5 步推送），再重跑预检；人工核对的不用重跑预检。
5. **推送**：没推过的分支 `git push -u <远端> <分支>`；推过且没改写历史的直接 `git push`；
   改写了已推送历史的用 `--force-with-lease`，但只限自己独用的分支（没有别人基于它开发；拿不准就问用户），
   且要先问用户同意。这一问在第 2 步动手改写之前就要问，不是推送时才问；不满足就停下问用户。
6. **提交 PR**：base 取 `<目标分支>`，head 取 `<分支>`。该分支已有开放的 PR 就不重建，推送已更新它；它的 base 与 `<目标分支>` 不一致时，停下问用户。
7. **清理本地**：先确认 PR 已存在（新建或已有）、分支已推到远端，没满足就不清理，汇报后结束。满足就立即清理，这是提交 PR 的一部分，不必再问：
   - 分支有自己单独的 worktree：先回到主工作副本，再 `git worktree remove`；
   - 分支停在当前所在的主工作副本里：切回目标分支（本地没有就从远端建跟踪分支）；
   - 最后 `git branch -D` 删除本地分支（它会连同该分支的 `targetBranch`、`forkPoint` 记录一起删掉）。

   清理时遇到 worktree 里有未提交或未跟踪的文件、目标分支被别的 worktree 占用而切不回去，停下来问用户，不要加 `--force`。

## PR 建好之后又冲突

本次调用结束后，目标分支又前进、PR 报冲突，用户再来处理时：分支与 PR 由用户指定，没指定就问。先告知用户 PR 有冲突，需要解冲突就问用户用 merge 还是 rebase
（rebase 要强推，选了就是同意；独用检查按第 5 步）。PR 还没合并、远端分支还在时，分支与记录已在第 7 步清掉，
目标分支取 PR 的 base（用户另有指定的除外）。先从远端重建：`git fetch` 后 `git switch -c <分支> <远端>/<分支>`，重新记 `targetBranch`，切出点用
`git merge-base HEAD <远端>/<目标分支>` 现算后记下。选 merge 的，把 `<远端>/<目标分支>` 合进分支、普通推送；
选 rebase 的，同第 3 步，推送按第 5 步。解冲突同第 3 步，解完重跑第 4 步的预检，推送后按第 7 步清理本地。

## 撰写身份

适用于所有提交信息（含 amend 的）、PR 标题与描述，语言跟随仓库历史：

- 不留任何 AI 痕迹：不写 `Co-Authored-By`、不写「Generated with …」、不提 AI 协助。
