# worktree 分支的操作

分支合并回哪、从哪切出，从它自己的 git config 读（怎么记见「## 创建」）：目标分支（`targetBranch`）读不出来就汇报，不要按分支名猜；切出点（`forkPoint`）缺失、或指定的分支所在 worktree 没有分支（临时的 `--detach` worktree）也汇报，不要自己估一个补上。
下文「分支」指在 worktree 里开发的分支，「目标分支」指它合回去的分支。出错或卡住时「汇报」：停下并告诉用户、等指示；需要用户选择或同意时「问用户」。
没指定是哪个分支时：在某个 worktree 里调用，就是该 worktree 的分支；在主工作副本里调用，只有一个 worktree 分支就是它，有多个就问用户，一个都没有就汇报。
下文的操作分两处做：对齐远程、合并与推送目标分支在目标分支所在的工作副本（仓库原目录，下称主工作副本）里，
压平、rebase 与验证在分支自己的 worktree 里。

## 创建

- 目标分支是创建 worktree 时当前工作副本检出的分支，不一定是主分支；当前是 detached HEAD、没有检出分支时汇报，不要猜。
- 分支名按变更类型取 `feat/`、`fix/`、`refactor/`、`docs/` 前缀；worktree 放在仓库内的 `.worktrees/<分支短名>/`，分支短名是分支名去掉这类前缀的部分（`feat/login-retry` 放在 `.worktrees/login-retry/`）。
- 只为验证而临时注入代码时，可另开不建分支的临时 worktree（`git worktree add --detach`），里面的改动不提交、验完即删。
- 创建 worktree 前，先看仓库有没有 `.githooks/`：没有就视为不用闸门，跳过这条和合并前的闸门预检；有就补装闸门（它的 hook 与常驻守护分支配置都在各 clone 自己的 `.git/` 里，不随仓库带来）：
  - 在主工作副本根目录执行 `git config --get-all revert-gate.branch >/dev/null || sh .githooks/install.sh $(git config core.hooksPath >/dev/null && echo --branches-only)`：已装过的什么也不做，没装的按随仓库提交的 `.githooks/branches` 补装。
  - 设了 `core.hooksPath` 的仓库由 husky 等体系接管 hook，命令只补写常驻守护分支（该仓库里始终受闸门守护的分支，通常是主分支，列在 `.githooks/branches` 里）配置。
  - 命令实际执行了安装的要告知用户；报错时汇报，不自行处理。
- 补装之后按下面的顺序创建：
  1. 按「## 对齐远程的目标分支」把目标分支对齐；领先远端（有未推送的提交）是正常的，不用处理。对齐不了就汇报，不要在旧位置上切出。
  2. 从对齐后的目标分支建分支和 worktree。
  3. 记下目标分支和切出点：`git config branch.<分支>.targetBranch <目标分支>`、`git config branch.<分支>.forkPoint $(git rev-parse <目标分支>)`。切出点由闸门读取，本文件只负责维护。只有对齐远程时的 `--onto` 搬动后才更新（规则见那里），普通 rebase 不更新：旧切出点仍在目标分支的历史里。

## 对齐远程的目标分支

- 三处要对齐：切出前、本地合并前、推送目标分支被拒后。在主工作副本里 `git fetch`（要快进或 rebase、而它有未提交的改动，先汇报），按目标分支与上游（`<目标分支>@{u}`）的关系处理：
  - 落后（本地没有未推送的提交）：`git merge --ff-only <目标分支>@{u}` 快进。
  - 分叉（本地有未推送的提交、远程也有新提交）：先 `git rev-parse <目标分支>` 记下旧位置（下面搬其它分支要用），再 `git rebase <目标分支>@{u}`，把本地未推送的提交垫到最新远程之上，解冲突同「压平与 rebase」。
    - rebase 后在主工作副本里重新跑构建、测试、格式检查，通过才算对齐；不通过汇报，不要继续。
    - 目标分支上原有的未推送提交已被改写，从它们之上切出的分支里还是改写前的那份，直接 rebase 会把它们再搬一遍，要逐个搬：
      - 找这样的分支：`git config --get-regexp '^branch\..*\.targetBranch$'` 里值等于该目标分支的，worktree 路径用 `git worktree list` 查；该 worktree 有未提交的改动时先问用户。
      - 搬：到它自己的 worktree 里执行 `git rebase --onto <目标分支> <旧位置>`，只搬分支自己的提交。
      - 搬完把它的切出点更新为 `git merge-base HEAD <目标分支>`（这是唯一更新切出点的情形）：旧切出点指向被改写的旧提交，留着会让回退核对把它们算进去。
  - 没有上游：只有一个远端有同名分支（`<远端>/<目标分支>`）就用它代替上游，不用设上游；多个远端都有时，问用户用哪个，再 `git branch -u <远端>/<目标分支>` 设好上游；都没有就跳过。

- **合并前才发现要对齐**：分叉的，上面的 `--onto` 已把这个分支一并搬过；只是落后快进的，再对分支做普通 `git rebase <目标分支>`；之后按「## 合并」里「分支凡重新 rebase 过」那一条走。
- **推送被拒后才发现要对齐**：被合并的那个分支已经删掉了，别处还在的、从目标分支切出的分支按上面的 `--onto` 搬。

## 压平与 rebase

- 开发期间的提交不必讲究，合并前压平：目标分支上的每个提交都要能独立说明、独立回滚。分支只做了一件事就压成一个提交；确实包含多个互不依赖的变更才保留多个，拆分点落在同一个文件内部的，合成一个提交。提交信息描述最终状态，不复述过程（不写「修复上一个提交」「按反馈调整」），语言跟随仓库历史。
- 压平一律在原基点上做：`git reset --soft $(git merge-base HEAD <目标分支>)` 后重新提交。不要 reset 到 `<目标分支>` 等更新的提交，也不要另开分支再把文件拷过去——基点换了而内容没合，旧代码就会被当成新改动，悄悄撤销基点之后目标分支上的改动。压平前先记下 `git rev-parse HEAD`；压完核对压出来的那个提交的父提交仍是原基点、`git diff <记下的提交> HEAD` 为空，任何一条不满足就 `git reset --hard <记下的提交>` 退回重做。
- 压平后再 `git rebase <目标分支>`，一个提交只解一次冲突。解冲突要把双方的改动合起来，不要一律取自己这一侧；拿不准怎么合就问用户。rebase 后还要改的，并回原提交，不要再堆新提交。
- 自己独用的分支（远端上没有别人的提交；拿不准就问用户）已推送过的，压平后需要用 `--force-with-lease` 强制推送，推之前先向用户确认。
- 已推送、却不是独用的分支（远端有别人的提交）：不压平、不强推，汇报，由用户定。

## 回退与撤销

- 仓库装有回退闸门（`.githooks/revert-gate.py`）：受守护的分支（各分支 `targetBranch` 记下的目标分支，以及闸门的常驻守护分支）移动时，本地 merge / commit / reset 与 push 都会被自动检查，拒绝改写已发布的历史、以及撤销该分支已有改动的更新。
- 闸门报撤销了已有改动的，是压平或解冲突出了错：合并前报的，回分支重做；对齐远程时 rebase 被拦的，`git rebase --abort` 后重新 rebase；推送目标分支时才报的，在主工作副本里补提交恢复被撤销的改动，不要 reset 目标分支；推送开发分支被拦的，回分支重新压平，不要用 `--no-verify` 绕过。
- reset 被拦时，暂存区（`--hard` 还有工作树）已被改成目标位置的内容，`--hard` 用 `git reset --merge`、`--mixed` 用 `git reset` 复原。
- 确要撤销某个提交，先问用户，同意后在主工作副本里用 `git revert`，或在提交信息里加一行 `Reverts: <sha>` 向闸门声明是有意撤销；不要在目标分支上用 reset、amend 去掉已推送的提交。

## 合并

顺序：对齐远程 → 压平 → rebase → 验证 → 向用户确认 → 闸门预检 → `merge --ff-only` → 清理。验证是在分支的 worktree 里跑构建、测试、格式检查，不通过汇报、不合并。

- 项目改走 PR 合并的（用户说明，或仓库文档约定）：对齐、压平、rebase、验证照做，到向用户确认为止；不在本流程里提 PR，也不在本地 merge、不跑预检，提 PR 与之后的清理交给 `git-pr` skill，没装按用户指示。
- 本地合并前必须确认：前面各步都已做完（历史压不了的见「压平与 rebase」里「已推送、却不是独用的分支」那一条）；主工作副本仍在目标分支上（不在就切回；有未提交的改动切不回去就汇报）；已向用户确认（给用户看最终的提交列表与验证结果）；闸门预检通过（仓库没有 `.githooks/` 的跳过这项；merge 被闸门拦下时主工作副本已被写成分支内容，要 `git reset --merge` 复原，所以先预检）。闸门预检在主工作副本里执行下面的命令，退出码为 0 才算通过：

  ```bash
  b=$(git config --get-all revert-gate.branch | head -n1); s=$(git show "refs/heads/$b:.githooks/revert-gate.py" 2>/dev/null) || { echo "闸门未就绪" >&2; (exit 3); } && python3 -I -c "$s" check <目标分支> <分支>
  ```

  - 退出码 3（输出「闸门未就绪」）：依次试——(1) 按创建 worktree 时的补装那步补装，再重跑；(2) 仍报 3，且常驻守护分支的第一个（`git config --get-all revert-gate.branch` 第一行）在本 clone 没有本地分支（新 clone 里它可能只在远端），先 `git branch <该分支> <远端>/<该分支>` 建出来，再重跑；(3) 还报就汇报（可能是本 clone 未装，或主分支上还没提交闸门脚本），不当作通过。
  - 退出码 1：查出了问题，照提示处理；报撤销了已有改动的，按「## 回退与撤销」里「闸门报撤销了已有改动」那一条回分支重新压平；报目标分支落后或分叉于远程（以最近一次 fetch 为准）的，按「## 对齐远程的目标分支」处理。
  - 退出码 2：闸门自身出错，汇报，不当作通过。
- 本地合并在主工作副本里用 `git merge --ff-only <分支>`，快进失败说明目标分支又前进了或 rebase 没做干净：回分支重新 rebase，按下一条走完验证与确认，重跑预检再合。
- 分支凡重新 rebase 过（含对齐远程之后），带进来的新代码没参与过之前的验证，按下面走：
  - 先重跑验证（不通过的处理同上）；
  - 通过后，解过冲突的、或提交列表变了的（如重新压平）重新向用户确认，其余（分支自己的提交内容没变）沿用原确认；
  - 再重跑预检、合并。
- 确认合并成功（`merge --ff-only` 退出码为 0）后先回到主工作副本，立即 `git worktree remove` 掉该 worktree 并删除分支（失败就汇报，不要加 `--force`；不动远端分支）——这是合并动作的一部分，不必再问。不自动推送目标分支，用户要推再推。

## 推送

- 推送目标分支被拒（远端报非快进，或 pre-push 报远程有本地没有的提交）时不要强推，按「## 对齐远程的目标分支」里推送被拒后那条处理，对齐并验证通过后再重新推送。
