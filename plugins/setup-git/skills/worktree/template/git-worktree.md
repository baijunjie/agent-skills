# worktree 分支的操作

分支合并回哪、从哪切出，从它自己的 git config 读（怎么记见「## 创建」）；读不出来就汇报，不要按分支名猜。
下文的操作分两处做：对齐远程、合并与推送目标分支在检出目标分支的那个工作副本（下称主工作副本）里，
压平、rebase 与验证在分支自己的 worktree 里。

## 创建

- 分支名按变更类型取 `feat/`、`fix/`、`refactor/`、`docs/` 前缀；worktree 放在仓库内的 `.worktrees/<分支短名>/`，分支短名是分支名去掉这类前缀的部分（`feat/login-retry` 放在 `.worktrees/login-retry/`）。
- 建好分支就记下目标分支和切出点：`git config branch.<分支>.worktreeTarget <目标分支>`、`git config branch.<分支>.worktreeBase $(git rev-parse <目标分支>)`——换了会话也查得到该合并回哪；合并前的回退核对靠前者认出目标分支，靠后者把核对范围覆盖到切出点之后的全部提交。之后 rebase 也不要改切出点，删除分支时这两条会随之清掉。
- 创建 worktree 前，在主工作副本根目录执行 `git config --get-all revert-gate.branch >/dev/null || sh .githooks/install.sh $(git config core.hooksPath >/dev/null && echo --branches-only)`：回退闸门的 hook 与常驻守护分支配置都在各 clone 自己的 `.git/` 里，不随仓库带来，本 clone 没装时它按随仓库提交的 `.githooks/branches` 补装；设了 `core.hooksPath` 的仓库由 husky 等体系接管 hook，只补写常驻守护分支配置。补装了要告知用户；报错时汇报，不自行处理。

## 对齐远程的目标分支

- 本地合并前先对齐远程的目标分支，再压平、rebase：在主工作副本里 `git fetch`，按目标分支与上游（`<目标分支>@{u}`）的关系处理：
  - 落后（本地没有未推送的提交）：`git merge --ff-only <目标分支>@{u}` 快进。
  - 分叉（本地有未推送的提交、远程也有新提交）：`git rebase <目标分支>@{u}`，把本地未推送的提交垫到最新远程之上，解冲突要把双方的改动合起来。
    - rebase 后在主工作副本里重新跑构建、测试、格式检查，通过才算对齐。
    - 目标分支上原有的未推送提交已被改写，从它们之上切出的分支里还是改写前的那份，直接 rebase 会把它们再搬一遍：对每个这样的分支，到它自己的 worktree 里执行 `git rebase --onto <目标分支> <旧位置>`，只搬分支自己的提交。旧位置在 rebase 完成后就是 `<目标分支>@{1}`，目标分支之后再移动就不是了，所以先 `git rev-parse <目标分支>` 记下。
  - 没有上游：用远端唯一的同名分支（`<远端>/<目标分支>`）代替上游；远端有多个同名分支时，先 `git branch -u <远端>/<目标分支>` 设好上游；远端也没有同名分支就跳过。

  合并前或推送被拒后才发现要对齐的，对齐后同样把分支重新 rebase 到目标分支（分叉时用上面的 `--onto`），再回到合并前的确认。

## 压平与 rebase

- 开发期间的提交不必讲究，合并前压平：目标分支上的每个提交都要能独立说明、独立回滚。分支只做了一件事就压成一个提交；确实包含多个互不依赖的变更才保留多个，但拆分点落在同一个文件内部时不要硬拆。提交信息描述最终状态，不复述过程（不写「修复上一个提交」「按反馈调整」），语言跟随仓库历史。
- 压平一律在原基点上做：`git reset --soft $(git merge-base HEAD <目标分支>)` 后重新提交。不要 reset 到 `<目标分支>` 等更新的提交，也不要另开分支再把文件拷过去——基点换了而内容没合，旧代码就会被当成新改动，悄悄撤销基点之后目标分支上的改动。压完核对第一个提交的父提交仍是原基点、工作树与压平前完全一致，任何一条不满足就退回重做。
- 压平后再 `git rebase <目标分支>`，一个提交只解一次冲突。解冲突要把双方的改动合起来，不要一律取自己这一侧——那等于撤销目标分支上的对应改动。rebase 后还要改的，并回原提交，不要再堆新提交。
- 自己独用的分支压平后需要强制推送，推之前先向用户确认。
- 分支若又是别的 worktree 分支的目标分支（嵌套），要等那些子分支都合回并删除后再压平；嵌套中作为目标分支的分支推送过的，不能再压平强推。装有回退闸门时，这两种多半会被拒，但不要靠闸门拦，按本条自己遵守。

## 回退核对

- 仓库装有回退闸门（`.githooks/revert-gate.py`）：受守护的分支（各分支 `worktreeTarget` 记下的目标分支，以及闸门的常驻守护分支，通常是主分支）移动时，本地 merge / commit / reset 与 push 都会被自动检查，拒绝改写已发布的历史、以及撤销该分支已有改动的更新。照提示处理。
- 闸门报撤销了已有改动的，是压平或解冲突出了错：合并前报的，回分支重做；对齐远程时 rebase 被拦的，`git rebase --abort` 后重新 rebase；推送时才报的，在主工作副本里补提交恢复被撤销的改动，不要 reset 目标分支。
- reset 被拦时，暂存区（`--hard` 还有工作树）已被改成目标位置的内容，`--hard` 用 `git reset --merge`、`--mixed` 用 `git reset` 复原。
- 确要撤销某个提交，先问用户，同意后用 `git revert` 或在提交信息里加一行 `Reverts: <sha>`，不要在目标分支上用 reset、amend 去掉提交。

## 合并

- 本地合并前必须确认：功能已验证；历史已压平并 rebase 到最新的目标分支；主工作副本仍在目标分支上；已向用户确认；闸门预检通过（merge 被闸门拦下时主工作副本已被写成分支内容，要 `git reset --merge` 复原，所以先预检）。闸门预检执行下面的命令，退出码为 0 才算通过：

  ```bash
  b=$(git config --get-all revert-gate.branch | head -n1); s=$(git show "refs/heads/$b:.githooks/revert-gate.py" 2>/dev/null) || { echo "闸门未就绪" >&2; false; } && python3 -I -c "$s" check <目标分支> <分支>
  ```

  报「闸门未就绪」，先按创建 worktree 前那条补装再重跑；常驻守护分支的第一个（`git config --get-all revert-gate.branch` 第一行）在本 clone 没有本地分支时（新 clone 里它可能只在远端），先 `git branch <该分支> <远端>/<该分支>` 建本地分支再重跑；仍报，汇报（可能是本 clone 未装，或主分支上还没提交闸门脚本），不当作通过，也不当作查出回退。
  其余的退出码 1 是查出了问题，照提示处理；报目标分支落后或分叉于远程（以最近一次 fetch 为准）的，按上面的对齐远程那条处理。
  退出码 2 是闸门自身出错：同样汇报，不当作通过。
- 本地合并在主工作副本里用 `git merge --ff-only <分支>`，快进失败说明目标分支又前进了或 rebase 没做干净：回分支重新 rebase、重跑预检再合，不要退回裸 merge。
- 分支凡重新 rebase 过（含对齐远程之后），没解冲突时沿用原确认，解过冲突要重新确认。
- rebase 带进来的新代码没参与过之前的验证，rebase 后在 worktree 里重跑构建、测试、格式检查，通过后再做合并前的确认、再合并。
- 确认合并成功（`merge --ff-only` 退出码为 0、目标分支已指向该分支的提交）后立即 `git worktree remove` 掉该 worktree 并删除分支——这是合并动作的一部分，不必再问。

## 推送

- 推送目标分支被拒（远端报非快进，或 pre-push 报远程有本地没有的提交）时不要强推：先 `git fetch`，按以「本地合并前先对齐远程」开头那条里分叉的做法 rebase 到上游并验证，通过再推送。
