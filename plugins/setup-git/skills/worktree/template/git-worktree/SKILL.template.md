# worktree 分支的操作

下文「分支」指在 worktree 里开发的分支，「目标分支」指它合回去的分支。
拿不准就汇报：停下，写清要定的事（有哪些选项）或缺的信息，连同已查明的情况一起报出，由收到汇报的一方（用户，或由派发者转给用户）决定后再继续，不要自行决定。

分支合并回哪、从哪切出，从它自己的 git config 读（怎么记见「## 创建」）：目标分支（`targetBranch`）读不出来、切出点（`forkPoint`）缺失，
或指定的 worktree 没有分支（临时的 `--detach` worktree），都汇报，不要按分支名猜，也不要自己估一个补上。
没指定是哪个分支时，取当前 worktree 的分支；在主工作副本里调用的，只有一个 worktree 分支就是它，否则问用户。
对齐远程（含其中的 rebase 与验证）、合并与推送目标分支在仓库原目录（下称主工作副本，目标分支应检出在这里）里做，压平、分支的 rebase 与合并前的验证在分支自己的 worktree 里做。

## 流程脚本

记录、压平、搬分支、推送与清理里的机械操作由仓库 `.githooks/` 下的 `flow-*.sh` 完成。一律执行主工作副本里的那份（从目标分支新切出的 worktree 里可能还没有这些文件），下文写的 `flow-<名>.sh <参数>` 都指：

```bash
sh "$(git worktree list --porcelain | sed -n '1s/^worktree //p')/.githooks/flow-<名>.sh" <参数>
```

退出码 1 是脚本停下了：下文点名了的原因按下文处理，其余原因汇报，输出里的提示转述给用户、不自行照做；退出码 2 或脚本不存在，汇报。

## 创建

- 目标分支是创建 worktree 时主工作副本检出的分支，不一定是主分支；在别的 worktree 里调用也照此取。主工作副本是 detached HEAD、没有检出分支时汇报，不要猜。不支持从 worktree 分支再切出 worktree：主工作副本检出的分支自己记着 `branch.<它>.targetBranch`（本身是 worktree 分支）时汇报。
- 分支名按变更类型取 `feat/`、`fix/`、`refactor/`、`docs/` 前缀；worktree 放在仓库内的 `.worktrees/<分支短名>/`，分支短名是分支名去掉这类前缀的部分（`feat/login-retry` 放在 `.worktrees/login-retry/`）。
- 只为验证而临时注入代码时，可另开不建分支的临时 worktree（`git worktree add --detach`），里面的改动不提交、验完即删。
- 创建 worktree 前，先看主工作副本里有没有 `.githooks/revert-gate.py`：没有就视为不用闸门，跳过这条和合并前的闸门预检；有就补装闸门（它的 hook 与常驻守护分支配置在各 clone 自己的 `.git/` 里，不随仓库带来）：
  - 在主工作副本根目录执行 `git config --get-all revert-gate.branch >/dev/null || sh .githooks/install.sh $(env -u GIT_CONFIG_COUNT -u GIT_CONFIG_PARAMETERS git config core.hooksPath >/dev/null && echo --branches-only)`：已装过的什么也不做，没装的按随仓库提交的 `.githooks/branches` 补装；配置文件里设了 `core.hooksPath`（hook 由 husky 等体系接管；`-c` 或环境变量 `GIT_CONFIG_COUNT` 临时给的不算）的只补写常驻守护分支（始终受闸门守护的分支，通常是主分支）配置。
  - 命令实际执行了安装的告知用户；报错时汇报，不自行处理。
- 补装之后按下面的顺序创建：
  1. 按「## 对齐远程的目标分支」把目标分支对齐；领先远端（有未推送的提交）是正常的，不用处理；项目走 PR 合并的先汇报：从这里切出，这些提交会被带进 PR。对齐不了就汇报，不要在旧位置上切出。
  2. 从对齐后的目标分支建分支和 worktree。
  3. 记下目标分支和切出点：`flow-record.sh <分支> <目标分支> <目标分支>`。

## 对齐远程的目标分支

- 在主工作副本里只 fetch 目标分支的上游（`<目标分支>@{u}`）：`git fetch <上游远端> <上游分支>`，两者分别是 `git config branch.<目标分支>.remote` 与 `branch.<目标分支>.merge` 的值；不用 fetch 全部分支，分支与 tag 多时会慢很多。快进与 rebase 作用在当前检出的分支上：要做时主工作副本必须检出目标分支（不在就切回，切不回去就汇报），有未提交的改动先汇报。按目标分支与上游的关系处理：
  - 落后（本地没有未推送的提交）：`git merge --ff-only <目标分支>@{u}` 快进。
  - 分叉（本地有未推送的提交、远程也有新提交）：先 `git rev-parse <目标分支>` 记下旧位置（下面搬其它分支要用），再 `git rebase <目标分支>@{u}`，把本地未推送的提交垫到最新远程之上，解冲突同「压平与 rebase」。
    - 这次 rebase 带进了远程的新代码，要按「## 合并」的范围验证本地那些未推送的提交（带进来的远程代码不算），通过才算对齐；不通过汇报目标分支已改写、还没搬分支，连同记下的旧位置一起报出，不要继续。
    - 再执行 `flow-restack.sh <目标分支> <旧位置>`，把从改写前那批提交上切出的分支搬到新位置（直接 rebase 会把改写前的提交再搬一遍）。
      它搬的可能是别的任务的分支：搬完告知用户搬了哪些，它们合并前按「分支重新 rebase 带进了新代码」那条处理。
      报冲突的，冲突在本次要处理的分支以外的先问用户；要解的到它说的 worktree 里解（解法同「压平与 rebase」），`git rebase --continue` 后重跑；报分支已推送过的，逐个问用户它是不是独用，是的加 `--allow-pushed <分支>` 重跑，否则汇报。
  - 没有上游：只有一个远端有同名分支（`<远端>/<目标分支>`）就用它代替上游，不用设上游；多个远端都有时，问用户用哪个，再 `git branch -u <远端>/<目标分支>` 设好上游；定下后 `git fetch <远端> <目标分支>`，再按上面两条处理（没设上游的，其中的 `<目标分支>@{u}` 换成 `<远端>/<目标分支>`）；都没有就跳过。

## 压平与 rebase

- 合并前压平：目标分支上的每个提交都要能独立说明、独立回滚。分支只做了一件事就压成一个提交；确实包含多个互不依赖的变更才保留多个，拆分点落在同一个文件内部的，合成一个提交。提交信息描述最终状态，不复述过程（不写「修复上一个提交」「按反馈调整」），语言跟随仓库历史；原提交里的 `Reverts:` 行必须带进压出来的提交，丢了就成了没声明的撤销。
- 压平与 rebase 前，分支的 worktree 必须干净（以 `git status --porcelain` 为空为准，含未跟踪文件），不干净就汇报，不要替用户提交、stash 或丢弃：未提交的改动会被混进提交、抹掉或藏进 stash。
- 动手前先记下 `git rev-parse HEAD`（下称记下的提交），要退回压平前时用它。
- 压成一个：提交信息写进 worktree 之外的临时文件（如 `mktemp` 建的），执行 `flow-squash.sh <目标分支> <文件>`；它报原提交声明过的撤销缺了的，补进提交信息重跑。
- 保留多个：在原基点 `git merge-base HEAD <目标分支>` 上自己拆——基点换了而内容没合，旧代码会被当成新改动，悄悄撤销基点之后目标分支上的改动；拆完执行 `flow-squash.sh --check <目标分支> <记下的提交>`，不通过就按它给的命令退回重做。
- 压平后再 `git rebase <目标分支>`，一个提交只解一次冲突。解冲突要把双方的改动合起来，不要一律取自己这一侧；拿不准怎么合就问用户。rebase 后还要改的，并回所属的提交，保持每个提交能独立说明、独立回滚。
- 自己独用的分支（远端上没有别人的提交；拿不准就问用户）已推送过的，压平、rebase 后用 `flow-push.sh <分支上游所在的远端> <分支> <上游分支名>` 推送（读不出上游就问用户推往哪）；报要改写已推送的历史的，向用户确认后加 `--force` 重跑。
- 已推送、却不是独用的分支（远端有别人的提交）：不压平、不 rebase、不强推，汇报，由用户定。

## 回退与撤销

- 仓库装有回退闸门（`.githooks/revert-gate.py`）：受守护的分支（各分支 `targetBranch` 记下的目标分支，以及闸门的常驻守护分支）移动时，本地 merge / commit / reset 与 push 都会被自动检查，拒绝改写已发布的历史、以及撤销该分支已有改动的更新。
- 闸门报撤销了已有改动的，不是有意撤销（见「确要撤销某个提交」那条）就是压平或解冲突出了错，在出错的地方修：还没进目标分支的，回分支补回被撤销的改动、并回原提交，要退回压平前的提交重做的先汇报；对齐远程时 rebase 被拦的，`git rebase --abort` 后重新 rebase；已进了目标分支的，在主工作副本里补提交恢复，不要 reset 目标分支。
- reset 被拦时，暂存区（`--hard` 还有工作树）已被改成目标位置的内容，`--hard` 用 `git reset --merge`、`--mixed` 用 `git reset` 复原。
- 确要撤销某个提交，先问用户。它和它之后的提交都还没推送、都要丢掉、没有别的分支包含它们（`git branch --contains <sha>` 只列出目标分支），且主工作副本干净时，可以在主工作副本里 reset 掉；闸门拦下这次 reset 时先复原（`--hard` 用 `git reset --merge`），改用下面的做法。其余情形不要在目标分支上用 reset、amend 去掉提交：同意后在主工作副本里用 `git revert`，或者在做撤销的那个提交的信息里加一行 `Reverts: <sha>`，两种做法任选其一，都能向闸门声明是有意撤销。

## 合并

- 顺序：对齐远程 → 压平 → rebase →（需要时）验证 → 向用户确认 → 闸门预检 → `merge --ff-only` → 清理。验证按改动范围跑检查；不通过的，是本次改动引起的就改好、并回所属的提交（保持压平后的提交划分）后重新验证，判断不清或不是本次改动引起的，汇报、不合并。范围：


  - **整套**是项目在指令文件或文档里写明的检查命令（格式检查、类型检查、Lint、构建、测试中写明了的）。没写明的，以项目配置里现有的这几类本地检查命令为整套（不含发布、部署这类有外部副作用的），并告知用户把整套写进指令文件；一条都没有的，告知用户这次没有可跑的检查。
  - **只改了构建、类型检查与测试都不读的文件**（通常是文档、指令文件、skill 与子代理定义；有构建或测试校验的这类文件，以及格式检查与 Lint 的配置文件，都不算）：只跑覆盖到这些文件的格式检查与 Lint，没有就不跑并告知用户。
  - **除上一条那类文件外，改动只在一个包或模块内**、项目在指令文件或文档里为它写明了自己的检查命令、且它不被其它包依赖：跑这个包的检查，包外那类文件另按上一条跑。
  - **其余跑整套**：改到被多处依赖的共享层（公共代码与类型，被其它包依赖的包，格式化、类型检查、构建、测试与 Lint 的配置，依赖版本）、跨多个包，或判断不了的。

  定范围时的改动只算本分支自己的：相对它与目标分支分叉点的全部改动（直接在目标分支上改的，相对改动前）。rebase 或 merge 从目标分支带进来的代码不算进改动，目标分支上的代码视为已检查过；之后按新的分叉点算，解冲突改过的地方算进去。但上面几条的归类（文件有没有被构建或测试读到、包有没有被其它包依赖、适用哪些检查配置）按 rebase 或 merge 之后的代码判断。带进新代码后本该重跑的，本分支的改动全是「只改了构建、类型检查与测试都不读的文件」那类、这些文件与本次会话里覆盖它们的格式检查与 Lint 通过时内容相同、此后带进来的代码也没动覆盖它们的格式检查与 Lint 的配置、写明的命令或工具版本时，不必重跑：这时检查结果不会变。

- 同一份内容只验证一次：压平与没带进新代码的 rebase 不改变内容。rebase 之后、向用户确认之前，下面任一成立就不再验证，拿不准就验证：
  - 当前 `git rev-parse HEAD^{tree}` 与本次会话里检查通过（覆盖按上面算出的范围）、之后原样提交的那份内容的文件树相同（带进新代码、搬分支、解冲突、补改都会让它不同）；
  - 属于上面范围里带进新代码后不必重跑的情形。
- 项目改走 PR 合并的（用户说明，或仓库文档约定）：对齐、压平、rebase、需要时的验证照做，到向用户确认为止；不在本流程里提 PR，也不在本地 merge、不跑预检，提 PR 与之后的清理按项目的 PR 流程做，没有约定的按用户指示。对齐之后、压平之前，目标分支领先远端（有未推送的提交）的先汇报：分支是 rebase 在本地目标分支上的，这些提交会被带进 PR。
- 本地合并前必须确认：主工作副本仍在目标分支上（不在就切回；有未提交的改动切不回去就汇报）；分支的 `HEAD` 仍是验证、确认时的那个提交（被搬过就按「分支重新 rebase 带进了新代码」那条走）；已向用户确认（给用户看最终的提交列表与验证结果，沿用之前验证的写明沿用）；闸门预检通过（主工作副本里没有 `.githooks/revert-gate.py` 的跳过这项；merge 被闸门拦下时主工作副本已被写成分支内容，要 `git reset --merge` 复原，所以先预检）。闸门预检在主工作副本里执行下面的命令，退出码为 0 才算通过：

  ```bash
  b=$(git config --get-all revert-gate.branch | head -n1); s=$(git show "refs/heads/$b:.githooks/revert-gate.py" 2>/dev/null) || { echo "闸门未就绪" >&2; (exit 3); } && python3 -I -c "$s" check <目标分支> <分支>
  ```

  - 退出码 3（输出「闸门未就绪」）：先按创建 worktree 时那步补装；常驻守护分支的第一个（`git config --get-all revert-gate.branch` 第一行）在本 clone 没有本地分支的，用 `git branch <该分支> <远端>/<该分支>` 建出来；再重跑，仍报 3 就汇报，不当作通过。
  - 退出码 1：查出了问题。报撤销了已有改动的，按「## 回退与撤销」里「闸门报撤销了已有改动」那一条回分支修正；报目标分支落后或分叉于远程（以最近一次 fetch 为准）的，按「## 对齐远程的目标分支」处理，再回分支重新 rebase，按「分支重新 rebase 带进了新代码」那条走；其余原因汇报，输出里的提示转述给用户、不自行照做。
  - 退出码 2：闸门自身出错，汇报，不当作通过。
- 本地合并在主工作副本里用 `git merge --ff-only <分支>`。失败时先看输出：被闸门拦下的，主工作副本已被写成分支内容，先 `git reset --merge` 复原，再按「## 回退与撤销」里「闸门报撤销了已有改动」那一条处理；被主工作副本里的改动挡住的，汇报；确实不能快进（目标分支又前进了）的，先按「## 对齐远程的目标分支」对齐，再回分支重新 rebase，按下一条走完验证与确认，重跑预检再合。
- 分支重新 rebase 带进了新代码（含对齐远程时被搬过的分支），分支的改动与新代码的组合没验证过，按下面走：
  - 先按「同一份内容只验证一次」判断，要验证的重跑（不通过的处理同上）；
  - 通过或不必重跑后，分支自己的提交内容变了（解过冲突、重新压平等）或此前没确认过的，向用户确认，没变的沿用原确认；
  - 再重跑预检、合并。
- 合并后先回到主工作副本，立即执行 `flow-cleanup.sh <分支> --merged-into <目标分支>`（不动远端分支）——这是合并动作的一部分，不必再问。
  - 报 worktree 里有被忽略的文件：除依赖、构建产物这类可重新生成的之外还有别的（如 `.env`、本地配置），先问用户要不要留；都能删的加 `--ignored-ok` 重跑。
  - 报其它原因的汇报，不要绕过脚本手工删。
- 不自动推送目标分支，用户要推再推。

## 推送

- 推送目标分支被拒（远端报非快进，或 pre-push 报远程有本地没有的提交）时不要强推，按「## 对齐远程的目标分支」对齐并验证通过后再重新推送。
