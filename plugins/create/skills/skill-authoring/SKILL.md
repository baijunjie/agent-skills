# Skill 编写规范

Skill 是给 agent 的**规则**，不是操作手册。
判据：**agent 自己推不出来、又长期成立的，才写。**

skill 分两种：**安装器**往项目或用户配置里写文件，要的是确定性结果；**应用 skill** 在运行时指导 agent 做事。安装器装出的 skill、子代理定义、写进指令文件的规则都按应用 skill 写。

## 只写这些

分五类，其余细节交给 agent 判断：

| 类 | 写什么 |
|---|---|
| 事实与前提 | 反直觉的事实、隐蔽的前提、容易踩空的判定条件 |
| 处理原则 | 判断标准与取舍原则，让 agent 在没写到的情形里也知道往哪走 |
| 边界 | 只写死违反了会不可逆、或做错了难发现的约束；其余一律不写死 |
| 兜底 | 每份应用 skill 写一句「拿不准就汇报」（管日常行为的常驻规则——如子代理分派规则、输出风格——不写，免得为日常小决定停下），接住原则推不出、边界没覆盖的情形；无人值守运行的写明兜底方式（如记下后停止）；安装器确定不了产物时汇报并停下，不猜 |
| 必要的动作与顺序 | agent 推不出的动作与顺序，不受「边界」那行「只写死不可逆、难发现的」限制。安装器里决定产物内容的命令与步骤照写，不放宽；按现状分支时每个分支的这类命令照写，不写成 shell 的 if |

## 不写这些

- **会随代码改动失效的内容** —— 不为了让 agent 学写法而指向代码或文件（「见 `xxx.ts`」「照 `xxx` 目录的写法」），需要的知识直接写进正文。项目约定、skill 自己的产物位置、约定的文件位置照写；一起分发的模板、脚本可以引用（安装器指同一 plugin 内的，装出的 skill 指跟它一起装出去的）。
- **其它 skill 的名字** —— 每个 skill 都要能单独安装、单独工作，提到别处的规范时写成能力或约定本身（「项目有自己的文档规范时按它的」）；**用户明确要求把两个 skill 串成链路时才点名**。安装器提到它自己安装的东西、skill 派发同一安装器装出的子代理不在此列；改写时已有的点名视为用户要求过，保留。
- **工具缺陷与环境怪癖** —— 只在它影响做法时写，并写成约束（「改用 `--replace` 重新渲染，不要先删再写」），不写成缺陷描述。
- agent 从工具输出、报错信息、常识就能得到的内容——**包括罗列它自己有哪些工具、能力边界在哪**；需要某类动作时写动作本身（「让用户从选项里点选」），不点工具名
- 别处已有规范的复述 —— 「别处」只指 agent 运行时一定拿得到的来源（指令文件、项目的文档规范、公开标准、工具自带文档），写成约定（「按项目的 X 规范」）；只存在于代码、仓库现状或其它 skill 里的知识，必需的部分写进正文
- 宿主差异 —— 应用 skill 里不写：有安装器的由它按宿主装出对应内容，没有的写成宿主无关的动作；只在某一宿主运行的 skill 除外
- 铺陈式解释（「理由很直接…」「这是最常见的失误…」）—— 规则本身说清了就不解释；能帮 agent 推到没写到的情形的「为了保护什么」，并进原则写成半句
- 变更历史、对旧版本的迁移 / 兼容说明，包括「旧版装过的先删 X」这类清理命令 —— 重装按当前版本整体覆盖，不需要
- 单次任务里的特例、临时变量名、示例代码片段 —— 安装器的命令不在此列

## 不写情形清单

- 不为每种情形补细则：细则越补，边界情形越多，规则之间开始互相矛盾
- 发现没覆盖的情形，先问原则能不能推出、兜底能不能接住；能就不补，不能再判断该补原则还是补边界
- 修订时补一条规则又带出新的含糊处，说明在往细则方向走，退回原则层重写，不要继续打补丁
- 判断不了某条该不该写、属于哪一类，汇报

## 写法

- **步骤只留动作，判断留给 agent。** 不要把一次成功的操作过程逐步固化成脚本（安装器决定产物内容的命令除外）。
- 一条规则一行。有条件分支时先试着合成一条原则；合并不了、按条件走不同方向的，用「条件 | 做法」表格，不用段落。
- 边界用祈使句写死：「必须」「不要」；顺序写成「先…再…」；原则写成判断方向：「优先 X」「以 Y 为准」「X 与 Y 冲突时取 X」。都不用「建议」「可以考虑」。
- `description` 只为触发服务，模型靠它决定是否调用：一句话说它解决什么问题，加上 agent 该想到它的情形与用户的典型说法；不复述步骤与规则，那些只写在正文。只能手动调用的（如安装器），description 是给用户挑选时看的一句话：装出或做成什么、用于什么场景。
- SKILL.md 的正确性不依赖 `name`、`description` 以外的 frontmatter，其它字段只做调用控制；子代理定义的 description 同理，写「什么时候派给它」，工具白名单、模型等字段按宿主格式照写，正文不重复。
- 篇幅是信号。明显变长通常意味着混进了上面「不写这些」里的东西，回头砍。

## 自检

写完逐条问：

1. 这条 agent 自己想不到吗？想得到就删（兜底句、安装器决定产物内容的命令除外）。
2. 代码改了这条还成立吗？不成立说明它是代码引用，或把临时缺陷写成了描述而不是约束。
3. 这条不是边界、也不是必要的动作与顺序，却在替 agent 做决定？放宽成判断标准。
4. 这条属于「只写这些」的哪一类？哪类都不是的就是情形细则，删掉，确认原则或兜底接得住。
