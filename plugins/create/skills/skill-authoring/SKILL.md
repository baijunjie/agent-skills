# Skill 编写规范

判据：**agent 自己推不出来、又长期成立的，才写。**

先定类型，再按对应的那节写：

| 类型 | 正文是什么 | 只写什么 |
|---|---|---|
| 规范型 | 规则：什么对什么错、冲突时取谁，怎么做到由 agent 按情形定 | 规则本身，加规则判不出来时的判例；不写操作教程 |
| 教程型 | 流程：按什么顺序做什么，判断点在哪里分叉 | 操作的顺序与步骤，以及不同场景下的分叉；不复述知识 |

一份 skill 按主用途定一类，整份按那一类写；两样都要的拆成两份 skill。
类型按正文实际写的是什么定，与这份 skill 在项目里属于哪种业务类别无关。装出去的 skill、子代理定义、写进指令文件的规则，各按自己属于哪一类写。
拿不准属于哪一类、或某条该不该写、属于哪一项，汇报。

## 两类都写这些

分五项，其余细节交给 agent 判断：

| 项 | 写什么 |
|---|---|
| 事实与前提 | 反直觉的事实、隐蔽的前提、容易踩空的判定条件 |
| 处理原则 | 判断标准与取舍原则，让 agent 在没写到的情形里也知道往哪走 |
| 作用域 | 每条规则写明它管哪些对象、在什么条件下成立；与别处的规则共管同一对象时，在更一般的那条里点明例外归谁管，不靠两处各写一半——两处各写一半就会读出两种相反做法 |
| 边界 | 限制 agent 动作的硬约束只写两种：违反了不可逆；正常流程里没人会去查，要等用户碰到。构建、测试、复核会查到的不算，写成原则——判的是有没有人会去查，不是能不能查出来。陈述知识与约定的规则不是动作约束，不走这道闸 |
| 兜底 | 原则推不出、规则没覆盖的情形要有去处：有人看着的写一句「拿不准就汇报」，无人值守运行的写明兜底方式（如记下后停止）。管日常行为的常驻规则（子代理分派规则、输出风格）不写，免得为日常小决定停下 |

## 两类都不写这些

- **会随代码改动失效的内容** —— 不为了让 agent 学写法而指向代码或文件（「见 `xxx.ts`」「照 `xxx` 目录的写法」），需要的知识直接写进正文。项目约定、skill 自己的产物位置、约定的文件位置照写；一起分发的模板、脚本可以引用：各引用与自己一起分发、一起装出去的那一份。
- **其它 skill 的名字** —— 每个 skill 都要能单独安装、单独工作，提到别处的规范时写成能力或约定本身（「项目有自己的文档规范时按它的」）；**用户明确要求把两个 skill 串成链路时才点名**。提到自己装出去的东西、派发跟自己一起装出去的子代理不在此列；改写时已有的点名视为用户要求过，保留。
- **工具缺陷与环境怪癖** —— 只在它影响做法时写，并写成约束（「改用 `--replace` 重新渲染，不要先删再写」），不写成缺陷描述。
- agent 从工具输出、报错信息、常识就能得到的内容 —— 包括罗列它自己有哪些工具、能力边界在哪；需要某类动作时写动作本身（「让用户从选项里点选」），不点工具名。
- 别处已有规范的复述 —— 「别处」只指 agent 运行时一定拿得到的来源（指令文件、项目的文档规范、公开标准、工具自带文档），写成约定（「按项目的 X 规范」）；只存在于代码、仓库现状或其它 skill 里的知识，必需的部分写进正文。
- 宿主差异 —— 运行时读的正文里不写：要按宿主给出不同内容的，在生成或装出它的那一步按宿主产出，没有那一步的写成宿主无关的动作；只在某一宿主运行的 skill 除外。
- 铺陈式解释（「理由很直接…」「这是最常见的失误…」）—— 规则本身说清了就不解释；能帮 agent 推到没写到的情形的「为了保护什么」，并进原则写成半句。
- 变更历史、对旧版本的迁移 / 兼容说明，包括「旧版装过的先删 X」这类清理命令 —— 重装按当前版本整体覆盖，不需要。
- 单次任务里的特例、临时变量名、示例代码片段 —— 规范型的判例、教程型里决定产物内容的命令不在此列。
- 情形细则 —— 细则越补，边界情形越多，规则之间开始互相矛盾。发现没覆盖的情形，先问原则能不能推出、兜底能不能接住；能就不补，不能再判断该补原则、补判例还是补一支分叉。补了一条又带出新的含糊处，说明在往细则方向走，退回原则层重写，不要继续打补丁。

## 规范型

- 只陈述规则，不写步骤、不写命令：怎么做到由 agent 按情形定。
- 规则本身判不出来的典型情形才补**判例**，用「不要 | 要」「情形 | 写法」这类表格，不穷举。
- 规则之外的取舍与方向写成原则，不替 agent 做本该按情形判断的决定。

## 教程型

- 动作与顺序照写，不受「边界」那项只写死两种情况的限制；决定产物内容的命令与步骤照写，不放宽。
- 其余步骤只留动作，判断留给 agent：不要把一次成功的操作过程逐步固化成脚本。
- **分叉逐支写**：按现状、宿主、作用域分叉时，每支写明判断条件、这一支做什么、装出什么。不把「走哪一支」的判断塞进命令里交给解释器自己选——那样 agent 不知道实际走了哪一支、也报不出来，SKILL.md 也不再说明每种状态装出什么。命令块内部为取环境变量、路径做的回退不在此列，它不改变产物。
- 按步骤与现状确定不了要做什么、写到哪，汇报并停下，不猜。

## 写法

- 一条规则一行。有条件分支时先试着合成一条原则；合并不了、按条件走不同方向的，用「条件 | 做法」表格，不用段落。
- 边界用祈使句写死：「必须」「不要」；顺序写成「先…再…」；原则写成判断方向：「优先 X」「以 Y 为准」「X 与 Y 冲突时取 X」。都不用「建议」「可以考虑」。
- `description` 只为触发服务，模型靠它决定是否调用：一句话说它解决什么问题，加上 agent 该想到它的情形与用户的典型说法；不复述步骤与规则，那些只写在正文。只能手动调用的，description 是给用户挑选时看的一句话：装出或做成什么、用于什么场景。
- SKILL.md 的正确性不依赖 `name`、`description` 以外的 frontmatter，其它字段只做调用控制；子代理定义的 description 同理，写「什么时候派给它」，工具白名单、模型等字段按宿主格式照写，正文不重复。
- 篇幅是信号。明显变长通常意味着混进了「两类都不写这些」里的东西，回头砍。

## 自检

写完逐条问：

1. 这条 agent 自己想不到吗？想得到就删（兜底句、教程型里决定产物内容的命令除外）。
2. 代码改了这条还成立吗？不成立说明它是代码引用，或把临时缺陷写成了描述而不是约束。
3. 这条写明了管什么吗？别处还有规则管同一对象吗？有就在更一般的那条里点明例外归谁管。
4. 这条在限制一个动作，却既不是不可逆、也不是正常流程里没人会去查的？放宽成判断标准。
5. 这条属于本类型该写的哪一项？哪一项都不是的就是情形细则，删掉，确认原则、判例或兜底接得住。
