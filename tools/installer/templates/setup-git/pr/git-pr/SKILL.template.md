# 提交 PR

`<分支>` 指承载本次 PR 的分支：第 1 步另建了分支的是新分支，否则是当前分支。
`<推送目标>` 指 `<分支>` 在 `<推送远端>`（见「目标分支」）上对应的分支名：已有开放 PR 的取它的 head 分支，否则同 `<分支>`。

## 流程脚本

记录、压平、推送、清理里的机械操作由仓库 `.githooks/` 下的 `flow-*.sh` 完成。一律执行主工作副本里的那份（从目标分支新切出的 worktree 里可能还没有这些文件），下文写的 `flow-<名>.sh <参数>` 都指：

```bash
sh "$(git worktree list --porcelain | sed -n '1s/^worktree //p')/.githooks/flow-<名>.sh" <参数>
```

退出码 1 是脚本停下了：下文点名了的原因按下文处理，其余原因汇报，输出里的提示转述给用户、不自行照做；退出码 2 或脚本不存在，汇报。

## 目标分支

- 调用时指定了分支就提到那个分支，不改项目默认值，也不改别的分支的记录。
- 没指定、而当前分支记录了 `git config branch.<当前分支>.targetBranch` 时，提到它记录的分支。
- 没指定、也没有这条记录时，提到 `{{PR_BASE}}`（本项目默认的 PR 目标分支）；没有定下默认值的，提到主工作副本检出的分支。
- 当前分支已有开放的 PR、它的 base 与上面定出的目标分支不一致时，先问用户提到哪个，问完再做第 1 步：第 2 步起的改写与推送会直接更新这个 PR。
- 动手前先定两个远端：`<远端>` 是目标分支所在、只用于基准与比较的远端；`<推送远端>` 是 `<分支>` 推往、PR head 所在的远端，fork 工作流里两者不同。
  - 当前分支已有开放 PR 的（head 的仓库与分支都要对上，不只看分支名）以它为准：`<远端>` 取 base 仓库对应的远端，`<推送远端>` 取 head 仓库对应的远端。
  - 没有 PR 的按 git 配置推断：`<远端>` 看目标分支的上游，`<推送远端>` 看 `branch.<分支>.pushRemote`、`remote.pushDefault`，再看分支自己的上游（指向目标分支的不算），都没有就取 `<远端>`。
  - 推断不出或有歧义（对应的远端不存在、唯一的远端是 fork、别的远端也有目标分支等）就问用户，一次问清两个。
  - 判断分支是否推过、推送、PR 的 head 一律用 `<推送远端>/<推送目标>`，PR 建在 `<远端>` 对应的仓库：用错了会在别的仓库新建分支或建错 PR，已有 PR 停在旧内容上。
- 定好远端后只 fetch 本次要用的两个分支：第 1 步前 `git fetch <远端> <目标分支>`；第 1 步定下 `<分支>` 后、第 2 步判断是否推过前 `git fetch <推送远端> <推送目标>`，它报远端没有这个分支就是还没推过。不用 fetch 全部远端与分支：用不上，分支与 tag 多时还会慢很多。
- 压平、rebase 与比较的基准一律取 `<远端>/<目标分支>`，不取本地目标分支：合并发生在远端，本地目标分支可能领先远端，以它为基准会把没推送的本地提交垫进 PR。

## 步骤

操作被仓库的 git hook 拦下时照提示处理，不要绕过。提交信息、PR 标题与描述按文末「撰写身份」写。

1. **准备分支**：有未提交的改动时先问用户是否纳入本次 PR：纳入的先提交；不纳入的等用户自行提交或 stash 后再继续，不要替他处理。
   没有领先 `<远端>/<目标分支>` 的提交就告知用户没东西可提，结束。
   `git log <远端>/<目标分支>..HEAD` 里混有不属于本次 PR 的提交，先问用户，去向由用户定、不替他丢弃。
   **在目标分支上**的：用户要把其中一部分留在目标分支上的，汇报，由用户处理；否则先 `git switch -c` 另建新分支承载这些提交（按变更类型取 `feat/`、`fix/` 等前缀），再用 `git branch -f` 把本地目标分支退回远端位置，不然这些提交会残留在上面。
2. **压平**：
   - 先执行 `flow-record.sh <分支> <目标分支> $(git merge-base HEAD <远端>/<目标分支>)`，记下目标分支与切出点（`<目标分支>` 写分支名，不带远端前缀）。
   - 分支已推送过的（`<推送远端>` 上已有 `<推送目标>`），压平和第 3 步的 rebase 都会改写已推送的历史：远端那个分支有本地没有的提交（如在网页上采纳的建议、维护者推的修复）时先汇报，不要覆盖；没有的，动手前先确认能强推：只限自己独用的分支（远端上没有别人的提交；拿不准就问用户），且用户同意；不满足就停下，不要先改写。
   - 动手前先记下 `git rev-parse HEAD`（下称 `<压前提交>`）。
   - 多个提交默认压成一个：提交信息写进工作树之外的临时文件（如 `mktemp` 建的），执行 `flow-squash.sh <远端>/<目标分支> <文件>`；它报原提交声明过的撤销缺了的，补进提交信息重跑。
   - 确实包含多个互不依赖的变更时才保留多个：在原基点 `git merge-base HEAD <远端>/<目标分支>`（不是记着的切出点）上自己拆，基点换了而内容没合会悄悄撤销目标分支上的改动；
     拆完执行 `flow-squash.sh --check <远端>/<目标分支> <压前提交>`，不通过就按它给的命令退回重做。
3. **rebase 到最新的目标分支**：`git rebase <远端>/<目标分支>`。解冲突要把双方的改动合起来，不要一律取自己这一侧。
   rebase 后、第 4 步前**验证**：按改动范围跑检查。范围：

   {{include: check-scope}}

   同一份内容只验证一次：压平与没带进新代码的 rebase 不改变内容。
   rebase 或 merge 之后，下面任一成立就不再验证，拿不准就验证：
   - 当前 `git rev-parse HEAD^{tree}` 与本次会话里检查通过（覆盖按上面算出的范围）、之后原样提交的那份内容的文件树相同（带进新代码、解冲突、补改都会让它不同）；
   - 属于上面范围里带进新代码后不必重跑的情形。
   验证失败是本次改动引起的，改好并回原提交（保持压平后的提交划分）后重新验证；判断不清或不是本次改动引起的，汇报、不推送。
4. **推送前预检**：工作树里没有 `.githooks/revert-gate.py`（仓库没有回退闸门）的，直接做下面的「人工核对」；有的，先确认 hook 入口、再跑预检。

   **hook 入口**：它管第 5 步推送时的自动检查，缺了不影响预检。
   - 配置文件里设了 `core.hooksPath` 的（以 `env -u GIT_CONFIG_COUNT -u GIT_CONFIG_PARAMETERS git config core.hooksPath` 有输出为准；`-c` 或环境变量 `GIT_CONFIG_COUNT` 临时给的不算）：它指向的 `pre-push` 里没有调用 `.githooks/hook.sh` 就告知用户，继续往下做，不执行 `install.sh`。
   - 没设的：`$(git rev-parse --git-common-dir)/hooks/pre-push` 里没有 `# revert-gate hook entry` 一行，就在仓库（或当前 worktree）根目录执行
     `sh .githooks/install.sh` 补装并告知用户；仓库里没有 `.githooks/branches` 时加 `--pr-only`。

   **预检**：执行下面的命令，它读的是 `<远端>/<目标分支>` 上的脚本，整条命令的退出码就是预检的退出码：

   ```bash
   s=$(git show "<远端>/<目标分支>:.githooks/revert-gate.py" 2>/dev/null) || { echo "闸门未就绪" >&2; (exit 3); } && python3 -I -c "$s" check-pr <远端>/<目标分支> <分支>
   ```

   | 退出码 | 含义 | 做什么 |
   |---|---|---|
   | 0 | 通过 | 往下做第 5 步 |
   | 1 | 查出了问题 | 按输出的原因：还没 rebase 的回第 3 步；撤销了已有改动的按「撤销了已有改动」处理；其它原因汇报 |
   | 2、3 或其它 | 闸门自身出错，或预检跑不起来（闸门还没合进目标分支、没有 `python3` 等） | 做人工核对，不当作通过 |

   **人工核对**：逐个检查 `git log <切出点>..<远端>/<目标分支>`（`<切出点>` 是 `git config branch.<分支>.forkPoint` 的值）里的提交，
   确认它们的改动在当前分支里都还在；有改动不见了，按「撤销了已有改动」处理；核对过了告知用户这次没用上闸门。

   **撤销了已有改动**（预检报的，或人工核对发现的）：先判断是不是有意删除，判断不了就问用户。
   - 出了错的（压平或解冲突丢了改动）：回到第 2 步记下的 `<压前提交>`，重新压平并 rebase。
   - 确实要删掉切出点之后目标分支上新增内容的：先问用户，同意后用 amend 在做了这个删除的提交的信息里，
     为每个被撤销的提交加一行 `Reverts: <sha>`，再回到第 4 步。
5. **推送**：执行 `flow-push.sh <推送远端> <分支> <推送目标>`；报要改写已推送的历史的，第 2 步已确认能强推的加 `--force` 重跑，否则停下问用户。
6. **提交 PR**：建在 `<远端>` 对应的仓库，base 取 `<目标分支>`，head 取 `<推送远端>` 上的 `<推送目标>`（写明它所属的账号或仓库）。该分支已有开放的 PR 就不重建，推送已更新它；它的 base 与 `<目标分支>` 不一致的（动手前已问过用户），改成 `<目标分支>`。
7. **清理本地**：PR 已存在（新建或已有）就立即清理，这是提交 PR 的一部分，不必再问。先回到主工作副本（分支自己的 worktree 会被删掉），执行 `flow-cleanup.sh <分支> --pushed-to <推送远端>/<推送目标>`。
   - 报 worktree 里有被忽略的文件：除依赖、构建产物这类可重新生成的之外还有别的（如 `.env`、本地配置），先问用户要不要留；都能删的加 `--ignored-ok` 重跑。
   - 报其它原因的汇报，不要绕过脚本手工删。

## PR 建好之后又冲突

本次调用结束后目标分支又前进、PR 报冲突，用户再来处理时：

- 分支与 PR 由用户指定，没指定就问；动手前按「目标分支」一节定远端并 fetch 本次要用的两个分支，未提交的改动按第 1 步处理。本地分支已在第 7 步删掉的，`git switch -c <分支> <推送远端>/<推送目标>` 从远端重建，目标分支与切出点按第 2 步重新记。
- 问用户用 merge 还是 rebase 解：merge 的把 `<远端>/<目标分支>` 合进分支，merge 前本地分支要包含 `<推送远端>/<推送目标>`（落后就快进，分叉就汇报），解冲突同第 3 步；合并带进了新代码，按第 3 步验证、过第 4 步的预检后按第 5 步推送；这条路不改写已推送的历史：验证、预检或推送出了问题一律汇报，不加 `--force`；rebase 的按第 2–5 步走（选了就是同意强推，独用与否仍按第 2 步核对）。两种推送后都按第 7 步清理本地。

## 撰写身份

适用于所有提交信息（含 amend 的）、PR 标题与描述，语言跟随仓库历史：

- 不留任何 AI 痕迹：不写 `Co-Authored-By`、不写「Generated with …」、不提 AI 协助。
