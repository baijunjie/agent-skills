# 工作流

本节只定开工前与交付前何时调用什么、按什么顺序、何时跳过；每一步怎么做以对应的 skill 为准。
{{include: fallback-report}}

## 开工前

- 先确认分支是最新的：只 fetch 当前分支要合回去的那个分支（不必 fetch 全部），再看当前分支相对它有没有落后，落后就先对齐再动手；
  对齐不改写已推送、又不是自己独用的分支的历史。
<!-- if-installed: agent-docs -->
- 按 `agent-docs` skill 了解项目上下文。
<!-- end-if -->

## 交付前

自检针对本次改动全部写完后的一次**完整交付**，不是每一次编辑，阶段性提交也不算；用户要求推送、发 PR 或合并也算交付。交付时：

- 有需要用户确认的内容（待拍板的决定、要问的问题、用户说过要先过目的改动、影响较大的自行决定），
  先汇报，按反馈改完再重新判断。
- 没有就按以下顺序逐项自检：

<!-- if-installed: agent-unit-test -->
1. **补单元测试**：按 `agent-unit-test` skill 为本次改动补测试。
<!-- end-if -->
<!-- if-installed: agent-gallery -->
2. **gallery**：按 `agent-gallery` skill 让 gallery 跟上，要不要做、快速检查跑不跑、跑哪个范围以它的判定为准。
3. **UI 预览**：上一步做完就按 `agent-gallery` skill 给用户预览，不等后面各步；要不要预览、要不要等确认以它的判定为准，
   用户说过要先过目的界面也在这一步给，不在自检前先报。要等确认、或要等用户答复临时场景留不留的，得到答复后才进入下一步：
   用户可能还要改界面或留下场景，先跑后面各步会白跑。
<!-- end-if -->
<!-- if-installed: agent-change-check -->
4. **改动检查**：按 `agent-change-check` skill 审本次改动；审查通过、或剩余意见已由用户定下并按决定改完后，才进入下一步。
<!-- end-if -->
<!-- if-installed: agent-docs -->
5. **文档更新**：本次改动要更新给后来者看的文档时，按 `agent-docs` skill 更新。
<!-- end-if -->
6. **格式化与检查**：先执行项目约定的格式化命令改写代码，再按改动范围跑检查，确认都通过；不通过就改，改完按改后的改动重新定范围再跑（改了行为、逻辑或界面的按下面「自己又改了」重走）。
   这次交付走项目的合并流程、且它会把分支对齐到最新的目标分支的，这里只格式化并提交本次改动，检查放到它对齐之后、合并或推送之前跑一次：
   那时目标分支的新代码已经带进来，不必对齐前查一遍、对齐后再查一遍；合并流程在对齐后本就验证的，那次验证覆盖到的不另跑，没覆盖到的检查紧接着补跑，在向用户确认合并或推送之前。
   在合并流程里为通过检查或解冲突改了行为、逻辑或界面的，合并或推送前停下，按下面「自己又改了」重走，再回到合并流程。
   不走合并流程、或合并流程不对齐的，就在这里跑；推迟的检查没在合并流程里跑成（流程中止、改为不走它交付）的，交付前回到这里补跑，只格式化、提交不算做过检查。范围：

   {{include: check-scope}}

格式化与检查只按「格式化与检查」这一步跑、在交付（推送、发 PR 或合并）之前；前面各步不另跑（各步为确认自己的改动而跑的相关测试不算）。

- **自己又改了行为、逻辑或界面**（按改动检查的意见、按预览反馈、为通过检查、解冲突时改的）：对这部分新改动从第一个相关的步骤起重走；只改格式、类型标注这类机械问题的不重走。
- **同一份内容不重跑**：自检后内容没变的（如只压平），之后推送、发 PR 或合并不重做；检查后 rebase 或 merge 又从目标分支带进了新代码的，
  重跑检查（范围与不必重跑的情形见上面的范围）。
<!-- if-installed: agent-gallery -->
- **收尾**：交付（推送、发 PR 或合并）之前，按 `agent-gallery` skill 收尾清理；放弃这次改动或删掉工作副本之前同样要收尾。
<!-- end-if -->
