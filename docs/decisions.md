# 已定决策与不变量

面向本仓库的维护者。下面每条都已定下，怎么对照见 `docs/checklist.md`「动手前」；要推翻某条，先改这里并写明新理由。
每条后的「为什么」是定下它的理由，「校验」指出有没有机器检查兜底。AGENTS.md 或 `docs/` 下其它文档已有细则的只写结论并指过去。

## 宿主行为

### 同名优先级只在有依据处说明

- Claude Code：同名 skill **用户级优先于项目级**（与就近优先的直觉相反）；同名子代理**项目级优先于用户级**。
- Codex：没有官方原文说明同名优先级，安装器里不下断言。
- 安装器只在上面两条有依据的地方说明，文案只在 `tools/installer/fragments/skill-priority.md`、`skill-priority-project.md`、`subagent-rule.md` 三个片段里维护。

为什么：两条 Claude Code 规则方向相反、又反直觉，写错一次就会让用户以为项目级定制生效了；Codex 没有原文时写任何一边都可能是错的。
校验：`build.py`「片段放法」保证每个片段在一个安装器里至多出现一次；放在哪些源文件里不校验，见 `tools/installer/fragments/` 各片段文件开头的说明块。

### Codex 用户级 skill 固定装到 `$HOME/.agents/skills`

Codex 文档只列出这一处用户级 skill 位置，安装器就固定写它，不按 `${CODEX_HOME:-$HOME/.codex}/skills` 回退；`$CODEX_HOME` 只用于 agents 等配置目录。

为什么：写进文档没列的目录，Codex 可能根本不扫描，装了等于没装。
校验：`build.py`「命令块」项拦下生成物里的 `$X/skills`、`$CODEX_HOME/skills`、`.codex/skills` 等旧位置；各安装器直接写 `D="$HOME/.agents/skills/<名>"`。

### 应用 skill 与子代理模板里不写宿主差异

装出去的 skill、子代理模板正文不出现「Claude Code 下…，Codex 下…」的分支；宿主差异只写在安装器里，由安装器按宿主装出对应内容（必要时由 `plugins/setup-agent/scripts/` 的渲染脚本生成）。

为什么：装出的文件只在一个宿主里被读，写进另一宿主的说明是噪音，还会随宿主变化各自过期。
校验：无，靠复核。

## 安装器行为

### 重装语义

- 每次运行都按当前模板重装，不判断版本，也不与模板比对。
- 流程固定为：查软链 → 查冲突，有冲突问用户「完全覆盖」还是「融入现有内容」→ 读定制值 → 只清理本安装器装出的 → 装新的 → 填回定制值。
- 定制值以外的手改会被覆盖，安装器告知用户这一点。
- 要写入、替换或删除的路径是软链时，一律停下来问用户，不自行处理。

为什么：按版本判断要维护版本记录、还会漏掉手改过的安装；只清理本安装器装出的才不误删别人的内容；软链写入会写穿、删除会脱钩，且都不报错。
校验：`build.py`「片段放法」要求每个源文件各 include 一次 `pre-write`、`reinstall`、`state-mismatch`，且其后紧跟「本安装器另外要查的冲突：」「本安装器的定制值：」；定制值是否逐项写明来源与填回时机不校验。

### 指令文件内容用成对标记界定

安装器往 `CLAUDE.md` / `AGENTS.md` 写的内容包在成对的 HTML 注释标记 `<!-- setup-<领域>:<skill>:begin|end -->` 里，重装只替换本安装器的标记范围。只有写指令文件的 5 个安装器用标记：`setup-agent:subagents`、`setup-agent:report-style`、`setup-agent:workflow`、`setup-git:worktree`、`setup-tools:cron`。

为什么：按标题找会误伤用户自己写的同名节；不写指令文件的安装器带上标记只会制造无主的标记。
校验：`build.py`「标记」项（格式、名字、成对，以及写指令文件与 include `markers` 互为充要）。

### 写进指令文件的内容顶层用一级标题

安装器往指令文件写的内容，标记范围里最浅的节标题是 `#`；目标文件把 `#` 只用作全文的文档标题、用 `##` 分节时，
写入后整块降一级对齐。规则原文在 `tools/installer/fragments/markers.md`「标题层级」，各安装器不另行陈述。
`setup-agent:subagents` 的用户级安装是后一种情形的实例：指令文件里已有「# 全局规则」时按 `--no-header` 渲染，
顶层留在 `##` 挂到它底下。

为什么：几个安装器各按自己的假设定层级时，顶层写 `##` 的那几节会挂到上一节底下成为它的子节，而文件本身不报错、
看不出来；统一到 `#` 还不要求指令文件有一个统管全文的 `#` 标题。
校验：`build.py`「标记」项查 `template/` 里带成对标记的文件；渲染脚本输出的层级由 `tools/tests/scripts/` 的
`rules_*`、`style_*` 用例覆盖。

### 专职 skill 不自挂触发点

- 装出的专职 skill（`agent-docs`、`agent-unit-test`、`agent-change-check` 等）不往指令文件里挂触发说明，只靠自己的 `description` 被自动触发。
- 开工前与交付前的工作流只由 `setup-agent:workflow` 写入指令文件的「工作流」一节；规范如何改这一节的 `agent-workflow-edit` 只在 workflow 安装器自己的源文件、生成物与模板里出现，其它安装器、装出的 skill 与 README 都不提它的名字。
- 例外：同一安装器既写指令文件、又装出配套的操作 skill 时，可以在**自己的标记范围内**点名那份 skill 作为操作入口（目前只有 `setup-git:worktree` 指向 `git-worktree`）。标记范围由该安装器独占、只有一处、重装时整份覆盖，不会散落也无需别人统筹，所以不算自挂触发点。指令文件里只写无条件生效的约定与这个入口，操作细节只写在 skill 里，两边不复述。

为什么：各 skill 各挂一段会让工作流散落在指令文件多处、顺序无人统筹，增删 skill 时也没人收拾。
校验：AGENTS.md「硬规则」里关于工作流的那条是规则本身；`build.py`「标记」项会拦下不 include `markers` 却写指令文件的安装器。`agent-workflow-edit` 的出现范围不校验，可用 `grep -rn agent-workflow-edit` 核对；例外那条也不校验，可用 ``grep -rn '`git-worktree` skill'`` 核对点名只出现在 worktree 安装器自己的源文件、生成物、模板与 `README.md` 的说明列里。

### 不写迁移与兼容说明

skill、安装器、模板、README 里不得出现针对旧版本的迁移步骤或兼容说明（「旧版装过的先删 X」「兼容老格式」之类）。

为什么：重装语义已经是「按当前模板整体重装」，迁移说明既多余，又会随版本积累、永远删不掉。
校验：无，靠复核。

### 作用域三取值与固定措辞

安装器作用域只有 `project`、`project-user`、`user` 三种，在 `build.py` 的 `INSTALLERS` 声明；description 里的作用域措辞由 `build.py` 按作用域注入（`{{scope_lead}}` / `{{scope_tail}}`），源文件不手写。取值含义见 `docs/installers.md`「命名与归属」。

为什么：手写措辞会在十几个安装器里各自走样，作用域与正文的安装节也容易对不上。
校验：`build.py`「frontmatter」与「作用域」项。

### 步骤引用与模板替换原文

- 正文里的「第 N 步」不超过编号列表的最大序号。
- 要求改写模板原文的写成 `| 位置 | 原文 | 改成 |` 替换表，原文须在模板里恰好出现一次。

为什么：步骤重排后旧引用、模板改字后替换原文都会悄悄失效，装出的结果错了也不报错，多次整改都在补这类遗漏。
校验：`build.py`「步骤引用」「替换表」项；约定写法见 `docs/installers.md`「源文件契约」。前者只是最大步号检查，不保证指向正确的步骤。

## `setup-git:worktree` 的回退闸门

### 保证什么

- 拦下改写受守护分支上已发布的历史。
- 拦下撤销受守护分支上已有改动的更新（压平换了基点、解冲突只取自己一侧）。
- pre-push 时远端有本地没有的提交就拒绝，防止 `push --force` 覆盖队友刚推的提交。
- 对齐远程（`git rebase <目标分支>@{u}`）时丢了改动，在 rebase 当场拦下，而不是等到推送。

### 不保证什么（已知边界）

- 先 `git switch --detach` 再 `git branch -f` 退回、而特性分支仍持有那些提交，之后再删掉特性分支：与合法流程形态相同，放行。
- 被丢下的未推送提交只新增内容时拦不住（撤销纯新增的提交同理）。
- `git push --no-verify` 跳过 pre-push 一层；`REVERT_GATE_SKIP=1` 整体跳过；闸门自身出错时放行。

为什么：边界都是为了不误拦正常操作（删掉做完的计划文档、去掉临时代码、闸门故障不能卡死所有 ref 更新）而有意留下的，把它们写成「保证」会让人依赖闸门而不自己遵守规则。
校验：闸门行为的测试放在 `tools/tests/`；规则原文见 `plugins/setup-git/skills/worktree/template/githooks/revert-gate.py` 的模块 docstring。

### 团队工作方式

- 常见做法是在目标分支上攒多个提交再统一推送，不长期保留开发分支。
- 推送被拒后的恢复流程：`git fetch` → 在目标分支所在的工作副本里 `git rebase <目标分支>@{u}` → 重新验证 → 从目标分支切出的开发分支用 `git rebase --onto <目标分支> <旧位置>` 只搬自己的提交 → 再推送。
- 不强推目标分支。

为什么：目标分支上的本地提交会被 rebase 改写，从它切出的分支直接 rebase 会把改写前的提交再搬一遍；强推会覆盖队友的提交，闸门也会拒绝。
校验：操作步骤原文在 `plugins/setup-git/skills/worktree/template/git-worktree.md`（写进指令文件的那几条约定在同目录的 `rules.md`），闸门测试见上。

## `setup-agent:plan`

- 自足里程碑收尾时删掉它的文档，在总览 `README.md` 的里程碑清单里保留一行 `NN 已收尾`。
- 往已有主题追加里程碑时，编号接在清单与目录里出现过的最大编号之后，不填补缺口，已有文档不改号。
- 删除放在按完成判据的验证通过、且项目要求的审查（若有）也通过之后。

为什么：留下 `NN 已收尾` 才不会让后来的里程碑复用编号——留账文档和代码里的 `TODO` 按编号写着由谁删；验证或审查没过就删，返工时就没有设计依据了。
校验：无，规则原文在 `plugins/setup-agent/skills/plan/template/` 下的两个模板。

## 文案

### 固定用语

| 用语 | 含义 |
|---|---|
| 汇报 | 停下来，等对方做决定后再继续 |
| 在最终回复里写清 | 不停下，写进本次的最终回复 |
| 交给用户定 | 停下来，等用户决定 |
| 告知用户 | 只告知，不停下 |

「告诉用户」已禁用：分不出停不停，按意思改成上表里的「汇报」「告知用户」或「交给用户定」。

为什么：「停不停」是 agent 行为上最关键的差别，同一意思换着说法写会让 agent 在该停时不停、不该停时卡住。
校验：`build.py`「文案」项拦下 `tools/installer/sources/` 与 `fragments/` 里的「告诉用户」；安装器的 `template/` 不校验，靠复核与 `grep -rn 告诉用户`；其余用语用得对不对靠复核。

### README 说明列只写一句话

README 的 skill 索引表「说明」列只写一句话（装什么、解决什么问题、有无改指令文件或装子代理之类的特殊影响），不要求与生成物逐条对应；实现细节以安装器和装出的 skill 为准。规则本身在 `docs/authoring.md`「新增 skill」。

为什么：README 面向安装者，把实现细节抄进去，每次整改都要同步一遍、而且总有一处没同步。
校验：无。

## 发布与开发约束

### 版本只升一次

相对已发布版本（`origin/main` 上的 `version`）只升一次，细则见 `docs/release.md`「发布」；已推送的提交怎么处理见 AGENTS.md「硬规则」。

为什么：未发布的连续改动在用户看来是同一个版本。
校验：`tools/tests/manifest/` 套件比对工作副本与 `origin/main` 上的 `version`：内容有变化的 plugin 必须恰好升一级，没变的必须不变；依赖本地有 `origin/main`，没有时（如无远程）该项报 SKIP、不算失败。

### 不在真实仓库里做 git 实验

任何人（含子代理）都不在本仓库的工作副本里做 git 实验；需要实验时各自用 `mktemp -d` 建临时目录、复制一份副本在里面做，用完只删自己的目录。

为什么：实验里的 commit、reset、checkout 会改写真实仓库的分支、索引与工作树，已经出过一次事故；共用一个临时目录则会互相覆盖、误删。
校验：无，靠自觉。

### 工作流配置默认放行，不拿「是否放行」问用户

`.claude/settings.json` 的 `permissions.allow` 不为了防误用而收窄（如 `git branch`、`git remote`、`find`、`git log/diff/show` 的整条前缀放行）。判断一类问题该不该问用户：用户没有别的选择来继续任务（典型如权限是否放行，不放行只能终止任务），就不问，最大程度放行；只有会造成用户无法预期的破坏性灾难的，才不放行或要求确认。

为什么：目标是尽可能自动完成工作循环，没有备选项的询问只会打断任务，却不给用户任何决定空间。
校验：无，靠复核。
