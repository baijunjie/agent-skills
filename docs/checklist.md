# 检查清单

什么时候读、谁来对照见 AGENTS.md「什么时候读什么」的总则。每条冒号前是要求，后面是原因；跑命令、grep 这类机械检查由实施者做，判断性的核对由子代理在交付前做。

## 安全

- 跑实验、测试或任何会改 git / crontab 状态的命令时，守 `tools/tests/README.md`「安全设计」的「实验与危险命令」：落到真实仓库或真实 crontab 上的改动不可逆，也未必报错。

## 动手前

- 读 `docs/decisions.md`，不推翻已定决策，用其中「固定用语」的说法：已定议题重新讨论只会来回改。
- 同名优先级、各宿主路径与行为等事实，先查到官方文档原文再写，查不到就不断言：曾因写错事实整体删除又恢复。

## 改动后

- 改源文件、片段或安装器的 `template/`，按 `docs/installers.md`「生成」跑 `build.py` 与 `--check`，不手改生成物；改的是公共片段时跑全套测试：片段影响所有引用它的安装器。
- 按 `tools/tests/README.md` 的套件表跑改动对应的套件，并在该套件补用例：闸门发现新绕过先补用例再修；改 `build.py` 或加校验时在 `build/` 加破坏用例（校验项见 `build.py` 顶部注释）；改渲染脚本、`project-root` 或 cron 模板的行为时在 `scripts/`、`cron/` 补用例：没有用例的规则坏了没人发现。
- 删除或改写一个说法后用 `grep -rn` 全仓确认没有残留旧说法：曾因「编号缺口」等旧说法残留造成前后矛盾。
- 增删或重排安装器步骤后，交付前由子代理核对所有「第 N 步」引用、重装节、定制值的读出与填回、冲突检查的指向：`build.py` 只查最大步号，指错了不报错。

## 内容

- 安装器与 skill 只写 agent 难以辨明的方向和本仓库特别制定的事项，不写常识与变更历史：多余内容会稀释真正的规则。
- 同一规则只在一处陈述，其余引用：曾因多处复述反复不一致。
- 交付前、复核时由子代理对照 `docs/decisions.md`「应用 skill 与子代理模板里不写宿主差异」、`docs/installers.md`「源文件契约」的填写项要求与 `docs/authoring.md`「新增 skill」的 README 说明列：这几条最常漏。

## 命令块

- 每个命令块按独立 shell 写，变量块内先定义后使用，关键变量写成 `${VAR:?}`：shell 状态不跨调用，空变量会让路径落到别处。
- 写入前先查软链，整份替换用 `--replace`（见 `docs/authoring.md`「附带资源与共享模板」）：先删后写会把软链换成普通文件，失败时旧文件也没了。
- 进仓库根写成 `top=$(git rev-parse --show-toplevel) && cd "$top" || exit 1`：`cd ""` 会成功并留在原目录。
- 需要用户决定的检查放在第一条会写入的命令之前：写完再问已经来不及。

## 提交前

- `bash tools/tests/run.sh` 全绿；生成物首行 `---`、`name` 与目录名一致；改过的 JSON 都能解析；工作区没有 `__pycache__` 等残留：这些不全在测试覆盖内。
- 改了内容的 plugin 三份 manifest 版本一致，且相对已发布版本只升一次（见 `docs/release.md`「发布」；由 `tools/tests/manifest/` 套件检查，依赖本地有 `origin/main`）：版本是两个宿主判断更新的唯一边界。

## 复核

- 复核意见先归到根因再定解法，不逐条机械整改：逐条补丁会在别处留下同类问题。
- 发现缺陷先补测试或校验：同类问题以后由机器拦下，不再靠人工复核发现。
- 不因反复发现问题就缩小或终止复核：反复出现说明根因还没解决。
