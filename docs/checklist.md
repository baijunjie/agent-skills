# 检查清单

什么时候读、谁来对照见 AGENTS.md「什么时候读什么」的总则。每条冒号前是要求，后面是原因；跑命令、grep 这类机械检查由实施者做，判断性的核对由子代理在交付前做。

## 安全

- 跑实验、测试或任何会改 git / crontab 状态的命令时，守 `tools/tests/README.md`「安全设计」的「实验与危险命令」：落到真实仓库或真实 crontab 上的改动不可逆，也未必报错。

## 动手前

- 读 `docs/decisions.md`，不推翻已定决策，用其中「固定用语」的说法：已定议题重新讨论只会来回改。
- 同名优先级、各宿主路径与行为等事实，先查到官方文档原文再写，查不到就不断言：曾因写错事实整体删除又恢复。

## 改动后

- 改源文件、片段或安装器的 `template/`，按 `docs/installers.md`「生成」跑 `build.py` 与 `--check`，不手改生成物；改的是公共片段时，提交前跑全套测试：片段影响所有引用它的安装器。
- 按 `tools/tests/README.md` 的套件表确定改动对应的套件，并在该套件补用例（测试只在「提交前」跑，开发与整改的中途不跑；只有正在调试某条用例时才单独跑它所在的套件）：闸门发现新绕过先补用例再修；改 `build.py` 或加校验时在 `build/` 加破坏用例（校验项见 `build.py` 顶部注释）；改渲染脚本、`project-root` 或 cron 模板的行为时在 `scripts/`、`cron/` 补用例：没有用例的规则坏了没人发现。
- 删除或改写一个说法后用 `grep -rn` 全仓确认没有残留旧说法：曾因「编号缺口」等旧说法残留造成前后矛盾。
- 改闸门判据时同时补 `tools/tests/mutation/` 的 `teeth_*`（改坏这条判据，声明哪几条 gate 用例会 FAIL）：全套绿不代表这段逻辑有人盯着，这类「改坏了没人发现」已经出过两次。
- 增删或重排安装器步骤后，交付前由子代理核对所有「第 N 步」引用、重装节、定制值的读出与填回、冲突检查的指向：`build.py` 只查最大步号，指错了不报错。

## 内容

- 安装器与 skill 只写 agent 难以辨明的方向和本仓库特别制定的事项，不写常识与变更历史：多余内容会稀释真正的规则。
- 同一规则只在一处陈述，其余引用：曾因多处复述反复不一致。
- 交付前、复核时由子代理对照 `docs/decisions.md`「应用 skill 与子代理模板里不写宿主差异」、`docs/installers.md`「源文件契约」的填写项要求与 `docs/authoring.md`「新增 skill」的 README 说明列：这几条最常漏。

## 命令块

- 每个命令块按独立 shell 写，变量块内先定义后使用，关键变量写成 `${VAR:?}`：shell 状态不跨调用，空变量会让路径落到别处。
- 写入前先查软链，整份替换用 `--replace`（见 `docs/authoring.md`「附带资源与共享模板」）：先删后写会把软链换成普通文件，失败时旧文件也没了。
- 进仓库根写成 `top=$(git rev-parse --show-toplevel) && cd "$top" || exit 1`：`cd ""` 会成功并留在原目录。
- 需要用户决定的检查放在第一条会写入的命令之前：写完再问已经来不及。

## 提交前

只在提交前做一次，开发与整改的中途不跑：测试要跑几分钟，每轮都跑只会重复。

- `bash tools/tests/run.sh` 全绿；生成物首行 `---`、`name` 与目录名一致；改过的 JSON 都能解析；工作区没有 `__pycache__` 等残留：这些不全在测试覆盖内。
- 改了内容的 plugin 三份 manifest 版本一致，且相对已发布版本只升一次（见 `docs/release.md`「发布」；由 `tools/tests/manifest/` 套件检查，依赖本地有 `origin/main`）：版本是两个宿主判断更新的唯一边界。

## 复核

分三类：通用的对所有对象成立；程序化逻辑（闸门、`build.py`、渲染脚本、cron 模板）有测试可补，复审时盯着整改的差异；skill 与安装器的文本没有测试，靠换一个不知情的使用者来发现问题。

### 通用

- 复核意见先归到根因再定解法，不逐条机械整改：逐条补丁会在别处留下同类问题。
- 不因反复发现问题就缩小或终止复核：反复出现说明根因还没解决。

### 程序化逻辑

- 发现缺陷先补测试或校验：同类问题以后由机器拦下，不再靠人工复核发现。
- 整改完复核意见后，再由子代理复审这次整改的增量：整改本身改出新缺陷、或只换了说法没动根因，都出过。

### skill 与安装器的文本

「内容」「改动后」里按已有条款核对的检查仍告诉子代理查哪几条；审措辞与逻辑本身时反过来，不告诉它：

- 把子代理当成第一次拿到这份 skill 的使用者派出：只给 skill 文件的路径，说明目标是让它易于理解、逻辑通顺、上下文不自相矛盾，不说改过什么、定过什么、该查哪几条：提示会框住它的注意力，作者自己看不到的问题就查不出来。
- 不让它读仓库里的其它文档来补全理解：skill 要自足，靠别处文档才读得懂本身就是缺陷。
- 让它自己设想真实情形（没指定对象、指定了、卡住了、做完了等），在脑中逐一走一遍，看能不能明确知道下一步：只通读不走情形，发现不了「走到这一步不知道怎么办」。
- 要求每条报告写明位置、遇到的情形、问题、建议改法，按严重度排序，没问题的方面不凑数：没有情形的意见无从判断是否成立，凑数的意见稀释真问题。
- 同时要它指出多余的句子：读了不影响行动的、重复别处已说的规则、agent 本来就会这么做的常识，每条写明删掉后执行结果有没有变化：多余内容会稀释真正的规则，整改时又只增不减，不专门查就没人删。
- 一份 skill 派一个子代理，成对的 skill 也各审各的，并行：互相看过对方，就会替对方补全，看不出各自不自足的地方。
- 拿到意见后先按「通用」归根因再改；涉及设计取舍的，整理成互斥选项交给用户定，不替用户选：判据一旦改错，后面每一轮都在错的基础上审。
- 整改后换新的子代理再审一轮，直到只剩措辞层面的零星意见：同一个子代理已经知道改了什么，不再是第一次使用者，所以这里不用「程序化逻辑」里的复审增量。
